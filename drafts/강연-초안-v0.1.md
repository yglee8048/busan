# 부산 스타트업 강연 구성 초안 v0.1

> 3개 세션 × 45분 + 질의응답. 두 회사 모두 동일한 3세션 골격을 쓰고, **세션 내부의 시간 배분과 사례만 회사별로 바꾼다.**

---

## 0. 전체 설계

### 0.1 왜 이 3개인가

세션은 청중이 알고 싶어 하는 순서가 아니라, **답이 성립하는 순서**로 배치한다.

```text
세션 1. 마음가짐        →  "무엇을 기준으로 판단할 것인가"   (판단의 기준)
세션 2. 좋은 소프트웨어  →  "그 기준을 코드와 조직에 적용"   (기준의 적용)
세션 3. AI 시대         →  "도구가 바뀌어도 기준은 남는가"   (기준의 재검증)
```

세션 3의 결론이 세션 1·2로 되돌아오게 설계한다.
> **"AI가 먹기 좋은 코드베이스는 사람이 일하기 좋은 코드베이스와 같다."**
이 한 문장이 3시간을 하나로 묶는 축이다. 회사 2의 질문 목록에 답하면서도 회사 1의 관심사와 분리되지 않는다.

### 0.2 시간표 (4시간 / 09:00~13:00 기준)

| 시각 | 구성 | 비고 |
|---|---|---|
| 09:00~09:10 | 오프닝 · 범위 선언 · 청중 파악 | 손들기 3문항으로 난이도 조절 |
| 09:10~09:55 | **세션 1. 엔지니어로서의 마음가짐** | 45분 |
| 09:55~10:05 | 휴식 | |
| 10:05~10:50 | **세션 2. 좋은 소프트웨어를 만들어 나가는 방법** | 45분 |
| 10:50~11:00 | 휴식 | |
| 11:00~11:45 | **세션 3. AI 시대의 기술 지형 변화와 대응** | 45분 |
| 11:45~12:45 | 질의응답 · 토론 | 60분 |
| 12:45~13:00 | 마무리 · 자료 공유 | |

> 45분 세션은 **슬라이드 35분 + 즉석 질문 10분**으로 쪼갠다. 4시간을 통으로 듣게 하면 후반 집중도가 무너지고, 세션 중간에 나온 질문은 마지막 Q&A까지 살아남지 못한다.

### 0.3 두 회사 모두 동일한 자료로 진행한다

**확정 사항:** 슬라이드는 한 벌만 만든다. 회사별 편집을 하지 않는다. **차별화는 질의응답에서만 한다.**

이 결정이 자료 설계에 주는 제약 3가지:

1. **어느 세션도 줄일 수 없다.** 회사 1이 관심 없어 보이는 세션 3, 회사 2가 이미 안다고 여길 세션 2 모두 45분 풀버전으로 만든다. 각 세션이 단독으로 성립해야 한다.
2. **한쪽에만 유효한 결론을 넣지 않는다.** "여러분 규모에서는 X를 하세요" 같은 문장을 쓰지 않고, **판단 기준**만 제시한다. 어차피 범위 선언과도 일치한다.
3. **각 세션에 다른 쪽 청중을 위한 연결 고리를 심는다.** 회사 1 사람이 세션 3을 들을 이유, 회사 2 사람이 세션 2를 들을 이유를 슬라이드 안에 명시한다.

| 세션 | 회사 1 청중에게 주는 이유 | 회사 2 청중에게 주는 이유 |
|---|---|---|
| 1. 마음가짐 | 공통 | 공통 |
| 2. 좋은 소프트웨어 | 부채·관측·조직 운영의 직접 답 | **AI 도입의 전제 조건** — 3-2로 이어짐 |
| 3. AI 시대 | **부채 정리가 왜 AI 도입의 선행 조건인지** | Harness·Eval·책임의 직접 답 |

> 이 연결 고리는 이미 전체 축(0.1)과 같은 문장이다. 단일 자료로 가는 것이 오히려 강연의 논리를 단단하게 만든다.

**Q&A에서의 차별화는 사전 질문 3개로 만든다.** 회사별로 다른 질문을 미리 받아두면, 같은 자료로 발표하고도 뒷부분 60분이 완전히 달라진다. → 상세 설계는 아래 Q&A 절 참고.

### 0.4 오프닝에서 반드시 할 말 (2분)

> "오늘은 여러분 회사의 시스템을 진단하고 최적안을 드리는 자리가 아닙니다. 8년 차 백엔드 개발자가 겪은 것, 그리고 공개된 기업 사례를 공유하는 자리입니다. 무엇을 가져갈지는 여러분이 정하시면 됩니다."

이 문장을 슬라이드 한 장으로 띄우고 시작한다. 이게 있어야 세션 2에서 실제 사례를 편하게 다룰 수 있다.

## 세션 1. 엔지니어로서의 마음가짐 (45분)

> **한 문장:** 엔지니어링은 정답을 아는 일이 아니라, 불확실성 속에서 **반복적으로 의사결정하는 일**이다. 그래서 좋은 판단의 습관이 복리로 쌓인다.

**주 레퍼런스:** 클린 코더(뼈대) + 월가아재(프레임) + 구글(팀) + 모던 SW 엔지니어링(경험주의)

### 1-1. 오프닝 훅 — 2%의 복리 (5분)

월 100만 원씩 40년 투자했을 때:

| 연 수익률 | 40년 후 |
|---:|---:|
| 8% | 약 32억 |
| 14% | 약 171억 |

연 2%p씩 4번 차이가 139억을 만든다. → **개발자 버전으로 치환한다.**

```text
투자:   매년 반복되는 매매 판단   × 40년  = 자산
개발:   매일 반복되는 설계 판단   × 8년   = 코드베이스의 변경 비용
```

핵심 질문으로 넘어간다.
> "우리 코드베이스의 변경 비용은 지금 매달 몇 % 오르고 있습니까, 내리고 있습니까?"

이 질문은 세션 2 전체의 예고편이기도 하다.

### 1-2. 자연 수익률은 마이너스다 (6분)

월가아재의 "훈련받지 않은 개인의 자연 수익률 -10%" → 개발자 버전:

> **아무 원칙 없이 개발하면 코드베이스는 유지되는 게 아니라 나빠진다. 엔트로피가 기본값이다.**

- "일단 돌아가게" 는 중립이 아니라 마이너스다
- 그래서 **함부로 투자하지 않는 법을 먼저 배운다** → 개발 버전: 함부로 추상화하지 않는 법, 함부로 도입하지 않는 법
- [경험 슬롯 ①] 좋아 보여서 도입했다가 걷어낸 기술/구조 1건. 실패담으로 시작하면 이후 45분의 신뢰가 달라진다

### 1-3. 결과가 아니라 의사결정 과정을 복기한다 (8분)

운과 실력의 분리. 투자에서 "분석한 종목이 떨어지고 아무거나 산 사람이 오르는" 일이 개발에서도 똑같이 일어난다.

- 장애가 안 났다고 좋은 설계였던 것이 아니다 (운일 수 있다)
- 장애가 났다고 나쁜 판단이었던 것도 아니다 (당시 정보로는 최선이었을 수 있다)

**비난 없는 장애 분석** (구글) — 질문을 바꾼다.

| 나쁜 질문 | 좋은 질문 |
|---|---|
| 누가 실수했는가? | 왜 이 실수가 장애까지 갈 수 있었는가? |
| | 시스템은 왜 이걸 미리 못 잡았는가? |
| | 피해를 제한할 장치가 있었는가? |

> 매매일지 = 포스트모템. **결과가 아니라 그때의 가정을 적는다.**

- [경험 슬롯 ②] 실제 포스트모템 문서 한 장 (익명화). 스타트업이 바로 복사해 갈 수 있는 최소 템플릿으로 제시
- 스타트업용 최소 템플릿: `무슨 일이 / 언제부터 언제까지 / 사용자 영향 / 왜 늦게 알았나 / 다음에 뭘 바꾼다` 5줄

### 1-4. 추정과 약속을 구분한다 (10분) ★

세션 1에서 **가장 실용적인 블록.** 클린 코더 9·10장. 대표·PM이 참석한 자리라면 이 블록이 오늘의 하이라이트가 된다.

| 구분 | 의미 | 표현 |
|---|---|---|
| 추정 | 현재 정보에서의 가능성 분포 | "3~5일이 유력, 외부 API 이슈가 있으면 8일" |
| 약속 | 특정 시점까지 하겠다는 표명 | "수요일까지 A 범위를 인수 가능한 상태로" |

날짜 하나만 말하면 듣는 사람은 그것을 약속으로 받아들인다. → 갈등의 대부분이 여기서 시작된다.

**좋은 거절의 문법** (반대가 아니라 협상)

```text
"금요일까지 전체 다" → 불가능

대신:
- 필수 A, B는 금요일까지 가능
- C를 포함하면 다음 주 수요일
- 범위를 유지해야 한다면 순서와 위험을 다시 협의
```

**늦어지면 마감 당일이 아니라 아는 즉시 알린다.** 압박이 클수록 테스트와 작은 변경을 지킨다 — 압박은 규율을 버릴 이유가 아니라 규율이 필요한 이유다.

- [경험 슬롯 ③] 일정 협상 실제 사례. 거절했더니 오히려 신뢰가 올라간 경험
- 이 블록은 개발자에게는 "말하는 법", 대표/PM에게는 "듣는 법"으로 동시에 작동한다

### 1-5. 권위와 유행 대신 증거 (7분)

모던 SW 엔지니어링의 경험주의·실험주의.

```text
추측이나 권위  <  관찰 가능한 증거
```

- "마이크로서비스가 좋다", "이 프레임워크가 빠르다" → **우리 조직, 우리 트래픽에서 검증됐는가**
- 이력서 주도 개발(RDD) 경계. 판교 대기업이 쓴다는 것은 근거가 아니다
- 도구·방법론을 평가하는 두 질문:
  1. 이 방법이 우리가 **더 빨리 학습**하게 하는가?
  2. 이 방법이 **복잡성을 통제**하게 하는가?
- 유효한 실험의 조건: 가설 → 측정할 결과 → 작은 범위 → 결과를 다음 결정에 반영

### 1-6. 혼자 잘하는 것으로는 부족하다 (6분)

구글 2장 + 클린 코더 12·13장.

- **천재 신화 버리기**: 완성될 때까지 숨기면 잘못된 방향을 늦게 발견한다. 초기에 공유하는 게 결국 빠르다
- **겸손·존중·신뢰**: 사람이 아니라 코드와 아이디어를 비판한다
- 코드를 개인 소유물로 만들지 않는다 → 버스 팩터. 스타트업에서 가장 현실적인 리스크
- 문서 작성과 멘토링은 봉사가 아니라 **본업**이다

### 1-7. 마무리 — 내일부터의 5문항 (3분)

- [ ] 이번 판단의 **가정**을 어딘가에 적었는가?
- [ ] 날짜 하나 대신 **범위와 위험**을 말했는가?
- [ ] 못 지킬 것 같은 약속을 **아는 즉시** 알렸는가?
- [ ] 이 기술을 쓰는 이유가 **증거인가 유행인가**?
- [ ] 내가 없으면 멈추는 영역이 있는가?

## 세션 2. 좋은 소프트웨어를 만들어 나가는 방법 (45분)

> **한 문장:** 좋은 소프트웨어는 변하지 않는 소프트웨어가 아니라 **변경 비용이 낮은** 소프트웨어다.

**주 레퍼런스:** 모던 SW 엔지니어링(두 축) + Tidy First(부채) + 구글(프로세스·도구) + 클린 코더(테스트 책임)

### 2-1. 두 개의 축 (4분)

```text
좋은 소프트웨어 엔지니어링
├─ 학습 최적화     : 반복 · 피드백 · 점진 · 경험 · 실험
└─ 복잡성 관리     : 모듈성 · 응집성 · 관심사 분리 · 정보 은닉 · 결합도
```

- 소프트웨어는 **생산이 아니라 설계**다. 계획 실행이 아니라 발견 과정이다
- 이 두 축은 서로를 강화한다: 좋은 설계 → 빠른 피드백 → 더 나은 설계

### 2-2. 피드백 ① — 관측과 장애 대응 (12분)

회사 1의 RDS 관심사를 **일반 절차 설명의 소재**로 사용한다. (진단이 아니라 "이런 순서로 본다")

**장애 대응 5단계**

```text
감지 → 완화 → 원인 → 재발 방지 → 기록
```

대부분의 팀이 `완화`에서 멈춘다. **"쿼리를 죽여서 해결했다"는 대응이지 개선이 아니다.**

**알람이 알람이 되려면**

실제로 자주 보는 안티패턴: 알람이 자주 울려서 임계치를 30 → 45 → 60으로 올리는 것.

> 임계치를 올리는 건 해결이 아니라 **감도를 낮춘 것**이다. 다만 액션 없는 알람은 알람이 아니라 소음이므로, 임계치를 올리는 판단 자체는 틀리지 않았다. 문제는 **그 다음에 무엇을 했는가**다.

좋은 알람의 조건 3가지:
1. **액션 가능**해야 한다 — 울리면 할 일이 정해져 있다 (런북)
2. **사용자 영향** 기준이어야 한다 — CPU 98%보다 "응답 지연 p99 > 3초"
3. **원인이 아니라 증상**을 잡는다 — 원인은 대시보드에서 찾는다

**지표를 보는 순서** (일반론)

```text
사용자 체감 (SLI: 지연/에러율)
        ↓ 무엇이 느린가
요청 단위 (RED: Rate · Error · Duration)
        ↓ 어디가 포화됐나
자원 단위 (USE: Utilization · Saturation · Error)
        ↓ 어떤 작업이 원인인가
개별 쿼리 / 대기 이벤트
```

DB 부하는 **CPU가 아니라 동시 실행 스레드와 DB Load**가 먼저 움직인다. 그래서 "스레드 수 → 1분 뒤 DB Load → 종합 부하" 순으로 알람이 뜨는 건 전형적인 패턴이다.

**원인 쿼리를 빠르게 특정하는 일반적 방법** (자문 요청 5개 항목에 대응)

| 문제 | 일반적 대응 |
|---|---|
| 사후에 어떤 쿼리였는지 모른다 | Slow query log 상시 활성 + Performance Insights 보존 |
| 누가 호출했는지 모른다 | **SQL 주석에 호출자를 심는다** (`/* app=api svc=campaign ep=/list */`) — 가장 저렴하고 효과 큰 한 수 |
| 긴 쿼리가 DB를 잡는다 | `max_execution_time` / statement timeout, 커넥션 풀 상한 |
| 배치가 서비스를 친다 | 읽기 전용 복제본으로 배치·통계 분리 |
| 반복 원인을 모른다 | 주간 Top SQL 리뷰 (pt-query-digest 등) |

- [경험 슬롯 ④] 실제로 겪은 DB 장애 1건. **원인보다 "어떻게 알아냈는지"의 순서**를 보여준다
- 스타트업이 오늘 할 수 있는 것 3개만 뽑아서 제시 (전체 관측 체계 구축은 비현실적)

### 2-3. 복잡성 관리 — 쿼리가 말해주는 설계 (8분)

거대한 조회 쿼리(40+ 컬럼, 10+ LEFT JOIN, GROUP_CONCAT, 상관 서브쿼리)는 성능 문제이기 전에 **설계 신호**다.

> 화면 요구사항이 그대로 쿼리가 됐다 = **읽기 모델이 없다.**

- **본질적 복잡성** (도메인 자체) vs **우발적 복잡성** (구조 때문에 생긴 것) — 후자는 설계로 줄일 수 있다
- 응집성: 같은 이유·같은 주기로 변하는 것을 같이 둔다
- 관심사 분리: 핵심 로직이 DB/프레임워크를 직접 부르면 테스트도 변경도 어려워진다
- **테스트하기 어렵다 = 설계가 결합돼 있다는 신호.** 테스트 가능성은 품질 속성이 아니라 설계 품질의 계측기다
- 일반적 대응 방향(선택지로만 제시): 읽기/쓰기 분리, 집계값 비정규화, 목록과 상세의 분리, 페이징 경계

### 2-4. 멈추지 않고 기술 부채 줄이기 (13분) ★

*"지금 할 것 / 나중에 해도 될 것 / 미리 바꿔야 할 것"* 에 **정면으로 답하는 블록.** 세션 전체에서 가장 많은 질문이 나올 지점이다.

**Tidy First의 4분면**

| 선택 | 언제 | 예시 |
|---|---|---|
| **먼저** 정리 | 작은 정리가 지금 기능을 더 쉽고 안전하게 만든다 | 조건문을 가드 절로 바꾸고 분기 추가 |
| **나중에** 정리 | 구현해봐야 적절한 구조가 보인다 | 구현 후 드러난 중복 제거 |
| **훗날** 정리 | 가치는 있지만 지금 기능엔 도움 안 된다 | 여러 모듈에 걸친 공통 구조 |
| **안 함** | 다시 안 바뀌거나 비용 대비 이득 없다 | 곧 폐기할 코드 |

판단 기준은 미관이 아니라 경제성:
```text
정리 비용 + 정리 후 개발 비용  <  지금 구조에서 바로 개발하는 비용
```

**"미리 바꿔야 할 것"의 유일한 기준: 되돌리기 비용**

이게 회사 1 질문에 대한 가장 명확한 답이다.

| 되돌리기 쉬움 → 그냥 하라 | 되돌리기 어려움 → 미리, 신중히 |
|---|---|
| 이름 변경, 함수 추출/인라인 | **DB 스키마 변경** |
| 코드 이동, 순서 변경 | **외부 공개 API 계약** |
| 명시적 파라미터 도입 | **대규모 데이터 이전** |
| 죽은 코드 삭제 | **운영 데이터의 의미 변경** |

> 전자는 논의 대상이 아니라 그냥 하는 것. 후자만 설계 회의를 연다. **팀의 논의 시간이 전자에 쓰이고 있다면 그게 낭비다.**

**전담 인력 없이 하는 법**

- 시간 비율("스프린트의 20%")보다 **범위 제한**이 낫다: 이번 기능이 반드시 지나가는 코드만
- 몇 분 단위. **한 시간을 넘으면 범위가 커진 것**
- 구조 변경과 동작 변경을 **커밋/PR로 분리**한다
  ```text
  refactor: 결제 조건을 guard clause로 정리
  refactor: 금액 계산을 helper로 추출
  feat: 부분 환불 조건 추가
  ```
  리뷰어의 질문이 달라진다 — 구조 변경은 "동작이 그대로인가", 기능 변경은 "요구사항에 맞는가"
- **연쇄 작용 경계**: 정리하다 보면 계속 보인다. 다음 기능을 안전하게 만들 수 있으면 멈춘다

**부채를 기록하는 언어** (경영진 설득용)

"코드가 더럽다"는 예산을 못 받는다. 이렇게 쓴다:

```text
문제: 주문 상태 변경 시 5개 모듈을 함께 수정해야 한다
영향: 최근 3개 기능에서 각각 1~2일 추가 발생
다음 발생: 환불 정책 기능에서 재발 예상
개선 비용: 2일 / 회수: 향후 변경 2회 이내
```

> Kent Beck: **기능 변경 = 매출, 구조 변경 = 옵션.** 리팩터링은 "예정된 3개 기능을 각각 한 곳만 고쳐서 만들 수 있게 하는 투자"라고 설명한다.

- [경험 슬롯 ⑤] 신규 개발과 병행해서 부채를 줄인 실제 사례 1건

### 2-5. 조직 운영 — 대기업 방식 중 무엇을 가져올까 (6분)

회사 1의 4번 질문. **"규모별로 필요한 것이 다르다"**를 표로 정리한다.

| 대기업 방식 | 해결하려는 문제 | 10~30명 조직의 대안 |
|---|---|---|
| 모노레포 + 코드 검색 | 사용처 파악, 일관된 변경 | 저장소 통합 검색 + 명확한 오너 |
| 정교한 리뷰 도구 | 빠른 피드백, 지식 공유 | **작은 PR** + 리뷰 기준 + CI 통합 |
| 설계 문서 프로세스 | 결정의 맥락 보존 | **ADR 한 장** (배경/선택지/결정/결과) |
| 전사 테스트 인프라 | 변경 위험 조기 발견 | **핵심 경로부터** 자동 테스트 |
| 정식 포스트모템 | 재발 방지 | **5줄 템플릿** |
| 전담 QA 조직 | 다른 관점의 검증 | 인수 조건을 **개발 전에** 합의 |

**지금은 하지 않아도 되는 것:** 아키텍처 리뷰 위원회, 전사 표준 문서, 정교한 공수 산정 프로세스, 릴리스 관리 조직

**문서화 수준의 기준 하나:**
> 문서가 없는 것도 문제지만, **낡은 문서가 공식 정보처럼 남아 있는 게 더 위험하다.** 유지할 자신이 없는 문서는 만들지 않는다.

PM/디자인이 어디까지 정리해야 하는가 → **"인수 조건(어떤 입력에 어떤 결과)을 개발 전에 합의했는가"** 하나로 답한다. 화면 설계의 상세도가 아니라 완료 조건의 명확도가 기준이다.

### 2-6. 확장의 일반 원칙 (2분, 짧게)

깊이 들어가지 않고 체크리스트로만. 질문이 나오면 Q&A에서 확장.

- **외부 API 연동**(AI 모델 포함): 타임아웃 필수, 재시도는 멱등할 때만, 서킷 브레이커, 느린 작업은 큐로 비동기화, 장애 격리
- **글로벌**: 정적 자산은 CDN, 상태는 리전, DB 다중 리전은 마지막 수단. 대부분의 체감 속도 문제는 리전이 아니라 요청 수와 페이로드 크기

## 세션 3. AI 시대의 기술 지형 변화와 대응 (45분)

> **한 문장:** 질문을 바꾼다. *"AI가 코드를 얼마나 잘 쓰는가"* 가 아니라 *"우리 조직이 AI에게 맥락·실행환경·검증·피드백을 얼마나 잘 주는가"*.

**프레임:** `Context → Execution → Verification → Feedback` (회사 2 요구사항 전체를 이 4단계에 매핑)

### 3-1. 무엇이 실제로 바뀌었나 (6분)

**병목의 이동**

```text
[전]  요구사항 → 설계 → [코드 작성 ★병목] → 리뷰 → 배포
[후]  요구사항 → [맥락 정리 ★] → 코드 생성 → [검증/리뷰 ★★병목] → 배포
```

- 생성량은 늘었는데 **검토량은 사람 수만큼만 늘어난다.** 이게 AI 시대 개발 조직의 핵심 제약
- 그래서 승부처는 "얼마나 잘 만드는가"가 아니라 **"얼마나 빨리 확신할 수 있는가"**

**공수 산정은 어떻게 바뀌나** (회사 2 질문)
- 초안 작성 시간은 크게 줄고, **명세·검증 시간은 거의 안 준다**. 오히려 늘 수도 있다
- 그래서 산정 단위를 "구현 시간"에서 **"검증 가능한 변경 단위 수"**로 바꾸는 게 현실적
- 클린 코더의 추정/약속 구분은 여전히 유효 — AI가 초안을 5분에 만들어도 **약속의 단위는 인수 가능한 상태**다
- 주의: 낙관 편향이 심해진다. "AI가 하면 금방이죠"가 새로운 압박이 된다

### 3-2. Context — AI가 먹기 좋은 코드베이스 (9분) ★ 세션 2와 이어지는 지점

**결론을 먼저 말한다.**
> 세션 2에서 말한 좋은 설계가 **그대로** AI에게 좋은 조건이다. AI를 위해 따로 할 일은 생각보다 적다.

| 사람에게 좋은 것 | AI에게 왜 좋은가 |
|---|---|
| 명확한 모듈 경계 | 읽어야 할 범위가 좁아진다 |
| 높은 응집성 | 한 곳만 고치면 된다 |
| 테스트 | **AI가 스스로 채점할 수 있다** (가장 중요) |
| 재현 가능한 환경 | 실행해보고 고칠 수 있다 |
| 일관된 컨벤션 | 예시로부터 규칙을 추론한다 |

**추가로 필요한 것 (AI 전용)**

- 저장소 루트의 규칙 파일 (`CLAUDE.md` / `AGENTS.md`): 빌드·테스트 명령, 컨벤션, 하지 말 것
- **한 줄로 실행되는 테스트/린트 명령** — 없으면 에이전트는 검증 못 한다
- 디렉터리별 README, 타입/스키마, 시드 데이터, 로컬 도커 환경
- 문서를 코드 옆에 두고 코드처럼 버전 관리 (구글 3.3)

**반대로 AI를 가장 방해하는 것:** 거대한 함수, 암묵적 전역 상태, 실행할 수 없는 로컬 환경, 실패하는 기존 테스트, "이건 원래 이래" 지식이 사람 머리에만 있는 코드.

> **레거시일수록 AI 효과가 낮다는 사실을 솔직히 말한다.** 회사 1처럼 CI3 + 거대 쿼리가 있는 환경에서 "AI 넣으면 해결된다"는 기대는 조정이 필요하다. 오히려 세션 2를 먼저 하는 게 AI 도입의 준비다.

### 3-3. Execution — Harness · Tool · MCP를 누가 소유하나 (10분) ★

**구성요소 정리** (용어부터 맞춘다)

| 요소 | 역할 | 스타트업에서의 현실 |
|---|---|---|
| 프롬프트/규칙 파일 | 조직의 맥락과 금지사항 | 가장 먼저, 가장 싸게 효과 |
| 툴 / 스킬 | 반복 작업의 절차화 | 두 번 이상 반복되면 만든다 |
| MCP 서버 | 사내 시스템 연결(이슈, 문서, DB, 모니터링) | **읽기 전용부터** |
| 서브에이전트 | 역할 분리(리뷰, 조사) | 컨텍스트 분리 목적일 때만 |
| 훅 / CI 통합 | 사람이 안 잊게 강제 | 정착의 핵심 |

**소유 모델 3가지 비교**

| 모델 | 장점 | 단점 | 적합 규모 |
|---|---|---|---|
| 전담 조직 | 일관성, 보안 통제 | 현장과 괴리, 병목 | 수백 명+ |
| 팀별 자율 | 실제 필요에 맞음, 빠름 | 중복, 품질 편차, 전파 안 됨 | 소규모 |
| **하이브리드** | 중앙은 가드레일·플랫폼, 팀은 워크플로 | 경계 합의 필요 | 대부분 |

> 10~30명 조직에 **전담 조직은 과하다.** 대신 필요한 건 딱 두 개 — **명시적 오너 1명**과 **공용 저장소**. 오너가 없으면 아무도 관리 안 하고, 저장소가 없으면 전파가 안 된다.

**제작·개선 절차 (경량 버전)**
```text
개인이 만든다 → 본인 반복 업무에서 2주 써본다 → 쓸만하면 공용 레포에 PR
→ 리뷰(보안 권한 범위 위주) → 공용 배포 → 사용 안 되면 폐기
```
무거운 승인 절차를 앞에 두면 아무도 안 만든다. **관문은 앞이 아니라 "공용화 시점"에 둔다.**

**전파 방법**
- 공용 레포에 커밋해서 배포 (설치가 아니라 동기화가 되게)
- 문서보다 **실제 작업 시연 15분**이 훨씬 잘 퍼진다
- 사용 여부를 실제로 관측한다 (안 쓰이면 문서가 문제가 아니라 도구가 문제)

**위험도별 권한 등급** (보안 질문의 답)

| 등급 | 권한 | 검증 |
|---|---|---|
| 1 | 읽기 전용 (코드 검색, 문서) | 불필요 |
| 2 | 격리된 작업공간에서 파일 수정 | 사람 리뷰 |
| 3 | 브랜치 푸시, PR 생성 | 리뷰 + CI 필수 |
| 4 | 스테이징 배포 | 사람 승인 |
| — | **운영 DB 쓰기 / 운영 자격증명** | 에이전트에게 주지 않는다 |

> "격리 컨테이너냐 사람 눈이냐"는 양자택일이 아니다. **위험도에 따라 다르게** 하는 것이 답이다. 대부분의 작업은 등급 2~3이고, 여기선 격리와 사람 리뷰를 **둘 다** 한다.

### 3-4. Verification — 품질과 책임 (10분) ★

**대원칙부터 못 박는다**

> **AI는 저자가 아니라 도구다. 머지 버튼을 누른 사람이 저자이고 책임자다.**

회사 2의 "AI 코드가 사고를 냈을 때 책임 소재" 질문에 대한 답이 이것이다. 새로운 책임 체계가 필요한 게 아니라 **기존 체계가 그대로 적용된다.** 사후 프로세스도 세션 1의 비난 없는 포스트모템과 동일하되, 질문 하나가 추가된다:

> "왜 이 코드가 우리 리뷰와 테스트를 통과했는가?"

이건 AI 문제가 아니라 **검증 체계의 문제**로 다뤄야 한다.

**리뷰와 QA의 무게 이동** (회사 2 질문)

```text
[전]  사람 리뷰가 1차 방어선
[후]  자동 검증이 1차,  사람은 자동화가 못 잡는 것에 집중
```

| 자동에 맡길 것 | 사람이 봐야 할 것 |
|---|---|
| 포맷, 린트, 타입 | **설계 의도와 경계** |
| 테스트 통과 | **도메인 규칙의 정확성** |
| 커버리지, 중복 | **보안·권한·개인정보** |
| 관습적 코드 스멜 | **운영 데이터에 미치는 영향** |
| 1차 AI 리뷰 | **되돌리기 어려운 변경** (세션 2-4와 동일한 기준) |

- 결론: 리뷰 **횟수**는 늘고 리뷰 **깊이**는 좁아진다. QA는 줄지 않고 **탐색적 테스트 쪽으로 이동**한다
- AI 리뷰 에이전트의 현실적 강약점: 누락 케이스·테스트 보완·일관성 위반에 강하고, **"이 도메인에서 이게 맞는가"에는 약하다**
- [경험 슬롯 ⑥] AI 검수 에이전트를 실제로 쓴 사례 — 잘된 것과 안 된 것 **둘 다**

**무엇을 측정할 것인가** (Eval / 효과 측정 질문)

모델 벤치마크 점수는 조직에 의미가 없다. **워크플로 결과 지표**를 본다.

| 관점 | 지표 |
|---|---|
| 품질 | 재작업률, 롤백률, 리뷰 지적 수 |
| 속도 | PR 리드타임(생성→머지), 첫 리뷰까지 시간 |
| 채택 | **주간 실제 사용률** (가장 정직한 지표) |
| 만족 | 정기 설문 (정량만으로는 왜곡된다) |
| 비용 | 토큰 비용 / 절약된 시간 |

> 구글의 경고 그대로: **단일 지표로 생산성을 재면 행동이 왜곡된다.** "AI 사용률"을 KPI로 걸면 사용률만 오른다.

**폐기도 엔지니어링이다** (회사 2 질문)

계속 쓰이는 것과 버려진 것의 차이는 대체로 하나다:
> **기존 업무 흐름 안에 있느냐, 별도로 열어야 하느냐.**

- 살아남는 것: PR에 자동으로 붙는 것, CI에 들어간 것, 이미 쓰는 도구 안에 있는 것
- 죽는 것: 별도 사이트, 별도 명령어, "쓰라고 공지한 것"
- 폐기 절차: 대체 수단 제공 → 사용처 파악 → 공지 → 제거. 오래된 것을 안 지우면 신뢰가 떨어진다

### 3-5. Feedback — 직군 경계와 협업 (7분)

**비개발 직군의 생산성을 위해 개발자가 할 수 있는 일**

도구를 사주는 게 아니라 **안전한 접근 경로를 만들어주는 것**이다.

| 개발자가 제공 | 효과 |
|---|---|
| 읽기 전용 데이터 뷰 / 사내 MCP | 마케팅·CS가 직접 질문 → 개발 요청 감소 |
| 반복 요청의 셀프서비스화 | 데이터 추출 요청이 사라진다 |
| 안전한 샌드박스 | 사고 없이 실험 가능 |
| 잘 쓰는 사람의 프롬프트 공유 | 직군 무관하게 가장 효과 큼 |

**Figma ↔ 구현 정확도** (회사 2 질문)

솔직한 답: **도구 연동이 정확도를 만들지 않는다.**

```text
디자인 시스템이 없다  →  AI가 픽셀을 추측한다  →  매번 다른 결과
디자인 토큰 + 명명된 컴포넌트가 있다  →  AI가 "매핑"만 하면 된다  →  정확도 급상승
```

- 선행 조건: 디자인 토큰(색·간격·타이포), 컴포넌트 이름이 코드와 일치, 상태(hover/disabled/error) 정의
- 이게 없으면 Figma MCP를 붙여도 결과가 안 정착한다. **투자 순서는 연동이 아니라 디자인 시스템이 먼저**
- 웹/Flutter/네이티브를 한 번에 노리기보다 **한 플랫폼에서 컴포넌트 10개 정도로 검증**하고 넓히는 게 현실적

**경계는 흐려지는가**
- 흐려진다. 다만 **"할 수 있는 것"의 경계**가 흐려지는 것이고, **"책임지는 것"의 경계는 그대로**다
- PM이 프로토타입을 만들 수 있게 되는 것과, 그게 운영에 나가는 것은 다른 문제
- 개발자의 역할은 축소가 아니라 **판단과 검증 쪽으로 이동**한다

### 3-6. 마무리 — 3개 세션을 한 장으로 (3분)

```text
세션 1.  결과가 아니라 판단의 과정을 관리한다.        (도구가 바뀌어도 안 변함)
세션 2.  좋은 소프트웨어 = 변경 비용이 낮은 소프트웨어.  (AI 시대에 더 중요해짐)
세션 3.  AI가 먹기 좋은 코드베이스 = 사람이 일하기 좋은 코드베이스.
```

> 오늘 들은 것 중 **하나만** 내일 해보신다면 무엇을 고르시겠습니까? — 이 질문으로 Q&A를 연다.

## Q&A 설계 (60분) ★ 회사별 차별화가 일어나는 유일한 구간

슬라이드가 한 벌이므로, **이 60분이 두 강연을 다르게 만드는 전부다.** 빈 시간으로 두면 침묵하거나 한 사람이 독점한다. 구조를 만든다.

### 사전 질문 3개 — 가장 중요한 준비물

강연 전에 회사별로 **"가장 깊게 듣고 싶은 질문 3개"**를 받는다. 요구사항 문서의 사전 확인 항목이기도 하다. 이걸 받으면:

- 같은 자료로 발표하고도 뒷부분 60분이 완전히 달라진다
- 답변을 미리 준비할 수 있어 밀도가 올라간다
- 세션 중에 "이건 이따 Q&A에서 자세히"라고 연결할 수 있다 → 청중의 집중이 유지된다

### 진행 구조

| 시간 | 방식 | 비고 |
|---|---|---|
| 0~5분 | 사전 질문 3개를 화면에 띄우고 시작 | "오늘 이 세 개는 반드시 답하고 갑니다" |
| 5~35분 | 사전 질문 답변 | 미리 준비한 답변 + 관련 슬라이드 재활용 |
| 35~55분 | 현장 질문 | 세션 중 나온 질문 메모를 먼저 소진 |
| 55~60분 | 마무리 — "내일 할 수 있는 것 3가지" | 회사별로 다르게 제시 |

> 각 45분 세션의 **끝 10분 즉석 질문**에서 나온 것 중 답을 못 한 것을 적어두고, 35분 지점에서 먼저 꺼낸다. 이게 현장 질문이 안 나올 때의 보험이다.

### 회사 1 트랙 — 예상 질문과 답변 경로

| 질문 | 되돌아갈 슬라이드 | 답변의 뼈대 |
|---|---|---|
| "저희는 뭐부터 해야 하나요?" | 2-4 되돌리기 비용 표 | 정답 대신 **분류 기준**을 준다. 되돌리기 쉬운 건 그냥, 어려운 것만 회의 |
| "인력을 뺄 수가 없는데요" | 2-4 범위 제한 | 비율(20%)이 아니라 **범위**로 제한. 이번 기능이 지나가는 코드만 |
| "RDS 알람이 계속 울립니다" | 2-2 알람 3조건 | 임계치 상향은 틀린 판단이 아니다. **그 다음에 뭘 했는지**가 문제 |
| "문서를 어디까지 써야 하나요?" | 2-5 문서화 기준 | 낡은 문서가 없는 문서보다 위험. **유지할 자신이 있는 것만** |
| "PM이 어디까지 정리해줘야 하나요?" | 2-5 인수 조건 | 화면 상세도가 아니라 **완료 조건의 명확도** |
| "대기업 방식 중 뭘 가져올까요?" | 2-5 규모별 대안 표 | 방식이 아니라 **그 방식이 푸는 문제**를 먼저 본다 |
| "해외 사용자가 느리다는데요" | 2-6 | 대부분 리전이 아니라 **요청 수와 페이로드 크기** |

**회사 1의 마무리 3가지 (예시안)**
1. 이번 주 PR 하나에서 구조 변경과 동작 변경을 커밋으로 분리해본다
2. 실행 쿼리에 호출자 주석을 심는다 (`/* app= svc= ep= */`)
3. 부채 하나를 "문제/영향/다음 발생/비용/회수" 형식으로 적어본다

### 회사 2 트랙 — 예상 질문과 답변 경로

| 질문 | 되돌아갈 슬라이드 | 답변의 뼈대 |
|---|---|---|
| "전담 조직이 필요한가요?" | 3-3 소유 모델 표 | 규모에 따라. 소규모엔 **오너 1명 + 공용 레포**면 충분 |
| "잘 동작하는지 어떻게 판단하나요?" | 3-4 지표 표 | 모델 점수 말고 **워크플로 결과 지표**. 단일 지표 KPI는 왜곡을 만든다 |
| "폐기한 시스템과 살아남은 시스템의 차이는?" | 3-4 폐기 | **기존 흐름 안에 있느냐** 별도로 열어야 하느냐 |
| "AI 코드가 사고를 내면 책임은?" | 3-4 대원칙 | 새 체계가 아니라 **기존 체계 그대로**. 머지한 사람이 책임 |
| "격리 컨테이너 vs 사람 검수?" | 3-3 권한 등급표 | 양자택일이 아니라 **위험도별로 다르게** |
| "리뷰와 QA 중 어디에 무게가?" | 3-4 이동 표 | 리뷰 횟수는 늘고 깊이는 좁아진다. QA는 **탐색적 테스트로 이동** |
| "공수 산정을 어떻게 다시 잡나요?" | 3-1 | 구현 시간이 아니라 **검증 가능한 변경 단위** |
| "Figma에서 정확하게 뽑는 방법?" | 3-5 | 도구가 아니라 **디자인 시스템**이 정확도를 만든다 |
| "비개발자 생산성은 어떻게 올리나요?" | 3-5 표 | 도구를 사주는 게 아니라 **안전한 접근 경로**를 만들어주는 것 |
| "직군 경계가 흐려지나요?" | 3-5 | 할 수 있는 것의 경계는 흐려지고 **책임의 경계는 그대로** |

**회사 2의 마무리 3가지 (예시안)**
1. 저장소 루트에 규칙 파일 한 장을 만든다 (빌드·테스트 명령, 컨벤션, 금지사항)
2. 테스트·린트를 **한 줄 명령**으로 실행되게 만든다
3. 지금 쓰는 AI 도구의 **주간 실제 사용률**을 한 번 측정해본다

### 범위 밖 질문의 처리 문법

> "그건 제가 여러분 시스템을 봐야 답할 수 있는데, 제가 아는 **일반적인 판단 기준**은 이렇습니다. 이 기준으로 보시면 어떨까요."

정답 대신 **판단 기준**을 주는 것으로 일관되게 처리한다. 오프닝의 범위 선언(0.4)과 맞물려야 자연스럽다.

특히 조심할 유형:
- 특정 기업의 비공개 정책을 묻는 질문 → 공개된 범위만, 개인 경험은 소속 회사 공식 입장과 명확히 구분
- "이 코드/구조가 맞나요" 식의 즉석 진단 요청 → 기준으로 되돌린다
- "판교에서는 어떻게 하나요?" → 방식이 아니라 **그 방식이 푸는 문제**로 답한다

## 남은 결정 사항

1. **경험 슬롯 6개** — 발표의 실질적 가치는 여기서 나온다. 청중이 "완성된 정답보다 실패와 개선 과정"을 원한다고 명시했으므로, 실패담 위주로 채운다. 사례가 정해지면 세션별 시간 배분을 다시 조정.
2. **사전 질문 3개 수집** — 단일 자료로 가기로 한 이상 **가장 중요한 준비물.** 두 회사 각각에게 강연 전에 받아야 Q&A 60분이 차별화된다.
3. **시연 포함 여부** — 요구사항 문서의 사전 확인 항목. 넣으면 세션 3에서 10분 이상 필요하고 3-3/3-4를 줄여야 한다. 단일 자료이므로 회사 1에게도 같은 시연이 나간다는 점 고려.
4. **RDS 자료 노출 수위** — 현재는 그대로 사용하는 것으로 확정. 다만 회사 2 발표에도 동일하게 나가므로, 발표 직전에 회사명·테이블명 등 어디까지 남길지 최종 확인 필요.
5. **세션 내 즉석 질문 10분 운용** — 45분을 슬라이드 35 + 질문 10으로 쪼갤지, 45분 통으로 하고 Q&A에 몰지. 청중 규모가 정해지면 결정.
