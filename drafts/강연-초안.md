# 부산 스타트업 강연 구성안 v1.1 (실행본)

> 오프닝 15분 + (발표 40분 + 즉석 Q&A 5분 + 휴식 10분) × 3 + 커피챗 45분.
> 두 회사를 **자료와 진행 방식 모두 동일하게** 진행하고, 차별화는 **커피챗의 현장 대응**으로만 한다.

**v1.1 — 토스 공개 사례 · 사내 선행 발표 연결**

- **`[토스]` 마커 신설.** 토스 기술블로그 공개 사례를 각 블록의 근거로 연결. **`[KB]` 슬롯에서 말 못 하는 지점을 공개 사례가 대신 답한다.**
- 세션 3 도입에 **김현규 님 발표 프레임 연결.** 회사 2가 이미 들은 내용이라 이어받는 구조로.
- **부록 D: 토스 공개 사례 인덱스** 추가. 커피챗 현장 대응용.

**v1.0 — 내일 발표용 실행본**

- **두 회사 완전 동일 진행.** 준비 시간이 없으므로 회사별 자료·흐름을 따로 만들지 않는다.
- **소속사 사례 슬롯 14곳** 확보 (`[KB]` 마커). 회사 2가 특히 궁금해하는 영역에 집중 배치.
- **소속사 사례 공유 범위 가이드**(0.5) 신설. 금융권·상장사이므로 면책과 경계선을 명확히 한다.
- 청중 정정: 회사 1 = 5명 (개발 3 + 대표 + 사업부장), 회사 2 = 10명 (개발 8 + 대표 + 사업부장).

## 0. 전체 설계

### 0.1 전체를 관통하는 축

```text
                    확률적 우위 · 절제의 우위 · 자금의 우위
                                    │
   세션 1  ─────────────────────────┼───────────────────  판단의 기준
           카지노는 어떻게 돈을 버는가              (마음가짐)
                                    │
   세션 2  ─────────────────────────┼───────────────────  기준의 적용
           내 시간을 어디에 배분할 것인가           (자본 배분)
                                    │
   세션 3  ─────────────────────────┼───────────────────  기준의 재검증
           AI는 이 세 우위를 어떻게 바꾸는가        (지형 변화)
```

**전체에서 반복되는 두 개의 판단 기준**

```text
① 가역적인가, 비가역적인가        → 얼마나 신중할 것인가를 정한다
② 이 부채의 금리는 높은가, 낮은가  → 지금 갚을 것인가를 정한다
```

**보조 축 하나가 세션 2와 3을 잇는다.**
> "AI가 먹기 좋은 코드베이스는 사람이 일하기 좋은 코드베이스와 같다."

### 0.2 시간표 (09:00 시작 기준)

| 시각        | 구성                                                      | 길이 |
|-------------|-----------------------------------------------------------|------|
| 09:00~09:15 | **오프닝** — 소개 · 범위 선언 · 관심사 확인 · 오늘의 지도 | 15분 |
| 09:15~09:55 | **세션 1. 엔지니어로서의 마음가짐**                       | 40분 |
| 09:55~10:00 | 즉석 질의응답 ①                                           | 5분  |
| 10:00~10:10 | 휴식                                                      | 10분 |
| 10:10~10:50 | **세션 2. 좋은 소프트웨어를 만들어 나가는 방법**          | 40분 |
| 10:50~10:55 | 즉석 질의응답 ②                                           | 5분  |
| 10:55~11:05 | 휴식                                                      | 10분 |
| 11:05~11:45 | **세션 3. AI 시대의 기술 지형 변화와 대응**               | 40분 |
| 11:45~11:50 | 즉석 질의응답 ③                                           | 5분  |
| 11:50~12:00 | 휴식                                                      | 10분 |
| 12:00~12:45 | **커피챗 · 질의응답**                                     | 45분 |

**총 3시간 45분.** 4시간 일정이라면 **15분이 버퍼로 남는다** — 이건 낭비가 아니라 보험이다. 강연은 거의 항상 밀리고, 특히 소규모에서는 세션 중 질문이 붙어 밀린다. 버퍼가 없으면 커피챗이
잘려나간다.

**이 구조가 자료 설계에 주는 영향**

1. **즉석 질의응답 5분은 2~3개가 한계다.** 답을 못 한 질문은 반드시 적어두고 **커피챗에서 소진**한다. 5분의 목적은 "다 답하기"가 아니라 **"질문을 수집하기"**다.
2. **세션 3의 마무리가 강연의 마지막이 아니다.** 최종 정리는 커피챗 안에서 한 번 더 한다.
3. **오프닝 15분 중 5분을 청중에게 직접 묻는 데 쓴다.** 소규모라서 가능하고, 사전 질문을 못 받았더라도 여기서 회수할 수 있다.

### 0.3 청중 — 이 규모가 형식을 바꾼다

|                 | 회사 1     | 회사 2      |
|-----------------|------------|-------------|
| 개발자          | 3명        | 8명         |
| 대표 · 사업부장 | 2명        | 2명         |
| **합계**        | **약 5명** | **약 10명** |

> **둘 다 10명 이하다.** 그래서 진행 방식을 회사별로 다르게 준비할 필요가 없다. 양쪽 모두 **대화에 슬라이드가 붙은 형태**로 간다. 준비 시간이 없는 지금 이건 좋은 소식이다.

**이 규모에서 반드시 지킬 것 4가지**

**① 40분 독백을 하지 않는다.** 5명·10명 앞에서 일방적으로 40분을 넘기는 건 부자연스럽다.

- 세션 중 질문이 들어오면 **그 자리에서 받는다.** 뒤로 미루지 않는다
- 블록마다 한 번씩 "여기까지 어떠세요?" 를 던진다
- **40분을 다 못 채워도 괜찮다.** 오히려 그게 정상이다

**② 손들기 조사를 하지 않는다.** 5명에게 손 들라고 하면 우스꽝스럽다. **그냥 물어본다.** 오프닝 O-3이 그 역할을 한다.

**③ 비개발 직군이 회사 1에서는 40%다** (5명 중 2명).

- **`f = g + h` 수식은 노출하지 않는다.** "여기까지 쓴 비용 + 남은 예상 비용"으로 말로만 푼다
- SQL·git 명령 슬라이드는 띄우되 **"이건 개발자분들 참고용"**이라고 명시하고 빠르게 넘긴다
- 반대로 **조직·의사결정·투자 판단 파트의 가치가 커진다.** 의사결정권자에게 직접 닿는 흔치 않은 기회다

**④ 대표·사업부장 참석이 확정이므로 강조점을 옮긴다.**

| 블록                | 왜 이 자리에서 특히 중요한가                                                            |
|---------------------|-----------------------------------------------------------------------------------------|
| **1-5 추정과 약속** | 개발자에겐 "말하는 법", 대표·사업부장에겐 "듣는 법". 3분 → **5분으로 증량**             |
| **2-2 투자 논지**   | 기술 부채를 경영 언어로 번역하는 법. 양쪽이 같은 슬라이드를 보는 게 핵심                |
| **2-3 부채의 금리** | "왜 어떤 부채는 안 갚아도 되는가"는 대표가 가장 듣고 싶어 하는 답이다                   |
| **2-4 가역/비가역** | 의사결정 속도 규범. 조직 차원의 합의가 필요한 개념                                      |
| **1-4 조직의 장치** | 회사 1은 개발자가 3명이다. 이 규모의 진짜 위험은 프로세스 부재가 아니라 **버스 팩터**다 |

**규모가 답을 바꾸는 지점 (같은 슬라이드, 다른 강조)**

같은 자료를 쓰되 **말할 때 한 문장만 다르게** 붙이면 된다. 이건 준비물이 아니라 현장 감각이다.

|                       | 회사 1 (개발 3명)                                                                                 | 회사 2 (개발 8명)                                       |
|-----------------------|---------------------------------------------------------------------------------------------------|---------------------------------------------------------|
| 전담 리팩터링 인력    | **불가능이 당연한 전제.** Tidy First가 유일한 답                                                  | 가능하지만 여전히 비추천                                |
| 1-4 대기업 방식 표    | 해당하는 건 ADR 한 장 · 5줄 포스트모템 · 작은 PR **정도.** 나머지는 솔직히 "지금은 필요 없습니다" | 리뷰 프로세스·문서 소유자까지 의미가 있다               |
| 코드 리뷰의 목적      | 결함 검출보다 **지식 공유**로 크게 기운다 (버스 팩터)                                             | 결함 검출과 일관성이 함께 온다                          |
| 3-3 harness 소유 모델 | 오너를 따로 둘 사람도 없다. **규칙 파일 한 장부터**                                               | **"오너 1명 + 공용 레포"가 정확히 이 규모를 겨냥한 답** |

### 0.4 두 회사를 완전히 동일하게 진행한다

**확정:** 슬라이드 한 벌, 진행 방식 한 가지. **회사별로 준비하는 것은 없다.**

준비 시간이 없다는 제약에서 나온 결정이지만, 결과적으로 무리가 없다. 두 회사 모두 10명 이하이고 대표·사업부장이 참석하며, 관심사도 세션 2와 세션 3으로 갈릴 뿐 서로 배타적이지 않다.

1. **어느 세션도 줄이지 않는다.** 각 세션이 단독으로 성립한다.
2. **한쪽에만 유효한 결론을 넣지 않는다.** "여러분 규모에서는 X를 하세요" 대신 **판단 기준**만 준다. 이건 범위 선언과도 일치한다.
3. **각 세션에 다른 쪽 청중을 위한 연결 고리를 심는다.**

| 세션               | 회사 1 청중에게                            | 회사 2 청중에게             |
|--------------------|--------------------------------------------|-----------------------------|
| 1. 마음가짐        | 공통                                       | 공통                        |
| 2. 좋은 소프트웨어 | 부채·관측의 직접 답                        | **AI 도입의 전제 조건**     |
| 3. AI 시대         | **부채 정리가 왜 AI 도입의 선행 조건인지** | Harness·Eval·책임의 직접 답 |

**차별화는 딱 두 곳에서만 일어난다 — 둘 다 현장 대응이다.**

| 시점                 | 무엇을 하는가                                                                 |
|----------------------|-------------------------------------------------------------------------------|
| **오프닝 O-3 (5분)** | 관심사를 직접 듣고 화이트보드에 적는다. 이게 그 회사의 목차가 된다            |
| **커피챗 45분**      | 적어둔 것을 하나씩 지워나간다. 회사 2에서는 `[KB]` 사례로 답이 자주 흘러갈 것 |

> 세션 중에도 "아까 ○○님이 물어보신 게 이 부분입니다"로 연결하면, 같은 슬라이드가 그 회사만을 위한 자료처럼 들린다. **준비 없이 차별화하는 유일한 방법이다.**

### 0.5 소속사 사례를 어떻게 말할 것인가 ★ 반드시 먼저 읽을 것

회사 2가 **발표자 소속사의 사례와 일하는 방식**을 특히 궁금해했다. 이 강연의 가장 큰 자산이자, 유일하게 위험한 부분이다.

> 요구사항 문서에 이미 원칙이 있다.
> - 발표자의 개인 경험과 견해는 **소속 회사의 공식 정책과 구분한다**
> - 다른 기업 사례는 **공개된 자료 또는 공유 가능한 범위**에서만 사용한다
> - 범위 밖: 특정 기업의 **법적 책임체계나 비공개 보안정책을 공식 답변하는 것**

**면책 문구 — 오프닝 (O-2)에서 한 번, 세션 3 시작에서 한 번**

> "제가 지금 회사에서 백엔드 개발을 하고 있는데요. 오늘 제 경험을 많이 말씀드릴 텐데, **전부 제 개인 경험이고 회사의 공식 입장이 아닙니다.** 공개된 범위 안에서만 말씀드릴 거고요. 답변이 갑자기
> 두루뭉술해지는 부분이 있으면 그건 제가 말씀드릴 수 없는 영역이라고 이해해주시면 감사하겠습니다."

미리 선언해두면 나중에 답을 피할 때 어색하지 않다. **이 문장 하나가 4시간 내내 방어막이 된다.**

**세 가지 서랍**

|                          | 내용                                                                                                                                                                         | 화법                                                                 |
|--------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------|
| ✅ **말해도 되는 것**    | 기술 블로그·컨퍼런스 발표·채용 공고에 이미 공개된 것 / 업계 일반 관행 수준(코드 리뷰를 한다, CI를 돌린다) / **프로세스의 형태**(수치·설정 제외) / 발표자 본인이 직접 겪은 일 | "제가 있는 팀에서는~", "제 경험으로는~"                              |
| ⚠️ **조심할 것**         | 다른 팀 사정을 확정적으로 말하기 / 아직 출시 안 된 것 / 조직 개편·인사 / 특정 벤더·도구의 사내 평가                                                                          | "정확힌 모르지만 제가 듣기로는~" 또는 아예 안 한다                   |
| ⛔ **말하면 안 되는 것** | 보안 정책, 인증·인가 구현 세부 / **미공개 장애의 상세** / 내부 지표 수치, 인력 규모, 비용 / 벤더 계약 조건 / 금융 규제 대응 방식의 구체 / 고객 데이터 관련 일체              | "그건 제가 말씀드리기 어렵습니다" — **변명 없이 한 문장으로 끊는다** |

**가장 흔한 사고: 주어를 잘못 쓰는 것**

```text
❌ "저희 회사는 이렇게 합니다"      → 공식 입장으로 들린다
✅ "제가 있는 팀에서는 이렇게 했습니다"  → 개인 경험으로 들린다
```

**말 못 하는 질문이 왔을 때의 4단 대응**

1. **끊는다:** "그건 제가 말씀드리기 어렵습니다"
2. **공개 사례로 대체한다:** "대신 토스가 공개한 사례가 있는데요" → **부록 D**
3. **일반화한다:** "이 주제에 일반적으로 쓰이는 선택지는 이렇습니다"
4. **되돌린다:** "여러분 상황이라면 이 기준으로 판단해보시면 어떨까요"

변명하거나 얼버무리면 오히려 더 캐묻는다. **끊고 바로 대체안을 주는 게 가장 깔끔하다.**

> **2번이 이번 강연의 결정적 무기다.** 토스 기술블로그는 회사 2가 물은 것 대부분을 **공개적으로** 다뤘다. 소속사 얘기를 못 하는 자리에서 "그럼 이건 어떻게들 하나요"에 답할 수 있는 유일한 재료다.

**`[토스]` 마커 — `[KB]` 슬롯의 짝**

본문에 `[토스]` 마커로 공개 사례를 붙여뒀다. 사용 원칙:

- **출처를 밝히고 말한다.** "토스 기술블로그에 공개된 사례인데요" — 이러면 위험이 없다
- ⚠️ **전사 정책으로 일반화하지 않는다.** 토스 자료 자체가 "특정 팀 사례 / 작성자의 방향성 제안 / 전사 운영"을 구분하고 있다. **"토스는 ~합니다"가 아니라 "토스의 어느 팀이 이런 사례를 공개했습니다"**
- **`[KB]`와 짝을 지어 쓰면 가장 강하다:** 공개 사례로 형태를 보여주고 → 내 경험으로 온도를 더한다
- 회사 1에게도 유효하다. "판교는 어떻게 하나요"의 답이 된다
- ⏱ **`[토스]`도 추가 시간이 아니다.** 대부분 한두 문장이면 되고, 길게 풀 것은 커피챗으로 넘긴다

**`[KB]` 슬롯 운영 원칙**

- 본문 곳곳에 `[KB]` 마커로 자리를 표시해뒀다. **전체 14곳, 목록은 부록 C.**
- **14곳을 다 채울 필요는 없다.** 확실히 말할 수 있는 것만 고른다
- ⚠️ **슬롯 시간은 추가 시간이 아니다.** 해당 블록의 배정 시간 안에서 소화한다. 14곳 × 2분 = 28분인데 세션 총합은 120분이므로, 다 하면 슬라이드를 못 넘긴다. **★ 표시된 것 우선, 나머지는
  커피챗으로.**
- **실패 사례를 우선한다.** 청중이 요구한 게 "완성된 정답보다 실패와 개선 과정"이었고, 실패담은 대체로 공유 위험도 낮다
- 못 채운 슬롯은 그냥 넘어간다. 억지로 채우려다 선을 넘는 게 최악이다

# 세션 1. 엔지니어로서의 마음가짐 (40분)

> **한 문장:** 확률적 우위는 더 나은 판단, 절제의 우위는 그 판단을 흔들림 없이 반복하는 힘, 자금의 우위는 틀려도 다음 시도를 남기는 힘이다.

**주 레퍼런스:** 월가아재 3공리·13가지 인지 오류 + 클린 코더 + 구글 엔지니어 + 모던 SWE

### 1-1. 카지노는 어떻게 돈을 버는가 (7분) ★ 강연 전체의 훅

**룰렛 한 판을 본다.**

유럽식 룰렛에는 1~36과 0이 있다. 빨강에 걸면 37칸 중 18칸에서 이긴다.

```text
하우스 엣지 = 1 - (18/37 × 2) = 약 2.7%
```

> **카지노는 매 판 48.6%의 확률로 진다.** 절반 가까이 진다. 그런데 카지노는 망하지 않는다.

**왜 망하지 않는가 — 세 가지 우위**

| 우위            | 카지노가 하는 일                                                                 |
|-----------------|----------------------------------------------------------------------------------|
| **확률적 우위** | 2.7%. 작지만 **양수**이고, 모든 판에 동일하게 적용된다                           |
| **절제의 우위** | 손님이 연승해도 규칙을 바꾸지 않는다. 그리고 **베팅 한도**를 둔다                |
| **자금의 우위** | 손님보다 자금이 압도적으로 크다. **확률이 드러날 때까지 계속 앉아 있을 수 있다** |

**2.7%가 왜 그렇게 큰가 — 반복이 만드는 격차**

월 100만 원씩 40년:

| 연 수익률 |  40년 후 | 직전 대비 |
|----------:|---------:|----------:|
|        8% |  약 32억 |         – |
|       10% |  약 55억 |     +23억 |
|       12% |  약 97억 |     +42억 |
|       14% | 약 171억 |     +74억 |

8%와 14%의 차이는 약 139억. 매년 2%p가 네 번. **작은 우위 × 충분한 반복 = 큰 격차.**

하지만 반복의 효과를 얻으려면 그 전에 퇴장하지 않아야 한다. **겜블러의 파산 (Gambler's Ruin)** — 자금이 유한한 쪽과 사실상 무한한 쪽이 반복해서 붙으면, 게임이 완전히 공정해도 (50:50) 유한한 쪽이 결국 파산한다. 카지노는 여기에 확률 우위까지 얹고 있다.

> **카지노는 이기는 법을 아는 게 아니라, 지지 않고 계속 앉아 있는 법을 안다.**

**전환 — 우리 팀은 카지노인가 도박꾼인가**

|          | 카지노형 조직                         | 도박꾼형 조직                |
|----------|---------------------------------------|------------------------------|
| **확률** | 이 선택이 왜 더 나은지 설명할 수 있다 | "요즘 이게 대세라서"         |
| **절제** | 실패 조건과 롤백을 미리 정한다        | 안 되면 더 투입해서 만회한다 |
| **자금** | 작게 배포하고 여러 번 시도한다        | 6개월짜리 전면 재작성에 건다 |

> 오늘 세 세션은 이 세 우위를 각각 **판단 (1) → 시간 배분 (2) → AI 시대 (3)** 에 적용해보는 순서입니다.

- [경험 슬롯 ①] 도박꾼처럼 베팅했다가 잃은 경험 1건

### 1-2. 확률적 우위 — 결과가 아니라 기대값과 과정 (8분)

확률적 우위는 결과를 맞히는 능력이 아니라, 성공과 실패의 손익을 함께 보고 **더 나은 선택을 반복하는 것**이다.

**승률이 아니라 기대값이다**

```text
기대값 = Σ(결과 × 발생 확률)
```

이익이 2, 손실이 1이면 손익분기 승률은 약 33%다. **승률 40%여도 양의 기대값일 수 있고, 승률 60%여도 음의 기대값일 수 있다.**

개발에서 기대값을 계산하는 실질적인 방법은 **실패했을 때 되돌릴 수 있는가**를 보는 것이다.

| 선택                 | 성공 확률 | 실패 시 손실             | 판단             |
|----------------------|-----------|--------------------------|------------------|
| 이름 변경, 함수 추출 | 높음      | **거의 0 (가역적)**      | 그냥 한다        |
| 새 라이브러리 도입   | 중간      | 중간 (대체로 가역적)     | 작게 검증        |
| DB 스키마 변경       | 중간      | **큼 (비가역적)**        | 신중히           |
| 전면 재작성          | 낮음      | **파산 수준 (비가역적)** | 거의 하지 않는다 |

> 이 표의 마지막 칸이 오늘 계속 나올 기준이다. **가역적인가, 비가역적인가.**

**결과와 실력을 분리한다**

동전 앞면을 10번 연속 맞힐 확률은 약 0.098%다. 하지만 1,000명이 시도하면 한 명은 나온다. **연속 성공은 실력의 증거가 아니다.**

- 장애가 안 났다고 좋은 설계였던 것이 아니다 (운일 수 있다)
- 장애가 났다고 나쁜 판단이었던 것도 아니다 (당시 정보로는 최선이었을 수 있다)

> **좋은 판단 뒤의 손실은 부끄러워할 일이 아니고, 나쁜 판단 뒤의 행운은 자랑할 일이 아니다.**

**비난 없는 장애 분석** (구글) — 질문을 바꾼다.

| 나쁜 질문        | 좋은 질문                             |
|------------------|---------------------------------------|
| 누가 실수했는가? | 왜 이 실수가 장애까지 갈 수 있었는가? |
|                  | 시스템은 왜 이걸 미리 못 잡았는가?    |
|                  | 피해를 제한할 장치가 있었는가?        |

> **매매일지 = 포스트모템.** 결과가 아니라 **그때의 가정**을 적는다.
> 개인을 처벌하면 실수와 위험이 숨겨진다. 장애 보고서는 책임 추궁 문서가 아니라 학습 자료다.

> **[KB 2] 장애 회고를 실제로 어떻게 하는가 (2분)**
>
> ⚠️ **최종 공개 범위 검수:** 홈 TPS, Watchtower·Sentry 과부하, 당시 로직과 대응 내용을 발표 전에 다시 확인한다.
>
> "제가 지금 회사로 갓 이직했을 때 홈 화면의 색상 조회 코드에서 이런 부분을 발견했습니다.
>
> ```java
> try {
>     색상조회(색상키);
> } catch {
>     // log.error(...);
>     기본색상으로 fallback;
> }
> ```
>
> catch를 했는데 에러 로그가 주석 처리돼 있었습니다. 저는 당연히 로그를 남겨야 한다고 생각해서 별 의심 없이 주석을 풀었습니다. 그런데 이 코드에는 제가 모르는 운영의 역사가 있었습니다. 과거에 기본 색상의 색상키가 변경된 뒤 데이터가 정상적으로 이관되지 않아, 거의 모든 사용자의 요청이 색상 조회에 실패하고 catch에서 기본 색상으로 fallback 되고 있었습니다. 기능상으로는 정상처럼 보였지만, 예외가 사실상 정상 경로가 된 상태였습니다.
>
> 홈 화면은 TPS가 약 700에 이르는 영역이었습니다. 여기에 스택트레이스가 포함된 error 로그가 요청마다 쏟아지자 Watchtower 알림과 Sentry가 과부하되기 시작했고, 급증한 로그 파일은 애플리케이션 자원에도 부담을 줬습니다. 사용자 기능 자체에는 문제가 없어서 즉시 전체를 롤백하지는 않았고, 다음 날 error 로그의 주석을 다시 복원하는 배포로 우선 대응했습니다.
>
> 회고에서는 '로그를 푼 사람이 실수했다'로 끝내지 않고 다섯 가지를 정리했습니다. 첫째, 애초에 거의 모든 요청이 catch로 빠지는 구조가 문제였기 때문에 데이터를 이관해 정상적으로 색상을 조회하도록 했습니다. 둘째, 한 커밋에는 한 가지 변경만 담기로 했습니다. 셋째, 기능 변경과 리팩터링을 같은 커밋에 섞지 않기로 했습니다. 리뷰어가 의도를 구분하기 쉬워지고, 개발자 자신에게도 지금 무엇을 바꾸는지 다시 생각하게 하는 인지적 넛지가 되기 때문입니다. 넷째, 같은 프로젝트 구성원에게 반드시 리뷰받도록 했습니다. 다섯째, 이상해 보이는 코드가 있다면 먼저 '왜 이렇게 되어 있지?'라고 묻고 과거의 맥락을 확인하기로 했습니다.
>
> 제게 이 사건의 교훈은 단순합니다. **이상한 코드가 항상 틀린 코드는 아니고, 조용히 동작해 왔다는 사실도 안전하다는 증거는 아닙니다.** 그리고 주석 한 줄을 푸는 작은 변경도 트래픽과 관측 시스템을 만나면 결코 작은 운영 변경이 아닐 수 있습니다."


**경험주의 — 권위와 유행은 근거가 아니다** (모던 SWE)

```text
추측이나 권위  <  관찰 가능한 증거
```

- "마이크로서비스가 좋다", "이 프레임워크가 빠르다" → **우리 조직, 우리 트래픽에서 검증됐는가**
- 판교 대기업이 쓴다는 것은 근거가 아니다. 그건 **그들의 문제에 대한 답**이다
- 도구·방법론 평가의 두 질문: ① 더 빨리 **학습**하게 하는가 ② **복잡성**을 통제하게 하는가

**실험주의 — 그냥 해보는 것과 실험하는 것은 다르다** (모던 SWE)

유효한 실험의 5조건:

1. 검증할 **가설**을 세운다
2. 관찰하고 **측정할 결과**를 정한다
3. 가능한 범위에서 **변수를 통제**한다
4. **실패 비용이 작은 범위**에서 실행한다
5. 결과를 **다음 의사결정에 반영**한다

> "카프카 한번 도입해볼까요"는 실험이 아니다. "현재 배치 지연이 평균 40분인데, 이걸 5분 이내로 줄일 수 있는지 한 개 파이프라인에서 2주간 검증한다"가 실험이다.

### 1-3. 절제의 우위 — 개인의 규율 (8분)

건강을 위해 운동해야 한다는 걸 **몰라서** 안 하는 사람은 없다. 테스트를 써야 한다는 걸 몰라서 안 쓰는 것도 아니다.

> **투자 실력이 지식의 양이 아니듯, 개발 실력도 아는 것의 양이 아니다. 압박 속에서 그걸 행동으로 옮기는 능력까지 포함한다.**

**절제를 만드는 세 가지 — 개발자 버전**

| 월가아재     | 개발자 버전                                           |
|--------------|-------------------------------------------------------|
| 체력 관리    | **지속 가능한 상태에서 코딩한다**                     |
| 도파민 관리  | 새 기술 도입의 흥분, 리팩터링의 연쇄, **몰입의 과신** |
| 타자화(일기) | **코드 리뷰 · 페어링 · 포스트모템 · ADR**             |

**① 체력 — 판단할 수 없는 상태에서 코딩하지 않는다** (클린 코더 4장)

피곤·불안·분노 상태에서 짠 코드는 대개 내일 다시 짠다. 전문가는 자신의 상태를 인식하고 회복하거나 도움을 요청한다.

**막혔을 때의 대응** — 더 오래 혼자 버티는 것이 능사가 아니다.

- 페어 프로그래밍이나 리뷰를 요청한다
- 문제를 더 작게 나눈다
- 현재 가설을 **실패하는 테스트**로 명확히 한다
- 잠시 떨어진다

**② 도파민 — 몰입을 과신하지 않는다** (클린 코더 4장)

몰입은 즐겁지만 **시야가 좁아져** 큰 설계 문제와 대안을 놓친다. 대책은 몰입 자체를 목표로 삼지 않고 작은 피드백 루프를 유지하는 것이다 — 테스트 자주 실행, 작은 커밋, 중간 공유, 일정 간격의 휴식.

**정리의 연쇄**도 도파민이다. 코드 하나를 정리하면 다른 문제가 계속 보인다. 이게 리팩터링 범위가 끝없이 커지는 주된 원인이다. (→ 세션 2에서 멈추는 기준을 다룬다)

**③ 타자화 — 자기 판단을 남의 눈으로 보게 하는 장치**

투자에서 일기를 쓰는 이유와 개발에서 리뷰를 받는 이유가 같다. **자신을 한 걸음 떨어져서 관찰하기 위해서다.**

**연습은 업무 밖에서 한다** (클린 코더 6장)

업무는 성과를 만드는 시간이지 기초 기술을 처음 실험하는 연습장이 아니다.

| 방식          | 목적                                         |
|---------------|----------------------------------------------|
| 코딩 카타     | 작은 문제를 반복해 도구와 설계 루틴을 익힌다 |
| 개인 프로젝트 | 업무 스택 밖의 언어·패러다임을 경험한다      |

> 다만 이 원칙은 조심해서 전달한다. **학습 비용을 개인에게만 전가하면 불공정과 소진을 만든다.** 조직도 업무 시간·예산·멘토링을 제공해야 한다.

**엔지니어링이 도박이 되는 경계**

| 엔지니어링에 가까운             | 도박에 가까워지는                |
|---------------------------------|----------------------------------|
| 근거와 가정으로 기술을 선택한다 | 흥분과 소문으로 선택한다         |
| 실패 조건과 롤백을 미리 정한다  | 안 되면 더 투입해서 만회한다     |
| 작게 배포하고 결과를 합산한다   | 한 번의 대형 릴리스에 집착한다   |
| **안 하는 선택도 받아들인다**   | 뭐라도 계속 고쳐야 마음이 놓인다 |
| 판단을 기록하고 복기한다        | 결과만 보고 정당화한다           |

**개발자가 특히 잘 걸리는 인지 오류 6가지**

| 오류             | 개발 현장에서의 모습                                         |
|------------------|--------------------------------------------------------------|
| **안전 착각** ★ | 위험한 걸 몇 번 했는데 안 터졌다 → 안전하다고 믿는다         |
| 확신 편향        | 내가 고른 기술의 장점 자료만 찾아본다                        |
| 애착 편향        | 내가 짠 코드를 남의 코드보다 높게 평가한다. 그래서 못 지운다 |
| 현상유지 편향    | 이미 쓰고 있다는 이유로 계속 쓴다                            |
| 손실회피         | 3개월 쓴 프로젝트를 접지 못한다                              |
| 권위의존         | "구글도 이렇게 합니다" 로 논의를 끝낸다                      |

**안전 착각을 특히 강조한다.** 세션 2로 이어지는 다리다.

```text
알람이 울렸다 → 서비스에는 영향이 없었다 → 임계치를 올린다
→ 또 울렸다 → 또 올린다 → "이건 원래 울리는 알람이야"
→ 실제로 무슨 일이 있었는지는 끝내 확인되지 않았다
```

> 손실이 없었다는 사실은 **그 판단이 안전했다는 증거가 아니다.**

**현상유지 편향을 깨는 질문 하나**
> "지금 이걸 쓰고 있지 않다면, 오늘 새로 도입할 것인가?"

**목표는 무오류가 아니라 알아차림이다.** 편향을 없애는 건 불가능하다. 이름을 붙일 수 있게 되는 것이 1단계다.

- [경험 슬롯 ③] 안전 착각에 걸렸다가 결국 터진 사례

> **[KB 3] 8년 차가 되면서 바뀐 습관 (1분)**
>
> "주니어 때는 시야가 훨씬 좁았습니다. 어떤 기술적 문제 하나에 꽂히면 그것만 해결하려고 했고, 기술적으로 더 좋은 답을 찾는 것이 좋은 개발자의 역할이라고 생각했습니다.

>
> 예전에는 요청을 웬만하면 다 들어주고 어떻게든 해내는 사람이 좋은 개발자라고 생각했습니다. 그런데 지금은 무조건 다 들어주는 것이 책임감은 아니라는 걸 알게 됐습니다. 불가능하거나 비용에 비해 가치가 낮다면 왜 그런지 설명하고, 필요할 때는 '안 된다'고 말하려고 합니다.

>
> **경력이 쌓이면서 정답을 더 많이 알게 됐다기보다, 하나의 결정을 볼 때 고려하는 관점이 더 많아졌다고 생각합니다.**"

> 회사 얘기가 아니라 개인 성장 얘기라 **공유 위험이 가장 낮은 슬롯**이다.

### 1-4. 절제의 우위 — 조직의 장치 (6분)

개인의 의지에 기대는 규율은 확장되지 않는다. **좋은 행동을 가장 쉬운 행동으로 만드는 것**이 조직의 일이다.

**확장 가능한 정책** (구글)

```text
좋은 의도와 개인의 기억에 의존
              ↓
반복 가능한 절차로 표준화
              ↓
도구로 자동화
```

> 사람이 매번 기억해야 하는 규칙은 조직이 커지면 무너진다. **"조심하자"는 대책이 아니다.**

> **[KB 4] 규칙을 도구로 옮긴 사례 (2분)**
>
> "사람이 조심하는 것을 시스템의 동작으로 바꾼 경험이 두 가지 있습니다.
>
> 첫 번째는 LG CNS 클라우드 플랫폼팀에서 클라우드 비용 정산 화면을 개발했을 때입니다. 주니어 시절이었는데 개발 과정에서 정산 금액이 잘 맞지 않는 문제가 반복됐습니다. '배포 전에 정산 결과를 잘 확인하자'는 말만으로는 같은 문제를 막을 수 없었습니다. 그래서 계산 로직의 단위 테스트를 추가하는 데서 끝내지 않고, 최종 API를 대상으로 하는 통합 테스트를 만들었습니다. 배포 파이프라인이 새 버전의 API를 직접 호출해 정산 결과가 일치하는지 확인하고, 검증을 통과한 경우에만 블루·그린 환경을 전환하도록 수정했습니다. 정산 검증을 개발자의 기억이나 배포 전 체크리스트가 아니라 **배포의 필수 관문**으로 만든 것입니다.
>
> 두 번째는 오픈뱅킹에서의 경험입니다. 타행 계좌에서 다른 타행 계좌로 이체하려면 먼저 타행에서 당행으로 출금한 뒤, 당행에서 다시 타행으로 입금하는 두 단계가 필요합니다. 첫 번째 출금은 성공했는데 두 번째 입금이 실패하면 고객의 돈이 당행에 남기 때문에 두 단계 사이의 정합성을 맞추는 것이 항상 중요합니다.
>
> 과거에는 이런 불일치 건을 사람이 찾아 수기로 처리했습니다. 이후 실패한 거래를 시스템에서 재처리할 수 있도록 작업했고, 그 결과 수기 처리 비율을 현저히 줄일 수 있었습니다. 이 사례에서는 '실패하면 담당자가 확인해서 처리한다'는 운영 규칙을 **시스템이 복구할 수 있는 경로**로 옮긴 셈입니다.
>
> 하나는 문제가 있는 배포를 통과시키지 않는 예방 장치이고, 다른 하나는 분산된 처리 중 일부가 실패했을 때 복구하는 장치입니다. 공통점은 **사람이 매번 기억하고 판단해야 했던 일을 반복 가능한 시스템 동작으로 바꿨다는 것**입니다."
>
> ⚠️ **최종 공개 범위 검수:** 오픈뱅킹의 타행 간 이체 처리 흐름과 재처리 기능의 설명 범위를 발표 전에 확인한다.

**천재 신화를 버린다** (구글 2장)

작업을 완성할 때까지 숨기거나 코드를 개인이 독점하면:

- 잘못된 방향을 늦게 발견한다
- 지식이 한 사람에게 집중된다 (버스 팩터)
- 담당자가 자리를 비우면 프로젝트가 멈춘다
- 코드가 조직의 자산이 아닌 개인의 영역이 된다

**협업의 세 기둥**

| 원칙 | 의미                                 | 실무 행동                                |
|------|--------------------------------------|------------------------------------------|
| 겸손 | 자신이 틀릴 수 있음을 인정한다       | 피드백을 요청하고 실수를 공개한다        |
| 존중 | 동료의 능력과 관점을 인정한다        | **사람 대신 코드와 아이디어를 비판한다** |
| 신뢰 | 동료가 올바르게 행동할 것이라 믿는다 | 권한을 위임하고 과도하게 통제하지 않는다 |

**코드 리뷰는 버그 탐지 절차가 아니다** (구글 3.2)

리뷰의 6가지 목적: 정확성 향상 / **다른 사람이 이해할 수 있는지 확인** / 일관성 유지 / **설계 지식과 맥락 공유** / 공동 소유권 형성 / 멘토링

좋은 리뷰의 조건:

> **[KB 5] 코드 리뷰가 실제로 도는 방식 (2분)** ★ 양쪽 다 궁금해하는 주제
>
> "제가 있는 서버팀에서는 코드 리뷰가 시스템상 반드시 통과해야 하는 관문은 아니고, 공식적인 그라운드 룰로 정해둔 것도 아닙니다. 하지만 머지하기 전에는 MR을 리뷰 방에 무조건 올립니다. 팀원들도 가능한 한 적극적으로 봐주려고 하고, 특히 같은 프로젝트 구성원끼리는 머지 전에 한 번씩 확인하는 것이 암묵적인 규칙입니다.
>
> 여기에는 책임에 관한 팀의 인식도 있습니다. 리뷰 없이 배포했다면 배포한 사람이 그 변경에 대한 책임을 회피하기 어렵습니다. 반대로 MR을 올리고 함께 검토했다면 결과도 우리 모두의 공동 책임이라는 생각이 강합니다. 이것은 회사의 공식 책임 규정이라기보다 **제가 있는 팀의 협업 문화**입니다.
>
> 리뷰를 요청하는 사람에게도 책임이 있습니다. 리뷰어가 읽기 쉽도록 MR에 변경의 배경과 컨텍스트, 실제 변경사항을 자세히 적습니다. 커밋 하나에는 한 가지 변경사항과 한 가지 변경 이유만 담으려고 하고, 커밋 메시지에도 변경의 이유와 근거를 구체적으로 남깁니다. 기능 변경과 리팩터링은 반드시 별도 커밋으로 나누고, 가능하면 MR 자체의 범위도 작게 나눠 리뷰어의 부담을 낮춥니다.
>
> 모바일 클라이언트 개발 조직은 운영 방식이 더 명시적입니다. 코드 리뷰가 공식 그라운드 룰이고, Android는 Android 개발자끼리, iOS는 iOS 개발자끼리 전사 개발자 중 무작위로 배정된 최소 3명의 리뷰가 필요합니다. 여기에 실제 프로젝트 멤버도 별도의 필수 리뷰어로 참여합니다. 같은 회사 안에서도 팀과 플랫폼의 특성에 따라 리뷰 제도가 다를 수 있다는 사례입니다.
>
> 최근에는 AI 때문에 리뷰 방식도 달라지고 있습니다. AI로 코드 생산 속도가 빨라지면서 사람의 리뷰 속도가 따라가지 못하는 상황이 생깁니다. 은행이기 때문에 그럼에도 최대한 꼼꼼하게 보려고 하지만, 이제는 AI에게 1차 리뷰를 맡기고 개발자는 AI가 보기 어려운 영역에 집중하려고 합니다.
>
> 이때 커밋을 잘게 나누는 기존 규칙이 특히 유용하게 작동합니다. 리팩터링 커밋은 기능이 달라지면 안 된다는 비교적 명확한 정답이 있기 때문에 AI가 확인하기 좋은 영역입니다. 커밋에 리팩터링임을 명시하면 AI가 동작 변경 여부를 먼저 검사할 수 있고, 시간이 부족한 개발자는 비즈니스 의도가 들어간 기능 커밋을 중점적으로 볼 수 있습니다.
>
> **AI가 리뷰 규칙을 새로 만든 것이 아니라, 이전부터 지키던 작은 커밋과 변경 유형 분리가 AI 시대에 더 큰 효과를 내기 시작한 것입니다.**"
>
> ⚠️ **최종 공개 범위 검수:** 서버팀의 책임 인식, 모바일 클라이언트의 최소 3인·무작위 리뷰어 배정 규칙을 발표 전에 확인한다.
> 회사 1처럼 개발자가 3명인 팀에는 인원수를 복제하기보다 **같은 프로젝트의 다른 한 사람이 변경 맥락을 공유하는 것**이 핵심이라고 덧붙인다.

- 변경을 **작고 독립적으로** 만든다
- 변경 이유와 영향을 설명한다
- 필요한 최소 인원에게 요청한다
- **자동화할 수 있는 검사는 도구에 맡긴다** — 사람은 공백과 줄바꿈이 아니라 설계에 집중한다
- 완벽한 코드보다 **코드베이스를 전반적으로 개선하는 변경**을 지향한다

**문서도 코드처럼 관리한다** (구글 3.3)

- 독자를 명확히 정한다 / 소스와 함께 버전 관리 / 리뷰하고 이력 남김 / **소유자 지정** / 검색 가능한 위치 / 오래된 문서는 수정하거나 폐기

| 문서 유형          | 답해야 하는 질문                        |
|--------------------|-----------------------------------------|
| 참조 문서          | 정확히 어떻게 사용하는가?               |
| **설계 문서(ADR)** | 무엇을 왜 이런 구조로 만들 것인가?      |
| 튜토리얼           | 처음 사용하는 사람이 어떻게 시작하는가? |
| 개념 문서          | 어떤 원리로 동작하는가?                 |

> **문서가 없는 것도 문제지만, 낡은 문서가 공식 정보처럼 남아 있는 게 더 위험하다.** 유지할 자신이 없는 문서는 만들지 않는다.

> **[KB 6] 문서화를 어디까지 하는가 (2분)** ★ 회사 1의 원문 질문에 직결
>
> "저희도 모든 것을 문서화하지는 않습니다. 원래는 **코드가 유일한 SSOT이고, 가능한 한 코드 자체로 의도를 드러내자**는 경향이 강했습니다. 주석도 코드와 달라져 신뢰를 잃을 수 있기 때문에 최소화했습니다. 코드로 충분히 표현할 수 있는 내용은 별도 문서나 주석으로 반복하지 않고, 실수하기 쉬운 동작은 설명보다 테스트 코드로 회귀를 막는 쪽을 선호했습니다.
>
> 다만 코드만으로 남길 수 없는 것들은 따로 기록했습니다. 아키텍처, 기술 스택, 중요한 설계처럼 이견이 있었던 큰 결정은 프로젝트별 ADR로 남깁니다. 같은 논의를 반복하지 않도록 당시 선택의 근거와 이유를 기록하고, 그 근거와 전제가 바뀌지 않는 한 당시의 결정을 존중합니다. 코드로 드러내기 어려운 도메인 지식과 배경, 반복되는 문의와 운영 이슈, 장애 대응과 회고도 프로젝트나 팀 단위로 기록했습니다. 기술 부채는 Jira 백로그로 관리하고 개발자가 자발적으로 가져가거나 팀장이 필요에 따라 분배했습니다.
>
> 문제는 문서의 위치였습니다. Wiki와 Jira, 기획 문서, Google Sheets, PPT, Figma 등에 정보가 흩어졌고, 서로 다른 시점의 내용이 파편화된 채 최신화되지 않는 경우가 생겼습니다. 검색도 어려웠고 결국 확실히 믿을 수 있는 것은 다시 코드라는 결론으로 돌아가곤 했습니다.
>
> AI가 등장하면서 상황이 달라졌습니다. 문서 작성 비용이 낮아졌고 AI가 파편화된 정보를 모아 정리할 수도 있게 됐습니다. 반대로 흩어진 정보 중 하나라도 부정확하거나 오래됐다면 AI가 그것들을 그럴듯하게 조합해 잘못된 답을 만드는 문제도 생겼습니다. 그래서 최근에는 문서를 중앙에 모아, 일종의 나무위키처럼 공동으로 관리해보려는 시도를 하고 있습니다. 아직은 시범 운영 단계입니다.
>
> 동시에 AI가 코드베이스를 직접 읽고 빠르게 해석할 수 있게 되면서 코드가 SSOT라는 원칙의 가치도 커졌습니다. 과거에는 정책 담당자에게 묻거나 개발자에게 코드 확인을 요청했던 질문을 지금은 AI에게 코드베이스를 기준으로 물어볼 수 있습니다. AI가 코드를 읽어도 오류 가능성이 0은 아니지만, 제 경험상 오래되고 파편화된 2차 문서를 근거로 답하게 하는 것보다는 환각 가능성이 훨씬 낮습니다.
>
> 그래서 제 기준은 이렇습니다. **무엇을 하는지는 코드와 테스트로, 왜 그렇게 결정했는지와 코드만으로 알 수 없는 맥락은 문서로 남깁니다.** 반복되는 문의·운영 이슈와 장애 회고도 문서화할 가치가 있습니다. 반대로 코드로 명확히 드러나는 내용을 설명하기 위해 문서를 하나 더 만들지는 않습니다."
>
> ⚠️ **최종 공개 범위 검수:** 중앙 문서화 시도의 형태와 운영 단계, AI의 코드베이스 활용 방식에 관한 설명 범위를 발표 전에 확인한다.

**품질을 QA에게 넘기지 않는다** (클린 코더 8장)

"QA가 버그를 찾아주겠지"는 품질 책임의 전가다. 다만 **"QA는 아무것도 발견하지 않아야 한다"**는 표현은 QA가 불필요하다는 뜻이 아니라, **개발자가 알고도 남겨 둔 결함을 QA에게 넘기지 말라**는
목표로 읽어야 한다.

- 비즈니스와 QA가 **무엇이 올바른 동작인지** 정의한다
- 개발자는 그것을 실행 가능하게 만드는 데 협력한다
- 정상 경로뿐 아니라 **경계값·오류·권한·예외**도 합의한다

> PM·디자인이 어디까지 정리해야 하는가에 대한 답이 이것이다. **화면 상세도가 아니라 완료 조건의 명확도**다.

### 1-5. 절제의 우위 — 추정과 약속을 구분한다 (5분) ★ 대표·사업부장이 있는 자리의 하이라이트

가장 즉시 써먹을 수 있는 블록. 클린 코더 9·10장. 대표·PM이 참석한 자리라면 오늘의 하이라이트다.

절제의 우위는 무조건 수락하는 태도가 아니라, **불확실성을 숨기지 않고 약속의 경계를 지키는 힘**이다.

| 구분 | 의미                        | 표현                                       |
|------|-----------------------------|--------------------------------------------|
| 추정 | 현재 정보에서의 가능성 분포 | "3~5일이 유력, 외부 API 이슈가 있으면 8일" |
| 약속 | 특정 시점까지 하겠다는 표명 | "수요일까지 A 범위를 인수 가능한 상태로"   |

날짜 하나만 말하면 듣는 사람은 그것을 **약속으로 받아들인다.**

**신뢰할 수 있는 약속의 4요소:** 누가 / 무엇을 구체적으로 / 언제까지 / **그 수단이 자신의 통제 안에 있는가**

| 표현               | 문제                 | 더 좋은 표현                            |
|--------------------|----------------------|-----------------------------------------|
| "필요해요"         | 행위자와 행동이 없다 | "제가 오늘 4시까지 초안을 쓰겠습니다"   |
| "해보겠습니다"     | 성공 기준이 불분명   | "오전에 재현하고 11시에 공유하겠습니다" |
| "누군가 해야 해요" | 책임 주체가 없다     | "제가 오늘 담당자를 정하겠습니다"       |

**추정에 폭을 담는 법 (PERT)**

```text
기대값 μ = (O + 4N + P) / 6      O=낙관 N=유력 P=비관
표준편차 σ = (P - O) / 6
```

`O=2, N=4, P=8`이면 기대값 약 4.3일, 표준편차 1일. **계산의 정밀함보다 폭이 넓은 항목과 위험을 드러내는 데 의미가 있다.**

**좋은 거절의 문법** (반대가 아니라 협상)

```text
"금요일까지 전체 다" → 불가능

대신:
- 필수 A, B는 금요일까지 가능
- C를 포함하면 다음 주 수요일
- 범위를 유지해야 한다면 순서와 위험을 다시 협의
```

- 늦어지면 마감 당일이 아니라 **아는 즉시** 알린다
- **압박은 규율을 버릴 이유가 아니라 규율이 필요한 이유다**

- [경험 슬롯 ④] 일정 협상 사례. 거절했더니 오히려 신뢰가 올라간 경험

> **[KB 7] 일정과 범위를 협상하는 실제 화법 (2분)** ★ 대표·사업부장이 듣는 자리
>
> "회사마다 의사결정에서 기획자와 개발자가 갖는 무게는 다를 수 있습니다. 제가 있는 환경에서는 일정이 현실적으로 맞지 않으면 개발자가 '안 된다'고 말하는 편입니다. 특별히 극적인 사례를 고르기 어려울 정도로 일상적인 일입니다. 스펙을 줄이거나 일정을 미루는 선택지를 놓고 계속 협의합니다. 물론 개발자도 최대한 원래 일정을 맞추려고 노력하고, 개발 과정에서 요구사항이 늘어나는 일도 자주 생깁니다.
>
> 다만 좋은 거절은 '안 됩니다'로 끝나지 않습니다. 예를 들어 요청받은 방식대로 구현하면 난도가 크게 올라가지만, 일부 부가 기능을 조정한 다른 방식이라면 핵심 비즈니스 가치는 지키면서 구현 난도를 크게 낮출 수 있다고 설명합니다. 그러면 기획자는 어떤 가치는 절대 양보할 수 없고 어떤 부분은 조정할 수 있는지 판단합니다. 개발자는 두 선택지의 기술적 차이를 비즈니스가 판단할 수 있는 비용과 효과의 언어로 번역하고, 가능하면 더 나은 대안까지 가져옵니다.
>
> 그래서 '안 된다'고 말하는 것은 개발자가 결정을 막거나 힘을 행사하는 일이 아닙니다. **불가능한 약속을 피하면서도 핵심 가치를 지킬 수 있는 새로운 선택지를 함께 만드는 일**입니다. 과거의 저는 요청을 모두 들어주는 것이 좋은 개발자라고 생각했지만, 지금은 근거 없이 다 된다고 하는 것이 오히려 무책임할 수 있다고 생각합니다.
>
> 제가 경험한 조직에서는 이런 협상 능력을 개발자의 중요한 역량으로 보고 평가하는 편입니다. 단순히 주어진 요구사항을 구현하는 단계를 넘어, 기술적 비용과 비즈니스 가치를 함께 설명하고 대안을 제시할 수 있는지가 **주니어를 벗어나고 있는지를 판단하는 핵심 지표 중 하나**라고 생각합니다."
>
> 대표·사업부장 쪽을 향해 덧붙일 문장: **"개발자에게 날짜 하나만 물으면 약속처럼 답하기 쉽습니다. 범위와 반드시 지켜야 할 가치도 함께 물어봐 주시면 훨씬 좋은 대안이 나옵니다."**
>
> ⚠️ **최종 공개 범위 검수:** 협상 능력이 개발자 평가와 성장 단계에서 어떻게 다뤄지는지에 관한 표현을 발표 전에 확인한다. 공식 인사 기준이 아니라 발표자가 경험한 문화와 개인 견해로 말한다.

> **전환:** 여기까지가 절제의 우위다. 더 나은 판단을 정하고 압박 속에서도 지켰다면, 마지막은 틀렸을 때도 다음 시도를 남기는 **자금의 우위**다.

### 1-6. 자금의 우위 — 파산하지 않는 것이 먼저다 (5분)

자금의 우위는 많이 가진다는 뜻보다, **한 번의 실패가 마지막 실패가 되지 않도록 베팅 크기를 제한하는 것**이다. 확률적 우위가 있고 절제의 원칙을 지켜도 한 번의 실패로 퇴장하면 그 우위는 실현되지 않는다.

승률 60%인 전략도 한 번에 전액을 걸면 40%로 끝난다. 나눠 걸면:

| 연속 시도 | 모두 실패할 확률 |
|----------:|-----------------:|
|       1회 |              40% |
|       2회 |              16% |
|       3회 |             6.4% |

> 핵심은 높은 승률에 대한 확신이 아니라 **우위가 드러날 때까지 살아남는 것**이다.

**개발에서의 베팅 사이즈**

| 자금 관리                  | 개발에서의 대응물                |
|----------------------------|----------------------------------|
| 한 번에 전액을 걸지 않는다 | **작은 PR, 작은 배포**           |
| 분할 매수                  | 기능 플래그, 카나리, 단계적 출시 |
| 손절 라인을 미리 정한다    | 롤백 경로, 실패 판정 기준        |
| 베팅 한도(table limit)     | 배포 단위 상한, 권한 등급        |
| 생활비와 투자금 분리       | **핵심 경로와 실험 분리**        |

> 모던 SWE가 "작은 변경"을 강조하는 이유가 이것이다. 작은 변경은 **일정 관리 기법이 아니라 자금 관리 기법**이다. 반복 개발은 잘못된 판단으로 인한 손실을 제한하는 **방어적 설계 전략**이다.

**여유가 없을수록 한 방에 끌린다**

자금의 우위는 극단적 위험을 감수하지 않아도 되는 **선택의 여유**이기도 하다.

자연 수익률은 마이너스다.

> **아무 원칙 없이 개발하면 코드베이스는 유지되는 게 아니라 나빠진다. 엔트로피가 기본값이다.**

"일단 돌아가게 만들자"는 중립이 아니라 마이너스다. 그래서 **함부로 투자하지 않는 법을 먼저 배운다** → 함부로 추상화하지 않는 법, 함부로 도입하지 않는 법.

**시드가 작을수록 극단적 위험을 택한다**

배고픈 새일수록 결과가 불확실한 먹이통을 고른다는 실험이 있다. 작지만 확실한 보상으로는 생존할 수 없을 때, 실패 가능성이 커도 큰 보상을 노리는 선택이 합리적으로 보인다.

> 스타트업이 "한 방에 뒤집을" 전면 재작성이나 최신 아키텍처 전환에 끌리는 이유가 여기 있을 수 있다. **조급함은 적절한 위험은 피하면서 극단적 위험을 택하게 만든다.**

비난이 아니라 구조의 문제로 다룬다. 다만 알고 하는 것과 모르고 하는 것은 다르다.

# 세션 2. 좋은 소프트웨어를 만들어 나가는 방법 (40분)

> **부제:** 개발자의 시간을 어디에 배분할 것인가
>
> **한 문장:** 좋은 소프트웨어는 변하지 않는 소프트웨어가 아니라 **변경 비용이 낮은** 소프트웨어다. 그리고 그 비용을 낮추는 일은 **자본 배분 문제**다.

**주 레퍼런스:** 모던 SWE + Tidy First + 투자 철학·초과수익 + 그리디/A\* + 구글

### 2-1. 좋은 소프트웨어의 정의 (3분)

**프로그래밍과 소프트웨어 엔지니어링의 차이** (구글 1장)

프로그래밍이 현재의 문제를 푸는 코드를 쓰는 일이라면, 소프트웨어 엔지니어링은 그 코드가 **계속 변경되고 더 많은 사람에게 쓰일 것**까지 고려하는 일이다.

- **시간과 변화**: 요구사항·기술·사용자는 계속 바뀐다
- **규모와 성장**: 지금 되는 방식이 커지면 안 될 수 있다
- **비용과 트레이드오프**: 모든 결정에 개발비·유지비·기회비용이 따른다

> **좋은 시스템은 변하지 않는 시스템이 아니라 안전하고 저렴하게 변경할 수 있는 시스템이다.**

**두 개의 축** (모던 SWE)

```text
좋은 소프트웨어 엔지니어링
├─ 학습 최적화     : 반복 · 피드백 · 점진주의 · 경험주의 · 실험주의
└─ 복잡성 관리     : 모듈성 · 응집성 · 관심사 분리 · 정보 은닉 · 결합도
```

- 소프트웨어는 **생산이 아니라 설계**다. 계획 실행이 아니라 발견 과정이다
- 두 축은 서로를 강화한다: 좋은 설계 → 빠른 피드백 → 더 나은 설계

**그런데 이걸 안다고 오늘 무엇을 할지가 정해지지는 않는다.** 그게 이 세션의 진짜 주제다.

### 2-2. 시간은 자본이다 — 무엇에 투자할 것인가 (8분)

**"좋은가"는 질문이 아니다**

투자자는 "이 주식이 좋은가?"를 묻지 않는다. 답이 늘 "여러 이유로 좋다"라서 **매매로 이어지지 않기 때문이다.**

> **"지금 이 순간에, 다른 종목이 아니라, 이 종목을 사야 하는 이유는 무엇인가?"**

개발자 버전:

> **"이번 스프린트에, 다른 작업이 아니라, 이 리팩터링을 해야 하는 이유는 무엇인가?"**

Tidy First의 "훗날 정리하기"가 백로그에서 영원히 실행되지 않는 이유가 이것이다. **"코드가 나쁘다"는 이 질문의 답이 아니다.** 언제나 참인 명제라 시점을 특정하지 못한다.

**촉매 (catalyst) — 가치는 저절로 실현되지 않는다**

아무도 안 보는 주식은 싸게 살 수 있지만 10년간 싼 채로 있을 수 있다.

```text
좋은 투자     = 가치와 가격의 괴리 + 괴리가 줄어들 계기 + 기다릴 여유
좋은 리팩터링 = 현재 구조의 마찰   + 그 마찰을 겪을 예정된 변경 + 일정 여유
```

> **촉매 = 예정된 변경.** 앞으로 안 건드릴 코드는 아무리 더러워도 가치가 실현되지 않는다.

**시간 포트폴리오 — 성격이 다른 네 자산**

| 자산        | 성격            | 수익 시점            |
|-------------|-----------------|----------------------|
| 기능 개발   | 직접 매출       | 즉시                 |
| 구조 개선   | **옵션**        | 다음 변경 때         |
| 관측·자동화 | **보험 + 정보** | 사고 시 / 지속적으로 |
| 학습        | **인적 자본**   | 불확실, 장기         |

Kent Beck: 기능 변경 = 매출, 구조 변경 = 옵션. 여기에 관측 (보험)과 학습 (인적 자본)을 더한다.

- 100% 기능에만 쓰는 팀 → **옵션이 없다.** 나중에 아무것도 선택할 수 없게 된다
- 100% 구조에 쓰는 팀 → **회수 시점이 오지 않는다**
- 관측에 0을 쓰는 팀 → 무슨 일이 일어나는지 모른 채 베팅한다

**투자 논지 (thesis)를 쓴다**

"코드가 더럽다"는 예산을 못 받는다.

```text
문제: 주문 상태 변경 시 5개 모듈을 함께 수정해야 한다
영향: 최근 3개 기능에서 각각 1~2일 추가 발생          ← 이자 (현재 새는 비용)
촉매: 환불 정책 기능이 다음 스프린트에 예정            ← 왜 지금인가
비용: 2일
회수: 향후 변경 2회 이내
틀렸다고 판단할 조건: 환불 기능이 취소되면 보류        ← 반증 조건
```

마지막 줄이 중요하다. **틀렸을 때 인정할 조건을 미리 적는 것**이 확신 편향에 대한 유일한 방어다.

**우리 팀의 알파는 어디에 있는가**

초과수익은 **시장의 비효율**에서 나온다. 남들이 다 하는 걸 그대로 하면 알파가 없다 — 이미 가격에 반영된 정보다.

> "판교가 이렇게 합니다"를 그대로 가져오는 것이 왜 위험한가. 그건 **그들의 비효율에 대한 답**이고, 이미 널리 알려진 정보다.

조직 안의 비효율 = **비용은 계속 나가는데 아무도 보고 있지 않은 곳**

- 매주 반복하는데 아무도 자동화하지 않은 수작업
- 모두가 참고 있는 마찰 (빌드 5분, 로컬 환경 세팅 반나절)
- 아무도 안 보는 지표, 아무도 안 읽는 로그
- "원래 이래요"라는 답이 돌아오는 것들

**효율성은 상대적이다.** 그 도메인을 오래 판 사람에게만 보이는 비효율이 있다. 경력의 가치가 여기 있다.

> 가져갈 질문: **"우리 팀에서 비용은 계속 나가는데 아무도 보고 있지 않은 곳은 어디인가?"**

- [경험 슬롯 ⑤] 아무도 안 보던 비효율을 찾아 고친 사례. 효과를 숫자로

> **[KB 8] 기능과 구조에 시간을 어떻게 나누는가 (2분)**
>
> "지금 진행 중인 셀카 인증 개선에서 기능과 구조 개선의 범위를 나눈 사례가 있습니다. 기존에는 클라이언트가 촬영한 여러 사진을 한 장으로 합친 뒤 JPEG으로 압축해 서버에 보냈습니다. 서버는 그 이미지를 다시 개별 사진으로 자르고 JPEG으로 한 번 더 압축해 AI 모델에 전달했습니다. 사진이 여러 서버를 거치는 동안에도 계속 multipart 요청으로 전달됐습니다.
>
> 이 구조에서는 JPEG 손실 압축이 두 번 일어나 이미지 품질이 떨어지고, 그 손실이 모델 성능에도 영향을 줄 수 있었습니다. 그래서 이번에는 두 번째 JPEG 압축을 없애는 데 집중했습니다. 중간 서버에서는 이미지를 직접 잘라 다시 압축하지 않고 자를 위치만 검출해 전달합니다. AI 모델 바로 앞의 전처리 서버가 벡터화할 때 전달받은 위치를 기준으로 이미지를 분할하도록 바꿨습니다. 이미지 전달 방식도 서버마다 multipart로 넘기지 않고 버킷에 한 번 올린 뒤 최종 사용처가 내려받도록 수정했습니다.
>
> 전체 구조를 다시 만드는 것보다 범위가 작은 변경이지만 고객의 인증 성공률과 대기시간, 모델 입력 품질에 직접 영향을 줄 수 있어 비용 대비 효과가 크다고 판단했습니다.
>
> 반면 여러 서버에 로직이 흩어져 생기는 결합도 문제까지 이번에 모두 해결하지는 않았습니다. 그것까지 건드리면 영향 범위와 리스크, 필요한 공수가 크게 늘어납니다. 해당 문제는 백로그에 기록하고 나중에 관련된 큰 프로젝트를 진행할 때 함께 수정하기로 했습니다.
>
> 저는 비용이 작은 개선은 오래 고민하기보다 눈에 보일 때 빠르게 처리하는 편입니다. 반대로 비용이 큰 개선은 기대 효과뿐 아니라 영향 범위와 리스크까지 반드시 봅니다. 리스크도 비용의 일부이기 때문입니다. 주어진 공수와 일정, 작업 크기, 기대 효과를 함께 놓고 판단합니다.
>
> 개인적으로는 할 수 있을 때 최대한 개선하려는 성향이 강하지만, 여기에 하나의 정답이 있다고 생각하지는 않습니다. 판단이 애매하면 혼자 밀어붙이지 않고 팀의 논의 주제로 던집니다. **작고 효과가 큰 개선은 지금 하고, 크고 결합된 문제는 촉매가 생길 때까지 기록해두는 것**이 현재 제가 균형을 잡는 방식입니다."
>
> ⚠️ **최종 공개 범위 검수:** 셀카 인증의 이미지 처리 단계, 서버 간 multipart 전달, 버킷 기반 전달 구조와 기대 효과의 공개 범위를 발표 전에 확인한다.

### 2-3. 부채의 금리 — 언제 갚고 언제 안 갚는가 (7분) ★ 대표가 가장 듣고 싶어 하는 답

**부채가 나쁜 게 아니다. 이자율이 문제다.**

Ward Cunningham의 원래 비유에는 이자가 있었다. 부채를 지는 것 자체는 정상적인 금융 활동이다.

```text
기술 부채의 이자 = 그 부채 때문에 매번 추가로 드는 비용
이자율 = 변경 빈도 × 변경당 추가 비용
```

|      | 저금리 부채                                                | 고금리 부채                                        |
|------|------------------------------------------------------------|----------------------------------------------------|
| 예시 | 3년째 안 건드린 배치 스크립트, 곧 폐기할 마이그레이션 코드 | 매주 건드리는 결제 모듈, 배포마다 사람이 붙는 절차 |
| 이자 | 거의 안 붙는다                                             | **복리로 붙는다**                                  |
| 판단 | **의도적으로 안 갚는다**                                   | **빨리 갚는다**                                    |

> **금리가 낮으면 부채를 들고 있는 게 손해가 아니다.** 의도적으로 게으르게 지불하는 것도 전략이다.
> 문제는 금리를 재보지도 않고 "부채는 나쁘다"로 일괄 처리하는 것이다. 그러면 저금리 부채를 갚느라 고금리 부채의 이자를 계속 낸다.

**이자율을 실제로 재는 법**

추상적인 개념이 아니라 측정 가능하다.

```bash
# 지난 6개월 동안 가장 자주 바뀐 파일 = 이자율이 가장 높은 후보
git log --since="6 months ago" --format= --name-only \
  | sort | uniq -c | sort -rn | head -20
```

여기에 두 가지를 더 묻는다.

1. 이 파일을 건드릴 때마다 **얼마나 더 걸렸나?** (변경당 추가 비용)
2. 앞으로 **몇 번 더 건드릴 예정인가?** (= 촉매)

> 자주 바뀌는 파일 목록과 로드맵을 나란히 놓으면 상환 우선순위가 대체로 나온다.

**부채 사분면** (Martin Fowler)

|            | 신중한                                               | 무모한             |
|------------|------------------------------------------------------|--------------------|
| **의도적** | "지금은 출시하고 나중에 갚는다" ← 정상적인 금융 활동 | "설계할 시간 없어" |
| **우발적** | "이제야 어떻게 했어야 했는지 알겠다" ← 불가피        | "설계가 뭐죠?"     |

좌상단은 문제가 아니다. **다만 갚을 계획이 있을 때만 그렇다.** 갚지 않는 의도적 부채는 무모한 부채와 같아진다.

**상환 우선순위 — 금리 × 가역성**

|              | 저금리 (변경 빈도 낮음) | 고금리 (변경 빈도 높음)              |
|--------------|-------------------------|--------------------------------------|
| **가역적**   | 안 갚는다               | **지금 갚는다** — 싸고 효과 크다     |
| **비가역적** | 기록만 해둔다           | ⚠️ **가장 위험. 계획을 세워 갚는다** |

우하단이 진짜 위험 구역이다. **자주 바뀌는데 되돌릴 수 없는 것** — 스키마가 매 스프린트 바뀌는 상황, 외부에 공개한 API가 계속 흔들리는 상황.

### 2-4. 가역적 결정과 비가역적 결정 (9분) ★ 오늘의 핵심 기준

**두 종류의 문**

|               | 가역적 결정           | 비가역적 결정             |
|---------------|-----------------------|---------------------------|
| 성격          | 틀리면 되돌릴 수 있다 | 되돌리는 비용이 매우 크다 |
| 속도          | **빠르고 과감하게**   | **신중하게, 천천히**      |
| 필요한 근거   | 적어도 된다           | 충분히                    |
| 의사결정 방식 | 담당자가 그냥 한다    | 설계 회의를 연다          |
| 실패 시       | 되돌린다              | **함께 살아야 한다**      |

| 가역적 → 그냥 하라          | 비가역적 → 미리, 신중히     |
|-----------------------------|-----------------------------|
| 이름 변경, 함수 추출/인라인 | **DB 스키마 변경**          |
| 코드 이동, 순서 변경        | **외부 공개 API 계약**      |
| 명시적 파라미터 도입        | **대규모 데이터 이전**      |
| 죽은 코드 삭제              | **운영 데이터의 의미 변경** |
| 대부분의 라이브러리 교체    | 결제·정산 로직의 계산 방식  |

**조직이 느려지는 진짜 이유**

|                       | 실제로 가역적         | 실제로 비가역적 |
|-----------------------|-----------------------|-----------------|
| **가역적으로 다룸**   | ✅ 빠르다             | ⚠️ 사고가 난다  |
| **비가역적으로 다룸** | ⚠️ **가장 흔한 낭비** | ✅ 안전하다     |

> **대부분의 결정은 가역적인데 비가역적인 것처럼 다뤄진다.** 변수명을 두고 30분 논쟁하는 팀이 스키마는 그냥 배포한다.
> **팀의 논의 시간이 좌하단에 쓰이고 있다면 그게 낭비다.**

**하이럼의 법칙 — 생각보다 더 비가역적인 것** (구글 1.1)

> API 사용자가 충분히 많아지면 **문서에 명시된 동작뿐 아니라 관찰 가능한 모든 동작**을 누군가 의존하게 된다.

- 결과의 출력 순서 / 오류 메시지 문구 / 처리 시간과 타이밍 / 명시되지 않은 기본값 / 우연히 노출된 내부 동작

내가 가역적이라고 생각한 것이 실제로는 비가역적일 수 있다. **정보 은닉이 중요한 이유가 이것이다** — 감춰두지 않은 것은 전부 계약이 된다.

**그리디와 A\* — 얼마나 탐색할 것인가**

```text
g(n) = 출발점에서 여기까지 실제로 든 비용
h(n) = 여기서 목표까지 남은 예상 비용

그리디 최우선 탐색 :  f = h(n)          목적지에 가까워 보이는 쪽으로
A*                :  f = g(n) + h(n)   여기까지 온 비용까지 포함해서
다익스트라         :  f = g(n)   (h=0)  전부 탐색
```

| 모드             | 개발에서의 모습                            | 특징                        |
|------------------|--------------------------------------------|-----------------------------|
| 그리디 (h만)     | "일단 되게 만들자"                         | 빠르다. 가끔 막다른 길      |
| A\* (g+h)        | "여기까지 온 것까지 포함해 어느 쪽이 싼가" | 균형. 좋은 감이 있으면 강력 |
| 다익스트라 (h=0) | 전수 검토, 3주짜리 설계 회의               | 확실하지만 느리다           |

**스타트업은 그리디로 시작해도 된다**

> 0.1초에 응답하는 API 1개보다, **0.5초에 동작하는 API 3개**가 나을 수 있다.

목표 함수가 다르기 때문이다. 대기업의 `h(n)`은 대체로 "완성도까지 남은 거리"지만, 스타트업의 `h(n)`은 **"검증까지, 생존까지 남은 거리"**다. 같은 지도를 걷고 있지 않다.

같은 이유로 정당화되는 선택들: 캐시 대신 인덱스 하나 / 추상화 없이 복붙 두 번 (세 번째에 추출) / 완벽한 도메인 모델 대신 동작하는 CRUD.

**그리디의 정의를 기억한다**

> 그리디 알고리즘의 정의는 "매 순간 최선을 고른다"가 아니다. **"그 선택을 되돌리지 않는다"**까지가 정의다.

```text
가역적 결정   → 그리디로 간다. "되돌리지 않는다"는 제약이 무해하다.
비가역적 결정 → 그리디를 쓰면 안 된다. 되돌릴 수 없으니까.
```

**그리디 선택 속성을 증명해야 한다**

알고리즘에서 그리디를 쓰려면 "지금의 최선이 전체의 최선으로 이어진다"를 **증명해야** 한다.

> **"이 빠른 선택이 나중에 우리를 막다른 길로 몰지 않는다"를 설명할 수 있는가?**
> 설명할 수 있으면 그리디는 게으름이 아니라 전략이다. 설명할 수 없으면 그냥 도박이다.

**반례를 기억한다 — 동전 교환**

동전 단위가 `1, 3, 4`이고 `6`을 만들 때:

```text
그리디(큰 것부터):  4 + 1 + 1 = 3개
최적:              3 + 3     = 2개
```

한국 동전 (500/100/50/10)에서는 그리디가 항상 최적이다. **그리디가 통하느냐는 문제의 구조에 달려 있지, 그리디 자체의 성질이 아니다.**

**g (n)과 매몰비용은 다르다**

|              | 미래 비교에 유효한가                                               |
|--------------|--------------------------------------------------------------------|
| A\*의 `g(n)` | **유효하다.** 이 경로로 계속 갔을 때의 총비용을 계산하는 데 쓰인다 |
| 매몰비용     | **무관하다.** 어떤 선택을 하든 회수되지 않는다                     |

- ❌ "이미 3개월 썼으니 계속해야 한다" → 매몰비용 오류
- ✅ "이 경로면 총 6개월, 다른 경로는 지금부터 총 2개월" → 올바른 `g+h` 비교
- 구분 기준: **이미 만든 것이 자산으로 남는가.** 남으면 `g(n)`의 일부고, 폐기해야 하면 매몰비용이다

**휴리스틱의 품질이 탐색 비용을 정한다**

- `h(n)`이 실제에 가까울수록 **적게 탐색하고 정답에 도달**한다 → **좋은 감 (感)은 탐색 비용을 줄인다**
- `h(n)`이 실제 비용을 **과대평가하면 최적을 놓친다** → "그건 어려울 거야"라는 과대평가가 시도 자체를 막는다
- `h(n) = 0`이면 다익스트라가 된다 → **아무 감도 없으면 전부 탐색해야 한다.** 도메인 학습이 곧 속도다

### 2-5. 실행 — 멈추지 않고 갚는 법 (6분)

**Tidy First의 4분면**

| 선택            | 언제                                            | 예시                                |
|-----------------|-------------------------------------------------|-------------------------------------|
| **먼저** 정리   | 작은 정리가 지금 기능을 더 쉽고 안전하게 만든다 | 조건문을 가드 절로 바꾸고 분기 추가 |
| **나중에** 정리 | 구현해봐야 적절한 구조가 보인다                 | 구현 후 드러난 중복 제거            |
| **훗날** 정리   | 가치는 있지만 **촉매가 없다**                   | 여러 모듈에 걸친 공통 구조          |
| **안 함**       | 저금리 부채                                     | 곧 폐기할 코드                      |

```text
정리 비용 + 정리 후 개발 비용  <  지금 구조에서 바로 개발하는 비용
```

> **이해하기 위해 구조 변경이 필요하면 먼저, 경험을 통해 구조를 발견해야 한다면 나중에.**

**작은 정리 기법 — 몇 분 안에 끝나고 전부 가역적이다**

| 기법                    | 내용                                                   |
|-------------------------|--------------------------------------------------------|
| 가드 절                 | 예외 조건을 먼저 반환해 중첩을 줄인다                  |
| 죽은 코드 삭제          | 실행되지 않는 코드를 제거한다                          |
| 설명 변수 / 설명 상수   | 복잡한 표현식과 리터럴에 의미를 드러내는 이름을 붙인다 |
| 도우미 함수 추출        | 세부 구현을 이름 있는 함수로 분리한다                  |
| 한 더미로 모으기        | 흩어진 관련 코드를 **먼저 한곳에 모은다**              |
| 대칭성 맞추기           | 같은 의미의 코드를 같은 형태로 통일한다                |
| 읽는 순서 / 응집도 순서 | 독자가 이해하기 좋은 순서로, 관련된 것을 가까이        |
| 명시적 파라미터         | 숨겨진 의존성을 함수의 입력으로 드러낸다               |

> 전부 **가역적**이다. 그래서 논의 대상이 아니라 그냥 하는 것이다.

**구조 변경과 동작 변경을 분리한다**

```text
작은 구조 변경 → 테스트
작은 구조 변경 → 테스트
기능 변경       → 테스트
```

커밋으로 분리하면 리뷰어의 질문이 달라진다.

```text
refactor: 결제 조건을 guard clause로 정리      → "동작이 그대로인가?"
refactor: 금액 계산을 helper로 추출            → "동작이 그대로인가?"
feat: 부분 환불 조건 추가                      → "요구사항에 맞는가?"
```

**전담 인력 없이 하는 법**

- 시간 비율 ("스프린트의 20%")보다 **범위 제한**이 낫다: 이번 기능이 반드시 지나가는 코드만
- 몇 분 단위. **한 시간을 넘으면 범위가 커진 것**
- 이렇게 하면 리팩터링은 신규 개발과 경쟁하는 별도 업무가 아니라 **신규 개발 비용의 일부**가 된다

**정리를 멈추는 5가지 신호** (도파민 경계 — 1-3과 연결)

- 다음 기능을 안전하게 구현할 수 있게 됐다
- 변경해야 할 코드가 충분히 좁아졌다
- 테스트할 수 있는 경계가 생겼다
- 추가 정리가 현재 기능과 직접 관계가 없다
- 구조 변경이 **새로운 설계 논의나 마이그레이션으로 번지기 시작했다**

### 2-6. 복잡성 관리와 관측 (7분)

**복잡성은 두 종류다** (모던 SWE)

| 종류              | 의미                                    | 대응                            |
|-------------------|-----------------------------------------|---------------------------------|
| 본질적 복잡성     | 업무와 문제 자체에 있는 복잡성          | 정확히 이해하고 모델링한다      |
| **우발적 복잡성** | 잘못된 기술·구조·프로세스가 더한 복잡성 | **설계 개선과 자동화로 줄인다** |

**거대한 조회 쿼리는 성능 문제이기 전에 설계 신호다**

40+ 컬럼, 10+ LEFT JOIN, GROUP_CONCAT, 상관 서브쿼리 →
> 화면 요구사항이 그대로 쿼리가 됐다 = **읽기 모델이 없다.** 전형적인 우발적 복잡성이다.

- 응집성: **같은 이유와 주기로 변경되는 요소를 함께 배치**한다
- 관심사 분리: 핵심 로직이 DB·프레임워크를 직접 부르면 테스트도 변경도 어려워진다
- **테스트하기 어렵다 = 설계가 결합돼 있다는 신호.** 테스트 가능성은 품질 속성이 아니라 **설계 품질의 계측기**다

**DRY를 기계적으로 적용하지 않는다**

> **잘못된 결합으로 만든 공통화보다 의도가 분명한 작은 중복이 나을 수 있다.**

서로 다른 이유와 속도로 변하는 코드를 중복 제거를 위해 묶으면 오히려 결합도가 높아진다. 마이크로서비스도 마찬가지다 — DB·동기 호출·배포 절차로 강하게 연결돼 있으면 **분산된 모놀리스**다.

**피드백은 계층마다 다르다** (모던 SWE)

| 영역     | 피드백 수단                      |
|----------|----------------------------------|
| 코딩     | 컴파일러, 정적 분석, 단위 테스트 |
| 통합     | 자동 빌드, 통합 테스트, CI       |
| 설계     | **테스트 가능성**, 코드 리뷰     |
| 아키텍처 | 배포 결과, 성능 측정, 운영 관찰  |
| 제품     | 사용자 행동, 실제 사용 데이터    |
| 조직     | 팀의 독립적인 변경·배포 능력     |

**관측 — 장애 대응 5단계**

```text
감지 → 완화 → 원인 → 재발 방지 → 기록
```

대부분의 팀이 `완화`에서 멈춘다. **"쿼리를 죽여서 해결했다"는 대응이지 개선이 아니다.**

**알람이 알람이 되려면**

자주 보는 패턴: 알람이 자주 울려서 임계치를 30 → 45 → 60으로 올린다.

> 임계치 상향 자체는 틀린 판단이 아니다. **액션 없는 알람은 알람이 아니라 소음**이므로. 문제는 세션 1의 **안전 착각**이다. 세 번 올리는 동안 "실제로 무슨 일이 있었는가"가 확인되지 않으면, 감도만
> 낮추고 위험은 그대로 남는다.

좋은 알람의 3조건:

1. **액션 가능** — 울리면 할 일이 정해져 있다 (런북)
2. **사용자 영향 기준** — CPU 98%보다 "응답 지연 p99 > 3초"
3. **원인이 아니라 증상** — 원인은 대시보드에서 찾는다

**지표를 보는 순서**

```text
사용자 체감 (SLI: 지연/에러율)
        ↓ 무엇이 느린가
요청 단위 (RED: Rate · Error · Duration)
        ↓ 어디가 포화됐나
자원 단위 (USE: Utilization · Saturation · Error)
        ↓ 어떤 작업이 원인인가
개별 쿼리 / 대기 이벤트
```

DB 부하는 **CPU가 아니라 동시 실행 스레드와 DB Load**가 먼저 움직인다.

**원인 쿼리를 빠르게 특정하는 일반적 방법**

| 문제                          | 일반적 대응                                                            |
|-------------------------------|------------------------------------------------------------------------|
| 사후에 어떤 쿼리였는지 모른다 | Slow query log 상시 활성 + Performance Insights 보존                   |
| 누가 호출했는지 모른다        | **SQL 주석에 호출자를 심는다** (`/* app=api svc=campaign ep=/list */`) |
| 긴 쿼리가 DB를 잡는다         | `max_execution_time`, 커넥션 풀 상한                                   |
| 배치가 서비스를 친다          | 읽기 전용 복제본으로 배치·통계 분리                                    |
| 반복 원인을 모른다            | 주간 Top SQL 리뷰                                                      |

**확장의 일반 원칙** (체크리스트만)

- 외부 API 연동 (AI 모델 포함): 타임아웃 필수, 재시도는 멱등할 때만, 서킷 브레이커, 느린 작업은 큐
- 글로벌: 정적 자산은 CDN, 상태는 리전. 대부분의 체감 속도 문제는 리전이 아니라 **요청 수와 페이로드 크기**

- [경험 슬롯 ⑥] 실제로 겪은 DB 장애 1건. **원인보다 "어떻게 알아냈는지"의 순서**

>
> ⚠️ **최종 공개 범위 검수:** 자동로그인, 1% 배포, 대상 서버의 부분 배포 실패와 모니터링 개선 내용을 발표 전에 다시 확인한다.
>
> "자동로그인을 개발할 때 저희가 호출하는 대상 서버에서 배포가 부분적으로 실패한 적이 있습니다. 배포 스크립트에 버그가 있어 일부 서버의 배포가 실패했는데도 결과가 성공으로 표시됐고, 담당 팀도 일부 서버의 형상이 달라졌다는 사실을 인지하지 못했습니다. 그 결과 요청이 정상 배포된 서버로 가면 성공하고, 배포에 실패한 서버로 라우팅되면 실패했습니다.
>
> 당시 자동로그인은 1% 배포 단계여서 전체 트래픽에서 차지하는 비중이 작았습니다. 일부 요청이 실패해도 전체 기준 실패율은 크게 움직이지 않아 Grafana 대시보드에서 빠르게 알아차리지 못했습니다. 대상 서버도 거대한 레거시 시스템이라 경고와 에러 로그가 이미 무분별하게 많이 남고 있었고, Sentry에서도 새로 발생한 중요한 오류를 기존 소음과 구분하기 어려웠습니다. 결국 시간이 한참 지난 뒤 내부 직원의 제보로 문제를 재현하면서 인지했습니다.
>
> 회고 후에는 세 가지를 바꿨습니다. 먼저 대상 팀에서 배포 스크립트를 재점검해 부분 실패를 성공으로 처리하지 않고 **명시적으로 실패하도록** 수정했습니다. 다음으로 전체 실패율만 보지 않고 새로 배포한 API 버전만 필터링해 모니터링할 수 있도록 Grafana 태그를 추가했습니다. 마지막으로 로그 레벨의 기준을 다시 세웠습니다. 당장 대응해야 하는 오류만 `error`, 즉시 대응할 필요는 없지만 확인하고 추적해야 하는 상황은 `warn`, 비밀번호 입력 오류 같은 비즈니스 오류는 `info`로 남기도록 했습니다. 정말 대응이 필요한 것만 알림으로 오고 Sentry에 남게 만들려는 목적이었습니다.
>
> 이 경험으로 배운 것은 **관측 지표가 많다고 문제가 잘 보이는 것은 아니라는 것**입니다. 전체 평균만 보면 작은 배포의 실패가 묻히고, 모든 것을 error로 남기면 중요한 오류가 소음 속에 묻힙니다. 배포 단위로 신호를 잘라 볼 수 있어야 하고, 알림은 실제로 행동할 수 있는 오류에 집중해야 합니다."

**포스트모템은 다섯 줄이면 충분하다**

앞의 장애 사례를 다음 대응의 기준으로 남기는 데 거대한 문서는 필요하지 않다. 스타트업용 최소 템플릿은 다음 다섯 줄이면 충분하다.

1. 무슨 일이 있었는가
2. 언제부터 언제까지 발생했는가
3. 사용자에게 어떤 영향이 있었는가
4. **왜 늦게 알았는가**
5. **다음에는 무엇을 바꿀 것인가**

앞의 자동로그인 사례라면 네 번째 줄에는 `전체 실패율에 묻히고 로그가 너무 많아 감지가 늦었다`, 다섯 번째 줄에는 `부분 배포를 실패로 처리하고, 배포 버전별 지표와 로그 레벨 기준을 추가한다`가 들어간다.

> 회고의 목적은 긴 보고서를 쓰는 것이 아니라 **다음 장애에서 더 빨리 알아채고 대응하는 것**이다. 문서를 못 쓰는 이유가 시간이라면 유지할 수 있는 크기로 줄인다.

# 세션 3. AI 시대의 기술 지형 변화와 대응 (40분)

> **한 문장:** 질문을 바꾼다. *"AI가 코드를 얼마나 잘 쓰는가"* 가 아니라 *"우리 조직이 AI에게 맥락·실행환경·검증·피드백을 얼마나 잘 주는가"*.

**프레임:** `Context → Execution → Verification → Feedback`

> 회사 2의 질문이 대부분 이 세션에 몰려 있으므로 **여기서 한 번 더 선을 그어두는 게 안전하다.**

### 3-0. 앞선 발표를 이어받는다 — 평가 기준이 명료할수록 (2분) ★

> **회사 2는 이 프레임을 이미 들었다.** 저희 회사 금융기술연구소 김현규 님의 「AI가 위협이 아닌, 당신을 위해 일하게 하기」 발표에 나온 내용이다. 같은 회사 사람이라 자연스럽게 이어받을 수 있고, **회사 1에게는 새 내용이라 양쪽 다 성립한다.**

그 발표의 결론은 이 한 문장이었다.

> **"좋은 AI 사용법은 없다. 좋은 사용처만 있을 뿐이다."**

AI는 **평가 기준을 먼저 만들고, 그 기준을 중심으로 발전한다.** 그래서 업무의 평가 기준이 명확할수록 AI를 적극적으로 쓸 수 있다.

평가 기준이 명확한지 판단하는 세 질문:
1. **기대하는 정답이 있는가?** (정답과 대조할 수 있는가)
2. **기대하는 요소가 있는가?** (사람 검수 또는 LLM as a Judge)
3. **검증할 수단이 있는가?** (테스트로 확인할 수 있는가)

**오늘 제가 덧붙이고 싶은 건 이겁니다.**

```text
김현규 님:  평가 기준이 명확할수록 AI를 적극 활용한다
제 언어로:  평가 기준이 명확하다 = 검증 비용이 싸다
           기대값 = 정확도 × 가치 − 검증 비용
```

**같은 얘기를 다른 언어로 한 것이다.** 그리고 여기서 오늘 세션 2와 이어지는 결론이 나온다.

> **소프트웨어 개발은 평가 기준이 이미 명확한 드문 영역이다.**
> 테스트가 곧 정답 대조이고 검증 수단이다. AI가 코딩에서 가장 빠르게 좋아진 이유가 이것이다.
> 그러면 우리가 할 일은 분명하다 — **평가 기준을 더 명확하게 만드는 것.** 그게 세션 2에서 말한 테스트고 경계다.

### 3-1. AI는 세 우위를 어떻게 바꾸는가 (6분)

**병목의 이동**

```text
[전]  요구사항 → 설계 → [코드 작성 ★병목] → 리뷰 → 배포
[후]  요구사항 → [맥락 정리 ★] → 코드 생성 → [검증/리뷰 ★★병목] → 배포
```

생성량은 늘었는데 **검토량은 사람 수만큼만 늘어난다.** 승부처는 "얼마나 잘 만드는가"가 아니라 **"얼마나 빨리 확신할 수 있는가"**다.

**세 우위로 다시 보면**

| 우위     | AI 이전                      | AI 이후                                                           |
|----------|------------------------------|-------------------------------------------------------------------|
| **확률** | 개발자의 판단력              | 판단력 + AI의 확률적 출력. **기대값 = 정확도 × 가치 − 검증 비용** |
| **자금** | 사람의 시간이 곧 베팅 사이즈 | **시도 비용이 급락 → 잘게 쪼개고 반복을 늘릴 수 있다**            |
| **절제** | 압박 속에서 규율 유지        | **싸지니까 더 크게 걸고 싶어진다.** 안전 착각이 강해진다          |

**가장 중요한 한 줄**

> **AI 시대의 진짜 이득은 "빨라진 것"이 아니라 "시행 횟수를 늘릴 수 있게 된 것"이다.**

확률적 우위는 반복해야 드러난다 (세션 1). 시도가 싸지면 반복이 늘고, 반복이 늘면 작은 우위가 실제 성과로 수렴한다.

**단, 조건이 있다.** 이 이득은 **검증도 함께 싸질 때만** 성립한다. 검증이 안 싸지면 생성만 늘고 병목만 커진다.

> **[토스] 검증도 자동화해야 한다는 문제의식**
> 토스 디바이스 팜 '네뷸라' 공개 글은 **"코드 생성량이 늘수록 리뷰·검증 비용이 커지므로 검증도 자동화해야 한다"**는 문제의식을 명시한다. 기기 15대·개발자 1명으로 시작해 실기기 100대 규모로 키웠고, 사람이 OS별로 30~40분 하던 검수를 10분 안에 자동화했다고 밝힌다.
> → 같은 API 위에 **웹 UI · SDK · CLI · AI Agent**가 각각 올라가는 구조. 확산에 유리한 형태다.

**가역성 판단이 더 중요해진다**

생성이 싸지면 **가역적 결정은 훨씬 과감하게** 해도 된다. 세 가지 구현을 만들어 비교하는 게 실제로 가능해졌다. 반대로 **비가역적 결정에서는 AI가 위험을 키운다** — 그럴듯한 스키마 마이그레이션을 5분
만에 만들어주기 때문이다.

> **싸진 것은 생성이지 되돌리기가 아니다.**

**공수 산정은 어떻게 바뀌나**

- 초안 작성 시간은 크게 줄고, **명세·검증 시간은 거의 안 준다**
- 산정 단위를 "구현 시간"에서 **"검증 가능한 변경 단위 수"**로
- 추정/약속의 구분 (1-5)은 그대로 유효 — **약속의 단위는 인수 가능한 상태**다
- 주의: **낙관 편향이 심해진다.** "AI가 하면 금방이죠"가 새로운 압박이 된다

> **[KB 10] 공수 산정이 실제로 바뀌었는가 (2분)** ★ 회사 2 원문 질문
>
> "솔직히 저희는 AI 도입 이후에도 공수 산정 기준이 크게 바뀌지는 않았습니다. 아직은 과도기이고 회사마다 변화의 속도도 다른 것 같습니다. 상대적으로 작은 회사에서는 산정 기준 자체가 달라지고 있다는 이야기를 더 많이 듣습니다. 토스나 당근 같은 회사의 사례가 자주 언급되지만, 이것을 모든 조직에 동일하게 적용되는 공식적인 변화로 일반화하기는 어렵습니다.
>
> 저희는 은행이기 때문에 전체 일정에서 법무 검토와 보안 검토처럼 AI가 줄여주기 어려운 시간이 상대적으로 큽니다. 회의와 이해관계자 간 논의, 의사결정, 설계에 드는 시간도 아직은 크게 달라지지 않았습니다. 코드 작성이 빨라졌다고 해서 기능이 실제로 출시되기까지의 모든 단계가 같은 비율로 짧아지는 것은 아닙니다.
>
> 대신 같은 개발 일정 안에서 개선 작업을 함께 하는 경우가 늘어난 것 같습니다. 구현에 필요한 부담과 리소스가 줄어들면서 남는 시간에 기존 코드를 정리하거나 오픈소스 라이브러리 버전을 올리는 등의 개선을 더 많이 수행할 수 있게 됐습니다. AI의 효과가 마감일을 일률적으로 앞당겼다기보다, **같은 일정 안에서 구현과 함께 가져갈 수 있는 개선 작업의 양을 늘린 것**에 가깝습니다.
>
> 현재 회사 차원에서는 AI 효과를 확정된 생산성 계수보다 불확실성의 영역으로 다루는 느낌입니다. 공수를 산정할 때 'AI를 쓰니 일괄적으로 몇 퍼센트 줄인다'는 기준은 없고, 어떤 작업에서 AI가 얼마나 도움이 될지는 개발자의 개인 판단에 맡겨져 있습니다.
>
> 그래서 지금 단계의 제 답은 이렇습니다. **공식 산정 기준은 아직 크게 바뀌지 않았지만, 개발자가 같은 시간 안에 선택할 수 있는 작업의 포트폴리오는 이미 달라지고 있습니다.**"
>
> ⚠️ **최종 사실·공개 범위 검수:** 토스·당근의 공수 산정 변화는 구체적인 공개 근거가 확인되지 않으면 회사명을 빼고 "상대적으로 작은 조직에서 그런 이야기를 더 많이 듣는다"로 표현한다. 소속사의 공식 정책이 아니라 발표자가 체감한 현재 상태로 말한다.

### 3-2. Context — AI가 먹기 좋은 코드베이스 (7분)

**결론을 먼저 말한다.**
> 세션 2에서 말한 좋은 설계가 **그대로** AI에게 좋은 조건이다. AI를 위해 따로 할 일은 생각보다 적다.

| 사람에게 좋은 것 | AI에게 왜 좋은가                                    |
|------------------|-----------------------------------------------------|
| 명확한 모듈 경계 | 읽어야 할 범위가 좁아진다                           |
| 높은 응집성      | 한 곳만 고치면 된다                                 |
| **테스트**       | **AI가 스스로 채점할 수 있다 → 검증 비용이 싸진다** |
| 재현 가능한 환경 | 실행해보고 고칠 수 있다                             |
| 일관된 컨벤션    | 예시로부터 규칙을 추론한다                          |
| 정보 은닉        | 알 필요 없는 것을 안 읽는다                         |

세 번째가 3-1의 조건에 대한 답이다. **테스트는 AI 시대의 검증 비용을 낮추는 장치다.**

저는 AI 시대가 되면서 **TDD 같은 테스트 중심 방법론과 클린 아키텍처처럼 실수의 영향을 제한하는 구조가 오히려 더 가치 있게 느껴진다.** 이것들이 AI만을 위해 새로 생긴 방법론이어서가 아니다. AI가 만들어내는 코드와 변경의 양이 늘면서, 기존의 검증 기준과 아키텍처 경계가 더 큰 효과를 내기 때문이다.

- **TDD는 검증 기준을 먼저 준다.** AI가 구현을 시작하기 전에 기대 동작과 실패 조건을 테스트로 고정하면, AI는 실행 결과를 보고 스스로 수정할 수 있다. 여기서 TDD는 AI에게 구현을 맡긴 뒤 테스트도 많이 생성하게 한다는 뜻이 아니다. **무엇이 맞는지를 먼저 정의해 피드백 루프를 짧게 만드는 것**이 핵심이다.
- **클린 아키텍처는 실수가 번질 범위를 제한한다.** 의존 방향과 도메인 경계가 분명하면 AI가 읽고 수정해야 할 범위가 좁아진다. 잘못된 변경이 생겨도 한 모듈이나 어댑터 안에 머물 가능성이 커서 발견하고 리뷰하고 되돌리기 쉽다. 핵심은 계층을 많이 만드는 것이 아니라 **AI의 실수가 시스템 전체로 전파되지 않게 경계를 두는 것**이다.

> AI가 코드를 더 많이 만들수록 **TDD는 무엇이 정답인지 알려주고, 클린 아키텍처는 틀렸을 때 어디까지 망가질 수 있는지를 제한한다.**

**시프트 레프트가 더 중요해진다** (구글 1.2)

문제를 개발 후반이 아니라 **작성·리뷰·빌드 단계**에서 발견하는 것. AI가 생성량을 늘리면 후반 검증은 즉시 포화된다. 앞단으로 옮기는 것 말고 방법이 없다.

**추가로 필요한 것 (AI 전용)**

- 저장소 루트의 규칙 파일 (`CLAUDE.md` / `AGENTS.md`): 빌드·테스트 명령, 컨벤션, 하지 말 것
- **한 줄로 실행되는 테스트/린트 명령** — 없으면 에이전트는 검증하지 못한다
- 디렉터리별 README, 타입/스키마, 시드 데이터, 로컬 도커 환경
- **문서를 코드 옆에 두고 코드처럼 버전 관리** (구글 3.3) — 낡은 문서는 사람보다 AI를 더 크게 오도한다

> **[KB 6 다시 호출] AI는 문서화를 싸게 만들었지만 SSOT 문제를 없애지 않았다**
> 파편화된 Wiki·Jira·기획 문서를 AI가 모아줄 수는 있지만, 낡거나 충돌하는 정보까지 그럴듯하게 합칠 수 있다. 실행 가능한 사실은 코드와 테스트를 기준으로 하고, 결정 이유와 도메인 맥락은 책임 있게 관리되는 중앙 문서로 보완한다.

**반대로 AI를 가장 방해하는 것:** 거대한 함수, 암묵적 전역 상태, 실행할 수 없는 로컬 환경, 실패하는 기존 테스트, "이건 원래 이래" 지식이 사람 머리에만 있는 코드.

> **레거시일수록 AI 효과가 낮다는 사실을 솔직히 말한다.** "AI 넣으면 해결된다"는 기대는 조정이 필요하다. 오히려 **세션 2를 먼저 하는 것이 AI 도입의 준비다.**

> **[토스] 좋은 MCP는 데이터 연결이 아니라 맥락 설계다** — 회사 2의 "AI가 먹는 코드베이스" 질문에 직결
> **사내 Swagger MCP:** 전체 문서를 한 번에 주입하지 않고 `서비스 목록 → API 목록 → 상세 명세 → 컴포넌트` 순으로 **단계적으로** 조회하게 설계. 토큰 초과 문제는 미사용 API 제거·정보 가공·페이징으로 해결. LLM이 툴을 잘 호출하지 않는 문제는 MCP Prompt로 보완.
> **보안 취약점 분석:** `tree-sitter`·`ctags`·`ripgrep`으로 소스를 인덱싱하고 SourceCode Browse MCP로 **필요한 정의와 참조만 선택 조회**.
>
> **핵심 메시지:** MCP 자체보다 **원본 명세의 정확성·최신성·검색 단위**가 더 중요하다. 이건 곧 세션 2의 "문서를 코드처럼 관리한다"와 같은 얘기다.

> **[KB 11] AI가 먹기 좋게 하려고 실제로 정비한 것 (2분)** ★ 회사 2 원문 질문
>
> "개인적으로는 AI에게 모든 정보를 한 파일에 넣어주기보다 **필요한 정보를 필요할 때 찾아갈 수 있는 구조**를 만들려고 합니다. `.claude`에는 항상 적용돼야 하는 최소한의 정보만 둡니다. 반복해서 수행하는 절차는 Skill로 만들고, 분량이 있는 참고 문서는 `docs/` 폴더에 주제별로 나눠둔 뒤 README에서 인덱스와 링크를 제공합니다.
>
> 이렇게 하면 기본 컨텍스트가 불필요하게 커지지 않으면서도 AI가 작업에 필요한 문서를 선택해서 읽을 수 있습니다. 문서를 한곳에 모두 복사해 넣는 대신, 작은 규칙 파일과 재사용 가능한 Skill, 탐색 가능한 문서 인덱스로 역할을 나눈 것입니다.
>
> 최근 가장 기억에 남는 작은 규칙은 Claude가 선택지를 표시할 때 Unicode escape나 깨질 수 있는 특수 표현을 사용하지 않고 UTF-8 한글을 직접 사용하도록 한 프롬프트입니다. 아주 사소해 보이지만 한글 선택지가 깨지는 문제를 막아 매번 사람이 고치던 마찰을 없애줬습니다.
>
> AI가 먹기 좋은 환경을 만든다는 것이 반드시 거대한 코드베이스 개편을 뜻하지는 않습니다. **반복되는 지시는 Skill로, 긴 참고자료는 링크된 문서로, 항상 지켜야 할 최소 규칙만 기본 컨텍스트로 분리하는 것**부터 시작할 수 있습니다."
>
> ⚠️ **최종 공개 범위·표현 검수:** `.claude` 구성과 `docs/` 관리 방식의 공개 범위를 확인한다. 인코딩 규칙은 실제 프롬프트를 보고 "Unicode escape 금지"인지 "특수문자 사용 제한"인지 정확한 문구를 확정한다.

### 3-3. Execution — Harness · Tool · MCP를 누가 소유하나 (9분)

**구성요소 정리**

| 요소               | 역할                   | 스타트업에서의 현실        |
|--------------------|------------------------|----------------------------|
| 프롬프트/규칙 파일 | 조직의 맥락과 금지사항 | 가장 먼저, 가장 싸게 효과  |
| 툴 / 스킬          | 반복 작업의 절차화     | 두 번 이상 반복되면 만든다 |
| MCP 서버           | 사내 시스템 연결       | **읽기 전용부터**          |
| 서브에이전트       | 역할 분리              | 컨텍스트 분리 목적일 때만  |
| 훅 / CI 통합       | 사람이 안 잊게 강제    | 정착의 핵심                |

**소유 모델 3가지**

| 모델           | 장점                           | 단점                        | 적합 규모 |
|----------------|--------------------------------|-----------------------------|-----------|
| 전담 조직      | 일관성, 보안 통제              | 현장과 괴리, 병목           | 수백 명+  |
| 팀별 자율      | 실제 필요에 맞음, 빠름         | 중복, 품질 편차, 전파 안 됨 | 소규모    |
| **하이브리드** | 중앙은 가드레일, 팀은 워크플로 | 경계 합의 필요              | 대부분    |

> 10~30명 조직에 **전담 조직은 과하다.** 필요한 건 딱 두 개 — **명시적 오너 1명**과 **공용 저장소**.

> **[토스] 한 회사 안에 두 모델이 공존한다** ★★ 회사 2의 1순위 질문에 대한 공개 근거
> - **중앙형:** AI DX Team이 서버 개발용 Harness와 **사내 공용 Skill**을 만들어 배포한다
> - **현업형:** 토스페이먼츠 결제 MCP는 전담조직의 하향식 과제가 아니라 **여러 팀 사람이 모이는 길드의 작은 논의에서 시작**됐다
>
> **즉 "전담이냐 팀별이냐"는 양자택일이 아니다.** 중앙이 공통 기반과 기준을 만들고, 현업이 도메인 맥락과 평가 데이터를 소유하는 **혼합 구조**로 보는 게 공개 사례에 가장 부합한다.
> ⚠️ 다만 모든 Skill을 AI DX Team이 직접 만드는지는 공개 자료로 확인되지 않는다. **"토스는 이렇게 한다"가 아니라 "이런 사례가 공개돼 있다"로 말한다.**

> **[KB 12] Harness·MCP를 누가 만들고 어떻게 퍼뜨리는가 (3분)** ★★ 회사 2의 1순위 질문
>
> "제가 경험한 현재 방식은 중앙 조직이 모든 것을 정해서 내려보내기보다 **각 팀과 개발자가 필요한 것을 먼저 만들고, 좋은 것이 자연스럽게 확산되는 바텀업 방식**에 가깝습니다.
>
> 팀별로 MCP를 적극적으로 만들어 공유합니다. 예를 들어 저희는 데이터베이스에 `메타`라는 공용 사전과 같은 체계를 운영합니다. 이전에는 이 메타 정보를 다루기 위해 DBA와 논의하고 확인하는 과정의 허들이 굉장히 컸는데, 지금은 MCP를 통해 필요한 작업과 확인을 훨씬 쉽게 처리할 수 있습니다. 다른 팀이나 다른 업무 영역에 관한 질문도 사람에게 바로 문의하기보다 AI와 사내 도구를 통해 먼저 확인하는 경우가 많아졌고, 그 결과 문의와 답변에 드는 시간이 줄었습니다.
>
> `.claude` 같은 설정도 아직 회사 전체의 공통 규칙이 있다기보다 각 팀이 관리합니다. 좋은 프롬프트나 설정이 나오면 팀 안에서 먼저 공유하고, 효과가 있으면 사내로 자연스럽게 퍼집니다.
>
> 이를 돕는 사내 프롬프트·Skill 공유 사이트도 있습니다. 구성원들이 만든 프롬프트와 Skill을 올리고 좋아요를 누르거나 공유할 수 있습니다. 상위 랭크에 오른 사람에게 상품을 주는 등 회사도 적극적으로 참여를 장려하고 있고, 실제로 많은 Skill이 이곳에 공유됩니다. 강제 표준을 먼저 만드는 대신 **발견·평가·확산의 장터**를 제공하는 형태입니다.
>
> 사내 코드·문서 검색 도구도 비슷한 과정을 거쳤습니다. 처음에는 여러 개발자가 각자 필요한 도구를 만들었는데, 사용과 공유가 늘면서 서로의 작업이 합쳐졌고 현재는 공식 도구로 운영되고 있습니다. 처음부터 전사 프로젝트로 시작하지 않아도 현업의 반복 문제를 잘 풀면 공용 자산으로 성장할 수 있다는 사례입니다.
>
> 토스의 공개 사례에는 관리팀이 등장하지만, 저희는 아직 개별 개발자가 자신이 만든 도구를 관리하는 단계에 가깝습니다. 다만 저장소를 사내에 오픈소스처럼 공개하기 때문에 다른 개발자가 적극적으로 기여하고 함께 개선할 수 있습니다. 기여와 사용이 쌓인 도구들이 서로 합쳐지면서 공용 도구가 되는 경우가 있습니다.
>
> 이 방식에서 소유자는 처음부터 하나의 전담조직으로 고정되지 않습니다. 팀이 도메인에 필요한 MCP와 설정을 만들고, 사내 공유 공간이 확산을 돕고, 저장소가 열려 있어 다른 개발자가 기여하며, 널리 쓰이기 시작한 도구는 합쳐져 공식화됩니다. **개인이 만든 것 → 팀에서 검증한 것 → 사내 오픈소스처럼 기여받는 것 → 공용 도구로 합쳐진 것**이라는 경로입니다."
>
> 회사 2처럼 개발자가 8명인 조직에는 거대한 전담조직보다 **팀별 제작 + 공용 저장소나 공유 공간 + 널리 쓰이는 자산의 명시적 오너 지정**까지가 현실적인 대응이라고 연결한다.
>
> ⚠️ **최종 공개 범위 검수:** DB `메타` MCP, 프롬프트·Skill 공유 사이트의 랭킹과 보상, 사내 코드·문서 검색 도구가 공식화된 과정의 공개 범위를 발표 전에 확인한다. 현재는 발표자가 관찰한 운영 형태이며 회사 전체의 공식 AI 거버넌스로 일반화하지 않는다.

**확장 가능한 정책을 그대로 적용한다** (구글 1.2)

```text
"이 프롬프트 좋으니까 다들 쓰세요"   ← 개인의 기억에 의존. 안 퍼진다
        ↓
공용 레포의 규칙 파일로 표준화        ← 반복 가능한 절차
        ↓
훅 / CI에 넣어 자동 적용              ← 도구로 자동화
```

**제작·개선 절차 (경량)**

```text
개인이 만든다 → 본인 업무에서 2주 써본다 → 쓸만하면 공용 레포에 PR
→ 리뷰(보안 권한 범위 위주) → 공용 배포 → 사용 안 되면 폐기
```

무거운 승인 절차를 앞에 두면 아무도 안 만든다. **관문은 앞이 아니라 "공용화 시점"에 둔다.**

> **[토스] 팀의 워크플로를 설치 가능한 형태로 배포한다**
> 전사 공통 규정 / 도메인 지식 / 레포지토리 규칙을 **Global · Domain · Local 계층으로 분리**하고, 팀의 가이드와 워크플로를 플러그인·마켓플레이스 형태로 배포하자는 제안.
> ⚠️ **이 글은 확정된 전사 체계가 아니라 실무자가 제시한 방향성·가설이다.** 글 자체가 그렇게 밝히고 있으므로 반드시 그렇게 소개한다.
>
> 시사점: Harness 전파는 "프롬프트 모음 공유"가 아니라 **표준 업무 흐름을 설치 가능한 형태로 배포하는 것**이다.

**전파 방법**

- 공용 레포에 커밋해서 배포 (설치가 아니라 동기화가 되게)
- 문서보다 **실제 작업 시연 15분**이 훨씬 잘 퍼진다
- 사용 여부를 실제로 관측한다

**위험도별 권한 등급 = 베팅 한도 (table limit)**

카지노가 한 판의 손실을 제한하는 장치가 테이블 리밋이다. 에이전트 권한 등급이 정확히 같은 역할을 한다.

| 등급 | 권한                             | 검증           | 가역성                   |
|------|----------------------------------|----------------|--------------------------|
| 1    | 읽기 전용 (코드 검색, 문서)      | 불필요         | 완전 가역                |
| 2    | 격리된 작업공간에서 파일 수정    | 사람 리뷰      | 가역                     |
| 3    | 브랜치 푸시, PR 생성             | 리뷰 + CI 필수 | 가역                     |
| 4    | 스테이징 배포                    | 사람 승인      | 대체로 가역              |
| —    | **운영 DB 쓰기 / 운영 자격증명** | —              | **비가역 → 주지 않는다** |

> "격리 컨테이너냐 사람 눈이냐"는 양자택일이 아니다. **가역성에 따라 다르게** 하는 것이 답이다.
> 등급을 나누는 기준이 세션 2의 기준과 같다는 점을 강조한다.

> **[토스] AI 단독 판정을 피하고 결정적 도구와 결합한다**
> 보안 취약점 분석 사례에서 LLM이 **같은 입력에도 탐지 결과가 달라지는** 문제를 겪었고, LLM의 비결정적 판단만 믿지 않고 **Semgrep 같은 SAST 도구를 결합**했다. 소스 접근도 제한된 Tool 인터페이스로만 제공.
> → 고위험 영역에서는 **AI의 의미 판단 + 결정적 도구**의 조합이 안전하다. 권한 등급표와 같은 사고방식이다.

### 3-4. Verification — 품질과 책임 (9분)

**대원칙**

> **AI는 저자가 아니라 도구다. 머지 버튼을 누른 사람이 저자이고 책임자다.**

"AI 코드가 사고를 냈을 때 책임 소재"에 대한 답이 이것이다. 새로운 책임 체계가 필요한 게 아니라 **기존 체계가 그대로 적용된다.** 사후 프로세스도 세션 1의 비난 없는 포스트모템과 동일하되 질문 하나가
추가된다:

> "왜 이 코드가 우리 리뷰와 테스트를 통과했는가?"

AI 문제가 아니라 **검증 체계의 문제**로 다룬다.

**리뷰와 QA의 무게 이동**

```text
[전]  사람 리뷰가 1차 방어선
[후]  자동 검증이 1차,  사람은 자동화가 못 잡는 것에 집중
```

| 자동에 맡길 것   | 사람이 봐야 할 것             |
|------------------|-------------------------------|
| 포맷, 린트, 타입 | **설계 의도와 경계**          |
| 테스트 통과      | **도메인 규칙의 정확성**      |
| 커버리지, 중복   | **보안·권한·개인정보**        |
| 관습적 코드 스멜 | **운영 데이터에 미치는 영향** |
| 1차 AI 리뷰      | **비가역적 변경**             |

- 리뷰 **횟수**는 늘고 **깊이**는 좁아진다. QA는 줄지 않고 **탐색적 테스트 쪽으로 이동**한다
- AI 리뷰 에이전트: 누락 케이스·테스트 보완·일관성 위반에 강하고, **"이 도메인에서 이게 맞는가"에는 약하다**

> **[KB 5 다시 호출] 커밋 분리가 AI와 사람의 리뷰 영역을 나눈다**
> 리팩터링 커밋은 "기능이 달라졌는가"라는 비교적 결정 가능한 질문을 AI가 먼저 확인한다. 사람은 별도로 분리된 기능 커밋에서 비즈니스 의도와 도메인 규칙을 집중해서 본다. AI가 사람을 대체한 것이 아니라, **변경 유형을 분리해 각자 잘하는 검증을 맡긴 사례**다.

**테스트를 잘 쓰는 법이 더 중요해진다** (구글 3.4~3.6)

AI가 테스트를 대량 생성할 수 있게 되면서 **나쁜 테스트도 대량 생성된다.** 기준을 팀이 갖고 있어야 한다.

좋은 테스트의 조건:

- **구현 내부가 아니라 공개된 동작**을 검증한다
- 개별 메서드보다 **의미 있는 행동**을 테스트한다
- 호출 순서보다 **최종 상태**를 검증한다
- 테스트 안에 복잡한 조건과 반복문을 넣지 않는다
- **내부 리팩터링만으로 쉽게 깨지지 않는다**

**테스트에서는 DRY보다 DAMP** — 약간의 반복을 허용하더라도 각 테스트가 자체적으로 읽히게 한다. 지나치게 공통화된 테스트는 읽는 사람이 헬퍼를 오가며 상황을 재구성하게 만든다.

**테스트 대역은 신중하게**

```text
실제 구현 → (안 되면) 페이크 → (제한적으로) 스텁 → (꼭 필요할 때) 목
```

목을 과도하게 쓰면 테스트가 구현 세부에 결합돼 **리팩터링할 때마다 깨진다.**

**무엇을 측정할 것인가**

모델 벤치마크 점수는 조직에 의미가 없다. **워크플로 결과 지표**를 본다.

| 관점 | 지표                                    |
|------|-----------------------------------------|
| 품질 | 재작업률, 롤백률, 리뷰 지적 수          |
| 속도 | PR 리드타임, 첫 리뷰까지 시간           |
| 채택 | **주간 실제 사용률** (가장 정직한 지표) |
| 만족 | 정기 설문                               |
| 비용 | 토큰 비용 / 절약된 시간                 |

측정의 순서 (구글 2.7): `목적 정의 → 신호 선택 → 지표 설계 → 타당성 검증 → 개선 후 추적`

**Eval은 AI 기능을 위한 테스트 코드다**

코드를 수정한 뒤 같은 테스트를 다시 돌리듯, 프롬프트·Skill·MCP를 바꿀 때도 **같은 업무 문제를 다시 풀리고 결과를 비교**해야 한다. 한 번의 데모에서 답이 잘 나왔다는 사실만으로는 AI 기능이 좋아졌는지 알 수 없다.

```text
목적 정의 → 실제 업무를 닮은 시험 문제 준비 → 채점 기준 정의
→ 코드·사람·LLM으로 채점 → 변경 전후 결과 비교
```

- **규칙·코드 테스트:** 형식이 맞는가, 금지 항목이 있는가, 실제로 실행되는가
- **사람 평가:** 업무 의도와 도메인 기준에 맞는가
- **LLM 평가:** 의미, 문체, 가독성처럼 코드로 표현하기 어려운 기준을 만족하는가

> **예: AI가 장애 보고서를 작성한다면**
>
> 설명을 위한 가상 사례로, 실제 장애와 비슷한 입력 20개를 고정해둔다. 각 입력에는 장애 로그와 타임라인을 주고 AI가 보고서를 작성하게 한다.
>
> - 원인·영향·조치 항목이 모두 있는지, 개인정보가 포함되지 않았는지는 **코드로 검사**한다.
> - 원인을 정확히 설명하는지, 처음 읽는 사람도 이해할 수 있는지는 **사람이나 LLM이 평가**한다.
> - 작성 시간과 토큰 비용도 함께 기록한다.
> - 프롬프트를 수정하면 동일한 20개를 다시 실행해 변경 전후 점수를 비교한다.
>
> 새 프롬프트가 우연히 한 문제를 잘 푼 것이 아니라, **전체 사례에서 더 좋아졌고 기존에 잘하던 것도 망가뜨리지 않았는지** 확인하는 것이 Eval이다.

> **[토스] Eval을 실제로 어떻게 설계했는가** ★ 회사 2의 "판단 기준" 질문에 직결
>
> **① Skill 품질 평가표** — Skill은 AI가 반복 업무를 수행할 때 따르는 **업무 매뉴얼**이다. 사내에 Skill이 많이 만들어졌지만 **필요할 때 잘 호출되지 않거나 효과가 없는 문제**가 있었다. 그래서 만든 체계:
> - 6개 섹션 30개 항목 (타당성 · 구조 · 트리거 · 콘텐츠 · 리소스 · 안전성)
> - 정답이 명확한 17개는 **코드로 검사**하고, 의미 판단이 필요한 13개는 **LLM으로 평가**
> - BLOCKER · MAJOR · MINOR 심각도 + S~F 등급. **BLOCKER 하나면 배포 불가**
> - **저비용 규칙 검사를 먼저 돌리고, 통과한 것만 비싼 모델 검사로** 넘긴다
>
> **② 같은 문제로 대조 실험** — MCP는 AI가 결제 명세 같은 **사내 정보와 도구를 조회하는 연결 방식**이다. 토스페이먼츠는 같은 결제 연동 문제를 세 조건에서 비교했다: `AI 코딩 도구만 사용` / `일반 문서 제공` / `MCP 연결`.
>
> **두 가지 시사점:**
> - Eval은 최종 출력 품질만이 아니라 **호출 가능성 · 구조 · 안전성 · 배포 가능성**을 함께 본다. "만들었는데 안 불린다"가 실제 문제였다
> - 효과 측정은 만족도 조사보다 **실제 업무 시나리오로 대조군을 비교**하는 게 설득력 있다. 스타트업도 바로 흉내 낼 수 있는 방법이다

> **단일 지표로 생산성을 재면 행동이 왜곡된다.** "AI 사용률"을 KPI로 걸면 사용률만 오른다. 수치에는 설문·인터뷰 같은 정성적 맥락이 함께 필요하다.

**폐기도 엔지니어링이다** (구글 3.7)

계속 쓰이는 것과 버려진 것의 차이는 대체로 하나다:
> **기존 업무 흐름 안에 있느냐, 별도로 열어야 하느냐.**

- 살아남는 것: PR에 자동으로 붙는 것, CI에 들어간 것, 이미 쓰는 도구 안에 있는 것
- 죽는 것: 별도 사이트, 별도 명령어, "쓰라고 공지한 것"

> **[토스] 좋은 Skill도 업무 흐름 밖에 있으면 안 쓰인다** ★★ 회사 2의 "폐기한 시스템" 질문에 대한 최적의 공개 사례
> Technical Writer들의 문서 작성·리뷰 원칙을 Skill로 만들었는데 **기대만큼 쓰이지 않았다.** 이유는 모델이나 프롬프트가 아니었다 — 사용자가 **직접 설치·업데이트하고, 문서 작성 시점을 스스로 떠올리고, 필요한 자료를 찾아 넣어야** 했기 때문이다.
>
> 그래서 전달 방식을 바꿨다:
> - 사내 **메신저**에서 대화 맥락을 찾아 문서 초안을 만드는 챗봇
> - 문서 PR이 열리면 **GitHub Actions에서 자동 시작**되는 AI 리뷰
>
> **핵심:** 완전히 폐기한 게 아니라 **원인을 찾아 전달 방식을 바꾼** 사례다. 사용률이 낮을 때 모델부터 고치지 말고 **설치·호출·맥락 수집의 마찰**을 먼저 본다.

안전한 폐기: `대체 수단 제공 → 사용처 파악 → 마이그레이션 일정 → 이전 방식 차단 → 잔여 제거`
**새로 만들 때부터 폐기할 방법을 생각한다.**

> **[토스] AI 문서의 책임·갱신·폐기** — "AI가 만든 문서를 누가 책임지나" 질문에 직결
> 문서 생성이 쉬워지자 **비슷한 문서가 쌓이고, AI가 낡은 정책을 근거로 틀린 답을 내는** 문제가 생겼다. 도구는 "어떤 문서를 믿을지, 누가 책임질지, 언제 폐기할지"를 대신 정해주지 않는다.
> - 반복 질문 · 중요 의사결정 · 신규 입사자가 알아야 할 것만 조직 지식으로 남긴다
> - **책임자와 검토 주기를 지정**해 최신성을 유지한다
> - Knowledge Committee가 전사 공통 기준을 정의하고, **각 도메인이 자기 영역의 책임자·갱신·폐기를 결정**한다
>
> **핵심:** AI 생성물의 품질 책임은 **"AI가 썼는가"가 아니라 "신뢰할 기준 문서가 무엇이고 담당자와 검토 주기가 정해졌는가"**의 문제다. 세션 1의 "낡은 문서가 더 위험하다"가 AI 시대에 더 심각해진 것.

- [경험 슬롯 ⑦] AI 검수 에이전트를 실제로 쓴 사례 — 잘된 것과 안 된 것 **둘 다**

>
> "AI 도구는 공식적으로 폐기 결정을 내리기보다 개인이나 팀이 만들어 잠깐 사용하다가 조용히 사라지는 사례가 정말 많습니다. 특정 실패 도구 하나를 꼽기 어려울 정도로 생성과 소멸이 빠릅니다.

>
> 제가 관찰한 차이는 **설정의 크기보다 지속적으로 관리할 사람이 있는지, 실제 업무에서 반복해서 호출되는지, 다른 사람이 기여할 수 있는 구조인지**에 있습니다. 만들어놓고 사용자가 기억해서 찾아와야 하는 개인 도구는 조용히 사라지기 쉽습니다. 실제 문제를 계속 해결하고 저장소가 열려 있는 도구는 개인 관리로 시작해도 공동 자산으로 성장할 수 있습니다."
>
> ⚠️ **최종 공개 범위·표현 검수:** 사내 Harness·spec-driven development의 현재 분위기와 코드·문서 검색 도구의 공식화 과정을 발표 전에 확인한다. 이것은 전사 통계나 공식 방향이 아니라 발표자가 주변에서 관찰한 흐름으로 말한다.

### 3-5. Feedback — 직군 경계와 협업 (5분)

# 질의응답 설계 — 즉석 5분 × 3 + 커피챗 45분

슬라이드가 한 벌이므로, **질의응답이 두 강연을 다르게 만드는 전부다.** 이번 타임테이블에서는 그 시간이 두 종류로 나뉜다.

|                 | 즉석 질의응답 (5분 × 3)    | 커피챗 · 질의응답 (45분) |
|-----------------|----------------------------|--------------------------|
| 목적            | **질문 수집**              | 질문 소진 + 깊은 대화    |
| 받을 수 있는 양 | 2~3개                      | 10~15개                  |
| 성격            | 방금 들은 내용의 즉시 확인 | 회사 맥락에 붙은 질문    |
| 발표자의 태도   | 짧게 답하고 **적어둔다**   | 시간을 들여 답한다       |

### 즉석 질의응답 5분 — 운영 규칙

5분에 완결하려 하면 오히려 망가진다. **목적을 "다 답하기"가 아니라 "질문을 수집하기"로 잡는다.**

1. **"두 개만 받겠습니다"라고 먼저 말한다.** 시간 관리 부담이 청중에게 넘어간다.
2. **길어질 질문은 그 자리에서 커피챗으로 넘긴다.** "이건 5분에 답하기 아까운 질문이라 이따 자세히 하겠습니다" — 무시가 아니라 승격으로 들린다.
3. **못 받은 질문은 반드시 메모한다.** 이름 또는 자리를 함께 적어두고 커피챗에서 먼저 찾아간다. 이게 신뢰를 만든다.
4. **질문이 안 나오면 발표자가 먼저 던진다.** "제가 자주 받는 질문은 이건데요" 로 하나 풀고 넘어간다. 침묵으로 5분을 쓰지 않는다.
5. 종이 쪽지나 슬랙 채널을 열어두면 **말하기 부담스러운 사람의 질문**이 나온다. 특히 대표가 있는 자리에서 효과가 크다.

**세션별로 나올 만한 즉석 질문 (미리 답을 준비해둘 것)**

| 세션 | 예상 질문                                     | 30초 답변                                                                   |
|------|-----------------------------------------------|-----------------------------------------------------------------------------|
| 1    | "그럼 아무것도 확신하면 안 되나요?"           | 확신을 버리라는 게 아니라 **틀렸을 때 인정할 조건을 미리 적자**는 것        |
| 1    | "저희는 문서 쓸 시간이 없는데요"              | 그래서 **5줄 템플릿**입니다. 유지 못 할 문서는 안 만드는 게 낫습니다        |
| 2    | "가역/비가역을 누가 판단하나요?"              | 대부분 명확합니다. 애매하면 **되돌리는 데 며칠 걸리는지** 물어보면 갈립니다 |
| 2    | "그리디로 가면 나중에 다 갚아야 하지 않나요?" | 저금리면 안 갚아도 됩니다. **이자율을 재보는 게 먼저**입니다                |
| 3    | "AI가 개발자를 대체하나요?"                   | 병목이 작성에서 **검증**으로 옮겨간 것. 판단하는 사람은 더 필요해집니다     |
| 3    | "저희는 뭐부터 도입해야 하나요?"              | 도구보다 **한 줄로 도는 테스트 명령**이 먼저입니다                          |

### 커피챗 45분 — 진행 구조

5명·12명 규모에서는 소그룹으로 쪼갤 필요가 없다. **전체가 곧 커피챗이다.**

| 시각        | 구성                           | 내용                                                                                  |
|-------------|--------------------------------|---------------------------------------------------------------------------------------|
| 12:00~12:05 | 열기                           | 오프닝(O-3)에서 받은 관심사 + 세션 중 못 받은 질문을 **화면이나 화이트보드에 띄운다** |
| 12:05~12:33 | 전체 질의응답                  | 수집한 질문 → 사전 질문 → 현장 질문 순                                                |
| 12:33~12:42 | **"내일 할 수 있는 것 3가지"** | 흩어지기 전에 전체를 향해 한 번                                                       |
| 12:42~12:45 | 개별 대화 · 마무리             | 자료 공유, 연락처                                                                     |

**핵심 장치: 오프닝에서 받은 관심사 목록을 여기서 하나씩 지운다.**

O-3에서 한 마디씩 받아 적어둔 것을 화이트보드에 남겨두고, 커피챗에서 답할 때마다 지운다. 소규모 강연에서 가장 효과가 큰 장치다.

- 청중은 **자기 질문이 실제로 처리되는 것**을 눈으로 본다
- 발표자는 남은 시간과 남은 질문을 동시에 관리할 수 있다
- 다 못 지웠다면 그것 자체가 정직한 마무리다 — "이 두 개는 오늘 못 다뤘는데 자료에 답을 적어 보내드리겠습니다"

**12:33에 마무리 메시지를 넣는 이유:** 시간이 다 되면 이미 절반이 짐을 싸고 있다. 전체를 향해 말할 마지막 기회를 앞당긴다.

**대표·사업부장이 있는 커피챗의 특징**

- 개발자가 대표 앞에서 못 하는 질문, 대표가 개발자 앞에서 못 하는 질문이 **둘 다 나오지 않을 수 있다.** 이게 소규모의 함정이다
- 그래서 **발표자가 대신 물어주는 게 낫다.** "제가 자주 받는 질문인데요, 보통 이런 걸 궁금해하시더라고요" 로 민감한 주제를 꺼낸다
- 예: 일정 압박 상황에서 품질을 어디까지 양보하는가 / 부채 상환에 예산을 어떻게 배정하는가 / AI 도입 효과를 어떻게 보고하는가
- 조직 진단 요청이 들어오면 아래 "범위 밖 질문의 처리 문법"으로 일관되게

### 범위 밖 질문의 처리 문법

> "그건 제가 여러분 시스템을 봐야 답할 수 있는데, 제가 아는 **일반적인 판단 기준**은 이렇습니다. 이 기준으로 보시면 어떨까요."

정답 대신 **판단 기준**을 주는 것으로 일관되게 처리한다. 커피챗의 개별 대화에서 특히 자주 필요하다.

조심할 유형:

- 특정 기업의 비공개 정책 → 공개 범위만. 개인 경험은 소속사 공식 입장과 명확히 구분
- 즉석 진단 요청 → 기준으로 되돌린다
- "판교에서는?" → 방식이 아니라 **그 방식이 푸는 문제**로 답한다

```text
❌ "토스는 이렇게 합니다"
✅ "토스 기술블로그에 이런 사례가 공개돼 있는데요"
✅ "토스의 어느 팀이 이런 걸 공개했습니다"
```

토스 자료 자체가 **전사 운영 / 특정 팀 사례 / 작성자의 방향성 제안**을 구분하고 있다. ⚠️ 표시된 것은 확정된 체계가 아니라 제안이므로 그렇게 소개한다.

**두 개만 외운다면**

1. **Technical Writing Skill이 안 쓰인 이야기** — "폐기한 시스템 있나요"의 완벽한 답이고, 원인이 모델이 아니라 **설치·호출의 마찰**이었다는 게 핵심 교훈이다
2. **Skill 품질 Rubric** — "Eval 어떻게 하나요"의 답. 특히 **저비용 규칙 검사를 먼저 돌리고 통과한 것만 모델 검사로** 넘긴다는 설계는 스타트업도 바로 흉내 낼 수 있다

**해결됨**

- ~~회사별 자료·진행 차별화~~ → **하지 않는다.** 완전히 동일하게 진행하고 커피챗 현장 대응으로만
- ~~`f = g + h` 수식 노출~~ → **노출하지 않는다.** 회사 1은 청중의 40%가 비개발 직군
- ~~세션 내 질문 운용~~ → **세션 중에도 받는다.** 10명 이하라 미루는 게 오히려 부자연스럽다
- ~~시연 포함 여부~~ → **넣지 않는다.** 40분에 시연을 넣을 여유가 없다

**당일 현장 판단**

1. **KB 슬롯을 몇 개나 쓸지** — 준비된 것만. 시간이 밀리면 ★★와 ★만 하고 나머지는 커피챗으로
2. **경험 슬롯 ①~⑦** — 못 채운 자리는 `[KB]` 슬롯이나 공개 사례로 대체 가능. 비워둬도 슬라이드는 성립한다
3. **회사 1에서 슬라이드를 다 못 넘길 가능성** — 5명이면 대화가 길어진다. **대화를 우선한다.** 못 넘긴 부분은 자료를 공유하는 것으로 갈음
4. **카지노 훅의 수위** — 대표·사업부장 앞이다. "카지노형 vs 도박꾼형 조직"으로 프레이밍해 조직 진단이 아닌 자기 점검으로 읽히게 했다. 분위기를 보고 조절
5. **장소·화이트보드** — O-3에서 관심사를 적어두는 데 쓴다. 없으면 A4 한 장에 적어 들고 있어도 된다

**끝나고 할 것**

- 커피챗에서 다 못 지운 질문 → 자료와 함께 답을 정리해서 전달
- 답을 피한 질문 중 **공개 가능한 범위로 다시 정리할 수 있는 것**이 있으면 후속 공유
