# 부산 스타트업 강연 구성 초안 v0.2

> 3개 세션 × 45분 + 질의응답 60분. 두 회사 **동일한 자료**로 발표하고, 차별화는 질의응답에서만 한다.

**v0.2 변경점:** 카지노의 세 가지 우위를 전체 관통 축으로 도입. 세션 2를 "개발자의 시간을 어디에 배분할 것인가"로 재정의(자본 배분·촉매·그리디/A\* 신설). 세션 3에 세 우위 연결.

## 0. 전체 설계

### 0.1 전체를 관통하는 축

세 세션을 따로 노는 3개 강연이 아니라, **하나의 프레임을 세 층위에서 반복**하는 구조로 잡는다.

```text
                    확률의 우위 · 절제의 우위 · 자금의 우위
                                    │
   세션 1  ─────────────────────────┼───────────────────────  판단의 기준
           카지노는 어떻게 돈을 버는가              (마음가짐)
                                    │
   세션 2  ─────────────────────────┼───────────────────────  기준의 적용
           내 시간을 어디에 배분할 것인가           (자본 배분)
                                    │
   세션 3  ─────────────────────────┼───────────────────────  기준의 재검증
           AI는 이 세 우위를 어떻게 바꾸는가        (지형 변화)
```

**보조 축 하나가 세션 2와 3을 잇는다.**
> "AI가 먹기 좋은 코드베이스는 사람이 일하기 좋은 코드베이스와 같다."

### 0.3 두 회사 모두 동일한 자료로 진행한다

**확정 사항:** 슬라이드는 한 벌만 만든다. **차별화는 질의응답에서만 한다.**

이 결정이 자료 설계에 주는 제약 3가지:

1. **어느 세션도 줄일 수 없다.** 각 세션이 단독으로 성립해야 한다.
2. **한쪽에만 유효한 결론을 넣지 않는다.** "여러분 규모에서는 X를 하세요" 대신 **판단 기준**만 제시한다.
3. **각 세션에 다른 쪽 청중을 위한 연결 고리를 심는다.**

| 세션 | 회사 1 청중에게 | 회사 2 청중에게 |
|---|---|---|
| 1. 마음가짐 | 공통 | 공통 |
| 2. 좋은 소프트웨어 | 부채·관측·조직 운영의 직접 답 | **AI 도입의 전제 조건** |
| 3. AI 시대 | **부채 정리가 왜 AI 도입의 선행 조건인지** | Harness·Eval·책임의 직접 답 |

### 0.4 오프닝에서 반드시 할 말 (2분)

> "오늘은 여러분 회사의 시스템을 진단하고 최적안을 드리는 자리가 아닙니다. 8년 차 백엔드 개발자가 겪은 것, 그리고 공개된 기업 사례를 공유하는 자리입니다. 무엇을 가져갈지는 여러분이 정하시면 됩니다."

## 세션 1. 엔지니어로서의 마음가짐 (45분)

> **한 문장:** 엔지니어링은 정답을 아는 일이 아니라, 불확실성 속에서 **반복적으로 베팅하는 일**이다. 그래서 카지노가 돈을 버는 원리가 그대로 적용된다.

**주 레퍼런스:** 월가아재 3공리·13가지 인지 오류(뼈대) + 클린 코더(행동 규범) + 구글(팀) + 모던 SW 엔지니어링(경험주의)

### 1-1. 오프닝 — 카지노는 어떻게 돈을 버는가 (8분) ★ 강연 전체의 훅

**룰렛 한 판을 본다.**

유럽식 룰렛에는 1~36과 0이 있다. 빨강에 걸면 37칸 중 18칸에서 이긴다.

```text
하우스 엣지 = 1 - (18/37 × 2) = 약 2.7%
```

> **카지노는 매 판 48.6%의 확률로 진다.** 절반 가까이 진다. 그런데 카지노는 망하지 않는다.

**왜 망하지 않는가 — 세 가지 우위**

| 우위 | 카지노가 하는 일 |
|---|---|
| **확률의 우위** | 2.7%. 작지만 **양수**이고, 모든 판에 동일하게 적용된다 |
| **절제의 우위** | 손님이 연승해도 규칙을 바꾸지 않는다. 그리고 **베팅 한도**를 둔다 |
| **자금의 우위** | 손님보다 자금이 압도적으로 크다. **확률이 드러날 때까지 계속 앉아 있을 수 있다** |

세 번째가 핵심이다. **겜블러의 파산(Gambler's Ruin)** — 자금이 유한한 쪽과 사실상 무한한 쪽이 반복해서 붙으면, 게임이 완전히 공정해도(50:50) 유한한 쪽이 결국 파산한다. 카지노는 여기에 확률 우위까지 얹고 있다.

> **카지노는 이기는 법을 아는 게 아니라, 지지 않고 계속 앉아 있는 법을 안다.**

**2.7%가 왜 그렇게 큰가 — 반복이 만드는 격차**

월 100만 원씩 40년간 투자했을 때:

| 연 수익률 | 40년 후 | 직전 대비 차이 |
|---:|---:|---:|
| 8% | 약 32억 | – |
| 10% | 약 55억 | +23억 |
| 12% | 약 97억 | +42억 |
| 14% | 약 171억 | +74억 |

8%와 14%의 차이는 약 139억이다. 매년 2%p가 네 번. **작은 우위 × 충분한 반복 = 큰 격차.**

**전환 — 우리 팀은 카지노인가 도박꾼인가**

개발 조직도 매일 베팅한다. 어떤 기술을 쓸지, 어디에 시간을 쓸지, 무엇을 먼저 고칠지.

| | 카지노형 조직 | 도박꾼형 조직 |
|---|---|---|
| **확률** | 이 선택이 왜 더 나은지 설명할 수 있다 | "요즘 이게 대세라서" |
| **절제** | 실패 조건과 롤백을 미리 정한다 | 안 되면 더 투입해서 만회한다 |
| **자금** | 작게 배포하고 여러 번 시도한다 | 6개월짜리 전면 재작성에 건다 |

> 오늘 세 세션은 이 세 우위를 각각 **판단(1) → 시간 배분(2) → AI 시대(3)** 에 적용해보는 순서로 진행합니다.

- [경험 슬롯 ①] 도박꾼처럼 베팅했다가 잃은 경험 1건. 실패담으로 시작하면 이후 3시간의 신뢰가 달라진다

### 1-2. 확률의 우위 — 결과가 아니라 기대값과 과정 (11분)

**승률이 아니라 기대값이다**

```text
기대값 = Σ(결과 × 발생 확률)
```

이익이 2, 손실이 1이면 손익분기 승률은 약 33%다. **승률 40%여도 양의 기대값일 수 있고, 승률 60%여도 음의 기대값일 수 있다.**

개발 버전으로 바꾸면:

| 선택 | 성공 확률 | 성공 시 이득 | 실패 시 손실 | 판단 |
|---|---|---|---|---|
| 이름 변경, 함수 추출 | 높음 | 작음 | **거의 0 (되돌리기 쉬움)** | 그냥 한다 |
| 새 라이브러리 도입 | 중간 | 중간 | 중간 | 작게 검증 |
| DB 스키마 변경 | 중간 | 큼 | **매우 큼 (되돌리기 어려움)** | 신중히 |
| 전면 재작성 | 낮음 | 큼 | **파산 수준** | 거의 하지 않는다 |

> 개발에서 기대값을 계산하는 실질적인 방법은 **실패했을 때 얼마나 되돌릴 수 있는가**를 보는 것이다. 이 기준은 세션 2에서 다시 나온다.

**결과와 실력을 분리한다**

동전 앞면을 10번 연속 맞힐 확률은 약 0.098%다. 하지만 1,000명이 시도하면 한 명은 나온다. **연속 성공은 실력의 증거가 아니다.**

- 장애가 안 났다고 좋은 설계였던 것이 아니다 (운일 수 있다)
- 장애가 났다고 나쁜 판단이었던 것도 아니다 (당시 정보로는 최선이었을 수 있다)

> **좋은 판단 뒤의 손실은 부끄러워할 일이 아니고, 나쁜 판단 뒤의 행운은 자랑할 일이 아니다.**

**비난 없는 장애 분석** (구글) — 질문을 바꾼다.

| 나쁜 질문 | 좋은 질문 |
|---|---|
| 누가 실수했는가? | 왜 이 실수가 장애까지 갈 수 있었는가? |
| | 시스템은 왜 이걸 미리 못 잡았는가? |
| | 피해를 제한할 장치가 있었는가? |

> **매매일지 = 포스트모템.** 결과가 아니라 **그때의 가정**을 적는다.

스타트업용 최소 템플릿 5줄: `무슨 일이 / 언제부터 언제까지 / 사용자 영향 / 왜 늦게 알았나 / 다음에 뭘 바꾼다`

**권위와 유행은 근거가 아니다**

```text
추측이나 권위  <  관찰 가능한 증거
```

- "마이크로서비스가 좋다", "이 프레임워크가 빠르다" → **우리 조직, 우리 트래픽에서 검증됐는가**
- 판교 대기업이 쓴다는 것은 근거가 아니다. 그건 **그들의 문제에 대한 답**이다
- 도구·방법론 평가의 두 질문: ① 더 빨리 **학습**하게 하는가 ② **복잡성**을 통제하게 하는가

- [경험 슬롯 ②] 실제 포스트모템 문서 한 장 (익명화)

### 1-3. 절제의 우위 — 아는 것과 하는 것은 다르다 (12분)

건강을 위해 운동해야 한다는 걸 **몰라서** 안 하는 사람은 없다. 개발도 같다. 테스트를 써야 한다는 걸 몰라서 안 쓰는 게 아니다.

> **투자 실력이 지식의 양이 아니듯, 개발 실력도 아는 것의 양이 아니다. 압박 속에서 그걸 행동으로 옮기는 능력까지 포함한다.**

**절제를 만드는 세 가지 — 개발자 버전**

| 월가아재 | 개발자 버전 |
|---|---|
| 체력 관리 | **지속 가능한 상태에서 코딩한다.** 피곤·불안·분노 상태에서 짠 코드는 내일 다시 짠다 (클린 코더 4장) |
| 도파민 관리 | 새 기술 도입의 흥분, 리팩터링의 연쇄, **몰입의 과신** |
| 타자화(일기) | **코드 리뷰 · 페어링 · 포스트모템 · ADR** — 자기 판단을 남의 눈으로 보게 하는 장치 |

세 번째가 특히 중요하다. 투자에서 일기를 쓰는 이유와 개발에서 리뷰를 받는 이유가 같다. **자신을 한 걸음 떨어져서 관찰하기 위해서다.**

- 그래서 **코드를 개인 소유물로 만들지 않는 것**은 문화 얘기이기 이전에 절제의 장치다
- 천재 신화 버리기: 완성될 때까지 숨기면 잘못된 방향을 늦게 발견한다
- 겸손·존중·신뢰: 사람이 아니라 코드와 아이디어를 비판한다

**엔지니어링이 도박이 되는 경계**

| 엔지니어링에 가까운 | 도박에 가까워지는 |
|---|---|
| 근거와 가정으로 기술을 선택한다 | 흥분과 소문으로 선택한다 |
| 실패 조건과 롤백을 미리 정한다 | 안 되면 더 투입해서 만회한다 |
| 작게 배포하고 결과를 합산한다 | 한 번의 대형 릴리스에 집착한다 |
| **안 하는 선택도 받아들인다** | 뭐라도 계속 고쳐야 마음이 놓인다 |
| 판단을 기록하고 복기한다 | 결과만 보고 정당화한다 |

**개발자가 특히 잘 걸리는 인지 오류 6가지**

| 오류 | 개발 현장에서의 모습 |
|---|---|
| **안전 착각** ★ | 위험한 걸 몇 번 했는데 안 터졌다 → 안전하다고 믿는다 |
| 확신 편향 | 내가 고른 기술의 장점 자료만 찾아본다 |
| 애착 편향 | 내가 짠 코드를 남의 코드보다 높게 평가한다. 그래서 못 지운다 |
| 현상유지 편향 | 이미 쓰고 있다는 이유로 계속 쓴다 |
| 손실회피 | 3개월 쓴 프로젝트를 접지 못한다 |
| 권위의존 | "구글도 이렇게 합니다" 로 논의를 끝낸다 |

**안전 착각을 특히 강조한다.** 개발자에게 가장 치명적이고, 세션 2로 이어지는 다리이기 때문이다.

```text
알람이 울렸다 → 서비스에는 영향이 없었다 → 임계치를 올린다
→ 또 울렸다 → 또 올린다 → "이건 원래 울리는 알람이야"
→ 실제로 무슨 일이 있었는지는 끝내 확인되지 않았다
```

> 손실이 없었다는 사실은 **그 판단이 안전했다는 증거가 아니다.** 수익이 났다는 사실과 의사결정이 옳았다는 평가는 분리해야 한다.

**현상유지 편향을 깨는 질문 하나**
> "지금 이걸 쓰고 있지 않다면, 오늘 새로 도입할 것인가?"

**목표는 무오류가 아니라 알아차림이다.** 편향을 없애는 건 불가능하다. 이름을 붙일 수 있게 되는 것이 1단계다.

- [경험 슬롯 ③] 안전 착각에 걸렸다가 결국 터진 사례

### 1-4. 자금의 우위 — 파산하지 않는 것이 먼저다 (8분)

확률적 우위가 있어도 **한 번의 실패로 퇴장하면 그 우위는 실현되지 않는다.**

승률 60%인 전략도 한 번에 전액을 걸면 40%로 끝난다. 나눠 걸면:

| 연속 시도 | 모두 실패할 확률 |
|---:|---:|
| 1회 | 40% |
| 2회 | 16% |
| 3회 | 6.4% |

> 핵심은 높은 승률에 대한 확신이 아니라 **우위가 드러날 때까지 살아남는 것**이다.

**개발에서의 베팅 사이즈**

| 자금 관리 개념 | 개발에서의 대응물 |
|---|---|
| 한 번에 전액을 걸지 않는다 | **작은 PR, 작은 배포** |
| 분할 매수 | 기능 플래그, 카나리, 단계적 출시 |
| 손절 라인을 미리 정한다 | 롤백 경로, 실패 판정 기준 |
| 베팅 한도(table limit) | 배포 단위 상한, 권한 등급 |
| 생활비와 투자금을 분리한다 | **핵심 경로와 실험을 분리한다** |

> 모던 SW 엔지니어링이 "작은 변경"을 강조하는 이유가 이것이다. 작은 변경은 **일정 관리 기법이 아니라 자금 관리 기법**이다. 한 번의 판단 오류로 잃을 수 있는 최대치를 제한한다.

**자연 수익률은 마이너스다**

훈련받지 않은 개인 투자자의 '자연 수익률'을 -10%로 가정하라는 경고가 있다. 개발자 버전:

> **아무 원칙 없이 개발하면 코드베이스는 유지되는 게 아니라 나빠진다. 엔트로피가 기본값이다.**

"일단 돌아가게 만들자"는 중립이 아니라 마이너스다. 그래서 **함부로 투자하지 않는 법을 먼저 배운다** → 개발 버전: 함부로 추상화하지 않는 법, 함부로 도입하지 않는 법.

**시드가 작을수록 극단적 위험을 택한다**

배고픈 새일수록 결과가 불확실한 먹이통을 고른다는 실험이 있다. 작지만 확실한 보상으로는 생존할 수 없을 때, 실패 가능성이 커도 큰 보상을 노리는 선택이 합리적으로 보인다.

> 스타트업이 "한 방에 뒤집을" 전면 재작성이나 최신 아키텍처 전환에 끌리는 이유가 여기 있을 수 있다. **조급함은 적절한 위험은 피하면서 극단적 위험을 택하게 만든다.**

이건 비난이 아니라 구조의 문제로 다뤄야 한다. 다만 알고 하는 것과 모르고 하는 것은 다르다.

### 1-5. 추정과 약속을 구분한다 (5분)

세션 1에서 **가장 즉시 써먹을 수 있는 블록.** 클린 코더 9·10장. 대표·PM이 참석한 자리라면 오늘의 하이라이트가 된다.

| 구분 | 의미 | 표현 |
|---|---|---|
| 추정 | 현재 정보에서의 가능성 분포 | "3~5일이 유력, 외부 API 이슈가 있으면 8일" |
| 약속 | 특정 시점까지 하겠다는 표명 | "수요일까지 A 범위를 인수 가능한 상태로" |

날짜 하나만 말하면 듣는 사람은 그것을 **약속으로 받아들인다.** 갈등의 대부분이 여기서 시작된다.


- 늦어지면 마감 당일이 아니라 **아는 즉시** 알린다
- **압박은 규율을 버릴 이유가 아니라 규율이 필요한 이유다**

- [경험 슬롯 ④] 일정 협상 사례. 거절했더니 오히려 신뢰가 올라간 경험

## 세션 2. 좋은 소프트웨어를 만들어 나가는 방법 (45분)

> **부제:** 개발자의 시간을 어디에 배분할 것인가
>
> **한 문장:** 좋은 소프트웨어는 변하지 않는 소프트웨어가 아니라 **변경 비용이 낮은** 소프트웨어다. 그리고 그 비용을 낮추는 일은 **자본 배분 문제**다.

**주 레퍼런스:** 투자 철학·초과수익(자본 배분) + 그리디/A\* + Tidy First(부채) + 모던 SW 엔지니어링(두 축) + 구글(프로세스)

### 2-1. 좋은 소프트웨어의 정의와 두 축 (4분)

```text
좋은 소프트웨어 엔지니어링
├─ 학습 최적화     : 반복 · 피드백 · 점진 · 경험 · 실험
└─ 복잡성 관리     : 모듈성 · 응집성 · 관심사 분리 · 정보 은닉 · 결합도
```

- 소프트웨어는 **생산이 아니라 설계**다. 계획 실행이 아니라 발견 과정이다
- 두 축은 서로를 강화한다: 좋은 설계 → 빠른 피드백 → 더 나은 설계
- 그런데 **이걸 안다고 해서 오늘 무엇을 할지가 정해지지는 않는다.** 그게 이 세션의 진짜 주제다

### 2-2. 시간은 자본이다 — 무엇에 투자할 것인가 (11분) ★ 신설

**"좋은가"는 질문이 아니다**

투자자는 "이 주식이 좋은가?"를 묻지 않는다. 답이 늘 "여러 이유로 좋다"라서 **매매로 이어지지 않기 때문이다.** 실제로 사려면 다른 질문에 답해야 한다.

> **"지금 이 순간에, 다른 종목이 아니라, 이 종목을 사야 하는 이유는 무엇인가?"**

개발자 버전:

> **"이번 스프린트에, 다른 작업이 아니라, 이 리팩터링을 해야 하는 이유는 무엇인가?"**

Tidy First의 "훗날 정리하기"가 백로그에서 영원히 실행되지 않는 이유가 정확히 이것이다. **"코드가 나쁘다"는 이 질문의 답이 아니다.** 언제나 참인 명제라서 시점을 특정하지 못한다.

**촉매(catalyst) — 가치는 저절로 실현되지 않는다**

투자에서 저평가를 발견하는 것과 그 가치가 실현되는 것은 별개다. 아무도 안 보는 주식은 싸게 살 수 있지만 10년간 싼 채로 있을 수 있다.

```text
좋은 투자 = 가치와 가격의 괴리
          + 그 괴리가 줄어들 계기(촉매)
          + 기다리는 동안의 비용을 감당할 수 있음
```

리팩터링도 똑같은 구조다.

```text
좋은 리팩터링 = 현재 구조가 만드는 마찰
              + 그 마찰을 실제로 겪을 예정된 변경(촉매)
              + 지금 멈춰도 되는 일정 여유
```

> **촉매 = 예정된 변경.** 앞으로 안 건드릴 코드는 아무리 더러워도 가치가 실현되지 않는다. Tidy First가 **변경 빈도**를 첫 판단 기준으로 두는 이유다.

**시간 포트폴리오 — 성격이 다른 네 자산**

| 자산 | 성격 | 수익이 나는 시점 |
|---|---|---|
| 기능 개발 | 직접 매출 | 즉시 |
| 구조 개선 | **옵션** | 다음 변경 때 |
| 관측·자동화 | **보험 + 정보** | 사고 시 / 지속적으로 |
| 학습 | **인적 자본** | 불확실, 장기 |

Kent Beck의 표현을 확장한 것이다 — 기능 변경 = 매출, 구조 변경 = 옵션. 여기에 관측(보험)과 학습(인적 자본)을 더한다.

- 100% 기능에만 쓰는 팀 → 현금흐름은 좋은데 **옵션이 없다.** 나중에 아무것도 선택할 수 없게 된다
- 100% 구조에 쓰는 팀 → **회수 시점이 오지 않는다**
- 관측에 0을 쓰는 팀 → 무슨 일이 일어나는지 모른 채 베팅한다

> 비율의 정답은 없다. 다만 **네 칸이 있다는 것을 알고 배분하는 것**과 기능 하나만 보는 것은 다르다.

**투자 논지(thesis)를 쓴다**

"코드가 더럽다"는 예산을 못 받는다. 투자 논지의 형식으로 쓴다.

```text
문제: 주문 상태 변경 시 5개 모듈을 함께 수정해야 한다
영향: 최근 3개 기능에서 각각 1~2일 추가 발생          ← 현재 비용
촉매: 환불 정책 기능이 다음 스프린트에 예정            ← 왜 지금인가
비용: 2일
회수: 향후 변경 2회 이내
틀렸다고 판단할 조건: 환불 기능이 취소되면 보류        ← 반증 조건
```

마지막 줄이 중요하다. **틀렸을 때 인정할 조건을 미리 적는 것**이 확신 편향에 대한 유일한 방어다.

**우리 팀의 알파는 어디에 있는가**

초과수익은 **시장의 비효율**에서 나온다. 남들이 다 하는 걸 그대로 하면 알파가 없다 — 이미 가격에 반영된 정보이기 때문이다.

> "판교가 이렇게 합니다"를 그대로 가져오는 것이 왜 위험한가. 그건 **그들의 비효율에 대한 답**이고, 이미 널리 알려진 정보다.

조직 안의 비효율 = **비용은 계속 나가는데 아무도 보고 있지 않은 곳**

- 매주 반복하는데 아무도 자동화하지 않은 수작업
- 모두가 참고 있는 마찰 (빌드 5분, 로컬 환경 세팅 반나절)
- 아무도 안 보는 지표, 아무도 안 읽는 로그
- "원래 이래요"라는 답이 돌아오는 것들

**효율성은 상대적이다.** 같은 코드베이스도 그 도메인을 오래 판 사람에게만 보이는 비효율이 있다. 경력의 가치가 여기 있다.

> 오늘 가져갈 질문 하나: **"우리 팀에서 비용은 계속 나가는데 아무도 보고 있지 않은 곳은 어디인가?"**

- [경험 슬롯 ⑤] 아무도 안 보던 비효율을 찾아 고친 사례. 효과를 숫자로

### 2-3. 그리디와 A\* — 언제 빠른 선택이 옳은가 (9분) ★ 신설

**두 알고리즘의 평가 함수**

```text
g(n) = 출발점에서 여기까지 실제로 든 비용
h(n) = 여기서 목표까지 남은 예상 비용

그리디 최우선 탐색 :  f = h(n)          목적지에 가까워 보이는 쪽으로
A*                :  f = g(n) + h(n)   여기까지 온 비용까지 포함해서
다익스트라         :  f = g(n)   (h=0)  전부 탐색
```

개발에서의 대응물:

| 모드 | 개발에서의 모습 | 특징 |
|---|---|---|
| 그리디 (h만) | "일단 되게 만들자" | 빠르다. 가끔 막다른 길 |
| A\* (g+h) | "여기까지 온 것까지 포함해 어느 쪽이 싼가" | 균형. 좋은 감이 있으면 강력 |
| 다익스트라 (h=0) | 전수 검토, 3주짜리 설계 회의 | 확실하지만 느리다 |

**스타트업은 그리디로 시작해도 된다**

> 0.1초에 응답하는 API 1개보다, **0.5초에 동작하는 API 3개**가 나을 수 있다.

목표 함수가 다르기 때문이다. 대기업의 `h(n)`은 대체로 "완성도까지 남은 거리"지만, 스타트업의 `h(n)`은 **"검증까지, 생존까지 남은 거리"**다. 같은 지도를 걷고 있지 않다.

같은 이유로 이런 선택들이 정당화된다.
- 캐시 대신 인덱스 하나
- 추상화 없이 복붙 두 번 (세 번째에 추출)
- 완벽한 도메인 모델 대신 동작하는 CRUD

**단, 그리디의 정의를 기억해야 한다**

> 그리디 알고리즘의 정의는 "매 순간 최선을 고른다"가 아니다. **"그 선택을 되돌리지 않는다"**까지가 정의다.

여기서 다음 블록과 만난다.

```text
되돌리기 쉬운 선택   → 그리디로 간다. 틀리면 되돌리면 된다.
되돌리기 어려운 선택 → 그리디를 쓰면 안 된다. 되돌릴 수 없으니까.
```

**그리디 선택 속성을 증명해야 한다**

알고리즘에서 그리디를 쓰려면 "지금의 최선이 전체의 최선으로 이어진다"를 **증명해야** 한다. 개발 버전:

> **"이 빠른 선택이 나중에 우리를 막다른 길로 몰지 않는다"를 설명할 수 있는가?**

설명할 수 있으면 그리디는 게으름이 아니라 전략이다. 설명할 수 없으면 그냥 도박이다.

**반례를 기억한다 — 동전 교환**

동전 단위가 `1, 3, 4`이고 `6`을 만들 때:

```text
그리디(큰 것부터):  4 + 1 + 1 = 3개
최적:              3 + 3     = 2개
```

한국 동전(500/100/50/10)에서는 그리디가 항상 최적이다. **그리디가 통하느냐는 문제의 구조에 달려 있지, 그리디 자체의 성질이 아니다.**

**g(n)과 매몰비용은 다르다**

A\*는 `g(n)`, 즉 **이미 쓴 비용**을 본다. 그런데 인간의 의사결정에서 이미 쓴 비용을 보는 건 매몰비용 오류다. 모순인가? 아니다.

| | 미래 비교에 유효한가 |
|---|---|
| A\*의 `g(n)` | **유효하다.** 이 경로로 계속 갔을 때의 총비용을 계산하는 데 쓰인다 |
| 매몰비용 | **무관하다.** 어떤 선택을 하든 회수되지 않는다 |

개발에서 헷갈리는 지점:

- ❌ "이미 3개월 썼으니 계속해야 한다" → 매몰비용 오류
- ✅ "이 경로면 총 6개월, 다른 경로는 지금부터 총 2개월" → 올바른 `g+h` 비교
- 구분 기준: **이미 만든 것이 자산으로 남는가.** 남으면 `g(n)`의 일부고, 폐기해야 하면 매몰비용이다

세션 1의 손실회피·애착 편향이 여기서 실제 비용으로 나타난다.

**휴리스틱의 품질이 탐색 비용을 정한다**

- `h(n)`이 실제에 가까울수록 **적게 탐색하고 정답에 도달**한다 → **좋은 감(感)은 탐색 비용을 줄인다.** 경력의 가치
- 단, `h(n)`이 실제 비용을 **과대평가하면 최적을 놓친다** → "그건 어려울 거야"라는 과대평가가 시도 자체를 막는다
- `h(n) = 0`이면 다익스트라가 된다 → **아무 감도 없으면 전부 탐색해야 한다.** 그래서 도메인 학습이 곧 속도다

### 2-4. 되돌리기 비용 — "미리 바꿔야 할 것"의 기준 (8분)

*"지금 할 것 / 나중에 해도 될 것 / 미리 바꿔야 할 것"* 에 정면으로 답하는 블록.

**Tidy First의 4분면**

| 선택 | 언제 | 예시 |
|---|---|---|
| **먼저** 정리 | 작은 정리가 지금 기능을 더 쉽고 안전하게 만든다 | 조건문을 가드 절로 바꾸고 분기 추가 |
| **나중에** 정리 | 구현해봐야 적절한 구조가 보인다 | 구현 후 드러난 중복 제거 |
| **훗날** 정리 | 가치는 있지만 **촉매가 없다** | 여러 모듈에 걸친 공통 구조 |
| **안 함** | 다시 안 바뀌거나 비용 대비 이득 없다 | 곧 폐기할 코드 |

```text
정리 비용 + 정리 후 개발 비용  <  지금 구조에서 바로 개발하는 비용
```

**되돌리기 비용이 유일한 기준이다**

| 되돌리기 쉬움 → 그냥 하라 (그리디 OK) | 되돌리기 어려움 → 미리, 신중히 |
|---|---|
| 이름 변경, 함수 추출/인라인 | **DB 스키마 변경** |
| 코드 이동, 순서 변경 | **외부 공개 API 계약** |
| 명시적 파라미터 도입 | **대규모 데이터 이전** |
| 죽은 코드 삭제 | **운영 데이터의 의미 변경** |

> 전자는 논의 대상이 아니라 그냥 하는 것. 후자만 설계 회의를 연다. **팀의 논의 시간이 전자에 쓰이고 있다면 그게 낭비다.**

이것이 1-2의 기대값 표, 2-3의 그리디 적용 조건과 같은 기준이다. 세 번 다른 언어로 말한 하나의 원칙이다.

**전담 인력 없이 하는 법**

- 시간 비율("스프린트의 20%")보다 **범위 제한**이 낫다: 이번 기능이 반드시 지나가는 코드만
- 몇 분 단위. **한 시간을 넘으면 범위가 커진 것**
- 구조 변경과 동작 변경을 **커밋/PR로 분리**한다

```text
refactor: 결제 조건을 guard clause로 정리
refactor: 금액 계산을 helper로 추출
feat: 부분 환불 조건 추가
```

리뷰어의 질문이 달라진다 — 구조 변경은 "동작이 그대로인가", 기능 변경은 "요구사항에 맞는가".

- **연쇄 작용 경계**: 정리하다 보면 계속 보인다. 이게 도파민이다(1-3). 다음 기능을 안전하게 만들 수 있으면 멈춘다

### 2-5. 관측 — 우리가 무엇을 모르는지 아는가 (9분)

관측은 **보험이자 정보**다. 기대값 계산의 입력값을 만드는 일이다.

**장애 대응 5단계**

```text
감지 → 완화 → 원인 → 재발 방지 → 기록
```

대부분의 팀이 `완화`에서 멈춘다. **"쿼리를 죽여서 해결했다"는 대응이지 개선이 아니다.**

**알람이 알람이 되려면**

자주 보는 패턴: 알람이 자주 울려서 임계치를 30 → 45 → 60으로 올린다.

> 임계치 상향 자체는 틀린 판단이 아니다. **액션 없는 알람은 알람이 아니라 소음**이므로. 문제는 세션 1에서 말한 **안전 착각**이다. 세 번 올리는 동안 "실제로 무슨 일이 있었는가"가 확인되지 않으면, 감도만 낮추고 위험은 그대로 남는다.

좋은 알람의 조건 3가지:
1. **액션 가능**해야 한다 — 울리면 할 일이 정해져 있다 (런북)
2. **사용자 영향** 기준이어야 한다 — CPU 98%보다 "응답 지연 p99 > 3초"
3. **원인이 아니라 증상**을 잡는다 — 원인은 대시보드에서 찾는다

**지표를 보는 순서**

```text
사용자 체감 (SLI: 지연/에러율)
        ↓ 무엇이 느린가
요청 단위 (RED: Rate · Error · Duration)
        ↓ 어디가 포화됐나
자원 단위 (USE: Utilization · Saturation · Error)
        ↓ 어떤 작업이 원인인가
개별 쿼리 / 대기 이벤트
```

DB 부하는 **CPU가 아니라 동시 실행 스레드와 DB Load**가 먼저 움직인다. "스레드 수 → 1분 뒤 DB Load → 종합 부하" 순으로 알람이 뜨는 건 전형적인 패턴이다.

**원인 쿼리를 빠르게 특정하는 일반적 방법**

| 문제 | 일반적 대응 |
|---|---|
| 사후에 어떤 쿼리였는지 모른다 | Slow query log 상시 활성 + Performance Insights 보존 |
| 누가 호출했는지 모른다 | **SQL 주석에 호출자를 심는다** (`/* app=api svc=campaign ep=/list */`) — 가장 저렴하고 효과 큰 한 수 |
| 긴 쿼리가 DB를 잡는다 | `max_execution_time` / statement timeout, 커넥션 풀 상한 |
| 배치가 서비스를 친다 | 읽기 전용 복제본으로 배치·통계 분리 |
| 반복 원인을 모른다 | 주간 Top SQL 리뷰 |

- [경험 슬롯 ⑥] 실제로 겪은 DB 장애 1건. **원인보다 "어떻게 알아냈는지"의 순서**를 보여준다

### 2-6. 복잡성과 조직 (4분, 압축 · 상세는 Q&A)

**거대한 조회 쿼리는 성능 문제이기 전에 설계 신호다**

40+ 컬럼, 10+ LEFT JOIN, GROUP_CONCAT, 상관 서브쿼리 →
> 화면 요구사항이 그대로 쿼리가 됐다 = **읽기 모델이 없다.**

- 본질적 복잡성(도메인) vs **우발적 복잡성**(구조 때문에 생긴 것) — 후자는 설계로 줄일 수 있다
- **테스트하기 어렵다 = 설계가 결합돼 있다는 신호.** 테스트 가능성은 설계 품질의 계측기다

**대기업 방식 중 무엇을 가져올까**

| 대기업 방식 | 해결하려는 문제 | 10~30명 조직의 대안 |
|---|---|---|
| 모노레포 + 코드 검색 | 사용처 파악 | 통합 검색 + 명확한 오너 |
| 정교한 리뷰 도구 | 빠른 피드백 | **작은 PR** + 리뷰 기준 + CI |
| 설계 문서 프로세스 | 결정의 맥락 보존 | **ADR 한 장** |
| 전사 테스트 인프라 | 변경 위험 조기 발견 | **핵심 경로부터** |
| 정식 포스트모템 | 재발 방지 | **5줄 템플릿** |
| 전담 QA 조직 | 다른 관점의 검증 | 인수 조건을 **개발 전에** 합의 |

- **지금은 안 해도 되는 것:** 아키텍처 리뷰 위원회, 전사 표준 문서, 정교한 공수 산정 프로세스
- **문서화 기준 한 줄:** 문서가 없는 것도 문제지만 **낡은 문서가 공식 정보처럼 남아 있는 게 더 위험하다**
- **PM/디자인이 어디까지?** → 화면 상세도가 아니라 **완료 조건(인수 조건)의 명확도**

**확장의 일반 원칙** (체크리스트만, 상세는 Q&A)
- 외부 API 연동(AI 모델 포함): 타임아웃 필수, 재시도는 멱등할 때만, 서킷 브레이커, 느린 작업은 큐
- 글로벌: 정적 자산은 CDN, 상태는 리전. 대부분의 체감 속도 문제는 리전이 아니라 **요청 수와 페이로드 크기**

## 세션 3. AI 시대의 기술 지형 변화와 대응 (45분)

> **한 문장:** 질문을 바꾼다. *"AI가 코드를 얼마나 잘 쓰는가"* 가 아니라 *"우리 조직이 AI에게 맥락·실행환경·검증·피드백을 얼마나 잘 주는가"*.

**프레임:** `Context → Execution → Verification → Feedback`

### 3-1. AI는 세 우위를 어떻게 바꾸는가 (8분) ★ 세션 1·2와 연결

**병목의 이동**

```text
[전]  요구사항 → 설계 → [코드 작성 ★병목] → 리뷰 → 배포
[후]  요구사항 → [맥락 정리 ★] → 코드 생성 → [검증/리뷰 ★★병목] → 배포
```

생성량은 늘었는데 **검토량은 사람 수만큼만 늘어난다.** 승부처는 "얼마나 잘 만드는가"가 아니라 **"얼마나 빨리 확신할 수 있는가"**다.

**세 우위로 다시 보면**

| 우위 | AI 이전 | AI 이후 |
|---|---|---|
| **확률** | 개발자의 판단력 | 판단력 + AI의 확률적 출력. **기대값 = 정확도 × 가치 − 검증 비용** |
| **자금** | 사람의 시간이 곧 베팅 사이즈 | **시도 비용이 급락 → 잘게 쪼개고 반복을 늘릴 수 있다** |
| **절제** | 압박 속에서 규율 유지 | **싸지니까 더 크게 걸고 싶어진다.** 안전 착각이 강해진다 |

**가장 중요한 한 줄**

> **AI 시대의 진짜 이득은 "빨라진 것"이 아니라 "시행 횟수를 늘릴 수 있게 된 것"이다.**

확률적 우위는 반복해야 드러난다(세션 1). 시도가 싸지면 반복이 늘고, 반복이 늘면 작은 우위가 실제 성과로 수렴한다.

**단, 조건이 있다.** 이 이득은 **검증도 함께 싸질 때만** 성립한다. 검증이 안 싸지면 생성만 늘고 병목만 커진다.
→ 그래서 다음 블록(테스트·재현 가능한 환경)이 AI 시대의 핵심 인프라가 된다.

**공수 산정은 어떻게 바뀌나**
- 초안 작성 시간은 크게 줄고, **명세·검증 시간은 거의 안 준다**
- 산정 단위를 "구현 시간"에서 **"검증 가능한 변경 단위 수"**로
- 추정/약속의 구분(1-5)은 그대로 유효 — AI가 5분에 초안을 만들어도 **약속의 단위는 인수 가능한 상태**다
- 주의: **낙관 편향이 심해진다.** "AI가 하면 금방이죠"가 새로운 압박이 된다

### 3-2. Context — AI가 먹기 좋은 코드베이스 (9분)

**결론을 먼저 말한다.**
> 세션 2에서 말한 좋은 설계가 **그대로** AI에게 좋은 조건이다. AI를 위해 따로 할 일은 생각보다 적다.

| 사람에게 좋은 것 | AI에게 왜 좋은가 |
|---|---|
| 명확한 모듈 경계 | 읽어야 할 범위가 좁아진다 |
| 높은 응집성 | 한 곳만 고치면 된다 |
| **테스트** | **AI가 스스로 채점할 수 있다 → 검증 비용이 싸진다** |
| 재현 가능한 환경 | 실행해보고 고칠 수 있다 |
| 일관된 컨벤션 | 예시로부터 규칙을 추론한다 |

세 번째가 3-1의 조건에 대한 답이다. **테스트는 AI 시대의 검증 비용을 낮추는 장치다.**

**추가로 필요한 것 (AI 전용)**
- 저장소 루트의 규칙 파일 (`CLAUDE.md` / `AGENTS.md`): 빌드·테스트 명령, 컨벤션, 하지 말 것
- **한 줄로 실행되는 테스트/린트 명령** — 없으면 에이전트는 검증하지 못한다
- 디렉터리별 README, 타입/스키마, 시드 데이터, 로컬 도커 환경
- 문서를 코드 옆에 두고 코드처럼 버전 관리

**반대로 AI를 가장 방해하는 것:** 거대한 함수, 암묵적 전역 상태, 실행할 수 없는 로컬 환경, 실패하는 기존 테스트, "이건 원래 이래" 지식이 사람 머리에만 있는 코드.

> **레거시일수록 AI 효과가 낮다는 사실을 솔직히 말한다.** "AI 넣으면 해결된다"는 기대는 조정이 필요하다. 오히려 **세션 2를 먼저 하는 것이 AI 도입의 준비다.**

### 3-3. Execution — Harness · Tool · MCP를 누가 소유하나 (10분)

**구성요소 정리**

| 요소 | 역할 | 스타트업에서의 현실 |
|---|---|---|
| 프롬프트/규칙 파일 | 조직의 맥락과 금지사항 | 가장 먼저, 가장 싸게 효과 |
| 툴 / 스킬 | 반복 작업의 절차화 | 두 번 이상 반복되면 만든다 |
| MCP 서버 | 사내 시스템 연결 | **읽기 전용부터** |
| 서브에이전트 | 역할 분리 | 컨텍스트 분리 목적일 때만 |
| 훅 / CI 통합 | 사람이 안 잊게 강제 | 정착의 핵심 |

**소유 모델 3가지**

| 모델 | 장점 | 단점 | 적합 규모 |
|---|---|---|---|
| 전담 조직 | 일관성, 보안 통제 | 현장과 괴리, 병목 | 수백 명+ |
| 팀별 자율 | 실제 필요에 맞음, 빠름 | 중복, 품질 편차, 전파 안 됨 | 소규모 |
| **하이브리드** | 중앙은 가드레일, 팀은 워크플로 | 경계 합의 필요 | 대부분 |

> 10~30명 조직에 **전담 조직은 과하다.** 필요한 건 딱 두 개 — **명시적 오너 1명**과 **공용 저장소**.

**제작·개선 절차 (경량)**
```text
개인이 만든다 → 본인 업무에서 2주 써본다 → 쓸만하면 공용 레포에 PR
→ 리뷰(보안 권한 범위 위주) → 공용 배포 → 사용 안 되면 폐기
```
무거운 승인 절차를 앞에 두면 아무도 안 만든다. **관문은 앞이 아니라 "공용화 시점"에 둔다.**

**전파 방법**
- 공용 레포에 커밋해서 배포 (설치가 아니라 동기화가 되게)
- 문서보다 **실제 작업 시연 15분**이 훨씬 잘 퍼진다
- 사용 여부를 실제로 관측한다

**위험도별 권한 등급 = 베팅 한도(table limit)**

카지노가 한 판의 손실을 제한하는 장치가 테이블 리밋이다. 에이전트 권한 등급이 정확히 같은 역할을 한다.

| 등급 | 권한 | 검증 |
|---|---|---|
| 1 | 읽기 전용 (코드 검색, 문서) | 불필요 |
| 2 | 격리된 작업공간에서 파일 수정 | 사람 리뷰 |
| 3 | 브랜치 푸시, PR 생성 | 리뷰 + CI 필수 |
| 4 | 스테이징 배포 | 사람 승인 |
| — | **운영 DB 쓰기 / 운영 자격증명** | 에이전트에게 주지 않는다 |

> "격리 컨테이너냐 사람 눈이냐"는 양자택일이 아니다. **위험도에 따라 다르게** 하는 것이 답이다. 대부분의 작업은 등급 2~3이고, 여기선 격리와 사람 리뷰를 **둘 다** 한다.

### 3-4. Verification — 품질과 책임 (10분)

**대원칙**

> **AI는 저자가 아니라 도구다. 머지 버튼을 누른 사람이 저자이고 책임자다.**

"AI 코드가 사고를 냈을 때 책임 소재"에 대한 답이 이것이다. 새로운 책임 체계가 필요한 게 아니라 **기존 체계가 그대로 적용된다.** 사후 프로세스도 세션 1의 비난 없는 포스트모템과 동일하되 질문 하나가 추가된다:

> "왜 이 코드가 우리 리뷰와 테스트를 통과했는가?"

AI 문제가 아니라 **검증 체계의 문제**로 다룬다.

**리뷰와 QA의 무게 이동**

```text
[전]  사람 리뷰가 1차 방어선
[후]  자동 검증이 1차,  사람은 자동화가 못 잡는 것에 집중
```

| 자동에 맡길 것 | 사람이 봐야 할 것 |
|---|---|
| 포맷, 린트, 타입 | **설계 의도와 경계** |
| 테스트 통과 | **도메인 규칙의 정확성** |
| 커버리지, 중복 | **보안·권한·개인정보** |
| 관습적 코드 스멜 | **운영 데이터에 미치는 영향** |
| 1차 AI 리뷰 | **되돌리기 어려운 변경** (2-4와 동일한 기준) |

- 리뷰 **횟수**는 늘고 리뷰 **깊이**는 좁아진다. QA는 줄지 않고 **탐색적 테스트 쪽으로 이동**한다
- AI 리뷰 에이전트: 누락 케이스·테스트 보완·일관성 위반에 강하고, **"이 도메인에서 이게 맞는가"에는 약하다**

- [경험 슬롯 ⑦] AI 검수 에이전트를 실제로 쓴 사례 — 잘된 것과 안 된 것 **둘 다**

**무엇을 측정할 것인가**

모델 벤치마크 점수는 조직에 의미가 없다. **워크플로 결과 지표**를 본다.

| 관점 | 지표 |
|---|---|
| 품질 | 재작업률, 롤백률, 리뷰 지적 수 |
| 속도 | PR 리드타임, 첫 리뷰까지 시간 |
| 채택 | **주간 실제 사용률** (가장 정직한 지표) |
| 만족 | 정기 설문 |
| 비용 | 토큰 비용 / 절약된 시간 |

> **단일 지표로 생산성을 재면 행동이 왜곡된다.** "AI 사용률"을 KPI로 걸면 사용률만 오른다.

**폐기도 엔지니어링이다**

계속 쓰이는 것과 버려진 것의 차이는 대체로 하나다:
> **기존 업무 흐름 안에 있느냐, 별도로 열어야 하느냐.**

- 살아남는 것: PR에 자동으로 붙는 것, CI에 들어간 것, 이미 쓰는 도구 안에 있는 것
- 죽는 것: 별도 사이트, 별도 명령어, "쓰라고 공지한 것"
- 여기서도 **현상유지 편향**이 작동한다 — 안 쓰는 걸 안 지우면 신뢰가 떨어진다

### 3-5. Feedback — 직군 경계와 협업 (6분)

**비개발 직군의 생산성을 위해 개발자가 할 수 있는 일**

도구를 사주는 게 아니라 **안전한 접근 경로를 만들어주는 것**이다.

| 개발자가 제공 | 효과 |
|---|---|
| 읽기 전용 데이터 뷰 / 사내 MCP | 마케팅·CS가 직접 질문 → 개발 요청 감소 |
| 반복 요청의 셀프서비스화 | 데이터 추출 요청이 사라진다 |
| 안전한 샌드박스 | 사고 없이 실험 가능 |
| 잘 쓰는 사람의 프롬프트 공유 | 직군 무관하게 가장 효과 큼 |

**Figma ↔ 구현 정확도**

솔직한 답: **도구 연동이 정확도를 만들지 않는다.**

```text
디자인 시스템이 없다        → AI가 픽셀을 추측한다      → 매번 다른 결과
디자인 토큰 + 명명된 컴포넌트 → AI는 "매핑"만 하면 된다  → 정확도 급상승
```

- 선행 조건: 디자인 토큰(색·간격·타이포), 컴포넌트 이름이 코드와 일치, 상태(hover/disabled/error) 정의
- **투자 순서는 연동이 아니라 디자인 시스템이 먼저**
- 웹/Flutter/네이티브를 한 번에 노리기보다 **한 플랫폼에서 컴포넌트 10개로 검증**하고 넓힌다

**경계는 흐려지는가**
- 흐려진다. 다만 **"할 수 있는 것"의 경계**가 흐려지는 것이고, **"책임지는 것"의 경계는 그대로**다
- 개발자의 역할은 축소가 아니라 **판단과 검증 쪽으로 이동**한다

### 3-6. 마무리 — 세 우위로 돌아온다 (2분)

```text
확률의 우위   근거 있는 판단을 반복한다
              → 기대값으로 보고, 결과가 아니라 과정을 복기한다        (세션 1)

절제의 우위   규칙을 지키고 한도를 둔다
              → 되돌리기 비용으로 판단하고, 범위를 제한한다           (세션 2)

자금의 우위   한 번에 다 걸지 않는다
              → 작은 변경, 작은 배포, 권한 등급                       (세션 3)
```

> 카지노는 이기는 법을 아는 게 아니라, **지지 않고 계속 앉아 있는 법**을 압니다.
> 오늘 들은 것 중 **하나만** 내일 해보신다면 무엇을 고르시겠습니까?

## Q&A 설계 (60분) ★ 회사별 차별화가 일어나는 유일한 구간

슬라이드가 한 벌이므로, **이 60분이 두 강연을 다르게 만드는 전부다.**

### 사전 질문 3개 — 가장 중요한 준비물

강연 전에 회사별로 **"가장 깊게 듣고 싶은 질문 3개"**를 받는다.

- 같은 자료로 발표하고도 뒷부분 60분이 완전히 달라진다
- 답변을 미리 준비할 수 있어 밀도가 올라간다
- 세션 중에 "이건 이따 Q&A에서"라고 연결할 수 있다 → 집중이 유지된다

### 진행 구조

| 시간 | 방식 | 비고 |
|---|---|---|
| 0~5분 | 사전 질문 3개를 화면에 띄우고 시작 | "오늘 이 세 개는 반드시 답하고 갑니다" |
| 5~35분 | 사전 질문 답변 | 준비한 답변 + 관련 슬라이드 재활용 |
| 35~55분 | 현장 질문 | 세션 중 나온 질문 메모를 먼저 소진 |
| 55~60분 | "내일 할 수 있는 것 3가지" | 회사별로 다르게 |

### 회사 1 트랙 — 예상 질문과 답변 경로

| 질문 | 되돌아갈 슬라이드 | 답변의 뼈대 |
|---|---|---|
| "저희는 뭐부터 해야 하나요?" | 2-4 되돌리기 비용 | 정답 대신 **분류 기준**. 쉬운 건 그냥, 어려운 것만 회의 |
| "인력을 뺄 수가 없는데요" | 2-4 범위 제한 | 비율이 아니라 **범위**로 제한 |
| "리팩터링 우선순위는?" | 2-2 촉매 | "코드가 나쁘다"는 이유가 아니다. **예정된 변경**이 이유다 |
| "RDS 알람이 계속 울립니다" | 1-3 안전 착각 + 2-5 알람 3조건 | 임계치 상향은 틀리지 않았다. **그 다음에 뭘 했는지**가 문제 |
| "문서를 어디까지 써야 하나요?" | 2-6 | 낡은 문서가 없는 문서보다 위험. **유지할 자신이 있는 것만** |
| "PM이 어디까지 정리해줘야?" | 2-6 인수 조건 | 화면 상세도가 아니라 **완료 조건의 명확도** |
| "대기업 방식 중 뭘 가져올까요?" | 2-6 규모별 대안 | 방식이 아니라 **그 방식이 푸는 문제**를 본다 |
| "해외 사용자가 느립니다" | 2-6 | 대부분 리전이 아니라 **요청 수와 페이로드 크기** |

**회사 1의 마무리 3가지 (예시안)**
1. PR 하나에서 구조 변경과 동작 변경을 커밋으로 분리해본다
2. 실행 쿼리에 호출자 주석을 심는다 (`/* app= svc= ep= */`)
3. 부채 하나를 **촉매까지 포함한 투자 논지**로 적어본다

### 회사 2 트랙 — 예상 질문과 답변 경로

| 질문 | 되돌아갈 슬라이드 | 답변의 뼈대 |
|---|---|---|
| "전담 조직이 필요한가요?" | 3-3 소유 모델 | 소규모엔 **오너 1명 + 공용 레포** |
| "잘 동작하는지 어떻게 판단?" | 3-4 지표 | 모델 점수 말고 **워크플로 결과 지표** |
| "폐기한 것과 살아남은 것의 차이?" | 3-4 폐기 | **기존 흐름 안에 있느냐** |
| "AI 코드가 사고를 내면 책임은?" | 3-4 대원칙 | 새 체계가 아니라 **기존 체계 그대로** |
| "격리 컨테이너 vs 사람 검수?" | 3-3 권한 등급 | 양자택일이 아니라 **위험도별로** |
| "리뷰와 QA 중 어디에 무게가?" | 3-4 이동 표 | 리뷰 횟수↑ 깊이↓, QA는 **탐색적 테스트로** |
| "공수 산정을 어떻게 다시?" | 3-1 | 구현 시간이 아니라 **검증 가능한 변경 단위** |
| "Figma에서 정확하게 뽑는 법?" | 3-5 | 도구가 아니라 **디자인 시스템** |
| "비개발자 생산성은?" | 3-5 | 도구가 아니라 **안전한 접근 경로** |
| "직군 경계가 흐려지나요?" | 3-5 | 할 수 있는 것의 경계는 흐려지고 **책임은 그대로** |

**회사 2의 마무리 3가지 (예시안)**
1. 저장소 루트에 규칙 파일 한 장을 만든다
2. 테스트·린트를 **한 줄 명령**으로 실행되게 만든다
3. 지금 쓰는 AI 도구의 **주간 실제 사용률**을 한 번 측정해본다

### 범위 밖 질문의 처리 문법

> "그건 제가 여러분 시스템을 봐야 답할 수 있는데, 제가 아는 **일반적인 판단 기준**은 이렇습니다. 이 기준으로 보시면 어떨까요."

정답 대신 **판단 기준**을 주는 것으로 일관되게 처리한다.

조심할 유형:
- 특정 기업의 비공개 정책 → 공개 범위만, 개인 경험은 소속사 공식 입장과 구분
- 즉석 진단 요청 → 기준으로 되돌린다
- "판교에서는?" → 방식이 아니라 **그 방식이 푸는 문제**로 답한다

## 부록. 투자 개념 ↔ 개발 개념 대응표

발표 중 언제든 되돌아올 수 있는 한 장. 슬라이드 마지막에 배치를 권장.

| 투자 | 개발 | 등장 |
|---|---|---|
| 하우스 엣지 | 근거 있는 판단이 주는 작은 우위 | 1-1 |
| 겜블러의 파산 | 한 방에 걸면 결국 퇴장한다 | 1-1 |
| 기대값 | 성공 확률 × 이득 − 실패 시 **되돌리기 비용** | 1-2 |
| 매매일지 | 포스트모템 · ADR | 1-2 |
| 타자화 | 코드 리뷰 · 페어링 | 1-3 |
| 안전 착각 | "몇 번 안 터졌으니 괜찮다" | 1-3 |
| 베팅 사이즈 | PR·배포 단위 크기 | 1-4 |
| 테이블 리밋 | 에이전트 권한 등급 | 1-4, 3-3 |
| 자연 수익률 −10% | 방치하면 코드베이스는 나빠진다 | 1-4 |
| 자본 배분 | 스프린트 시간 배분 | 2-2 |
| 촉매(catalyst) | **예정된 변경** | 2-2 |
| 옵션 가치 | 구조 개선 | 2-2 |
| 투자 논지 | 부채 기록 (반증 조건 포함) | 2-2 |
| 시장의 비효율 | 아무도 안 보는데 비용이 나가는 곳 | 2-2 |
| 알파 | 남을 따라해서는 안 나온다 | 2-2 |
| 손절 라인 | 롤백 경로 · 실패 판정 기준 | 1-4, 2-4 |
| 분산 | 작은 변경, 여러 번 | 1-4, 3-1 |
| 시행 횟수 | AI가 늘려주는 것 | 3-1 |

## 남은 결정 사항

1. **경험 슬롯 7개** — 발표의 실질적 가치는 여기서 나온다. 실패담 위주로 채운다. 사례가 정해지면 세션별 시간 배분을 다시 조정.
2. **사전 질문 3개 수집** — 단일 자료로 가는 이상 **가장 중요한 준비물.**
3. **카지노 훅의 수위** — 대표가 참석하는 자리에서 도박 비유를 얼마나 밀지. 현재는 "카지노형 조직 vs 도박꾼형 조직"으로 프레이밍해 비유가 조직 진단이 아니라 자기 점검으로 읽히게 했다.
4. **그리디/A\* 블록의 난이도** — 비개발 직군(대표·PM·디자이너)이 참석하면 `f = g + h` 수식은 부담일 수 있다. 수식 없이 "지금까지 쓴 비용 + 남은 예상 비용" 말로만 갈지 결정 필요.
5. **시연 포함 여부** — 넣으면 세션 3에서 10분 필요, 3-3/3-4를 줄여야 한다.
6. **세션 내 즉석 질문 10분 운용** — 45분을 35+10으로 쪼갤지, 통으로 하고 Q&A에 몰지.
