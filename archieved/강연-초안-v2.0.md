# 부산 스타트업 강연 구성안 v2.0 — 기준을 세우고, 적용하고, 다시 검증하기

> 오프닝 15분 + (발표 40분 + 즉석 Q&A 5분 + 휴식 10분) × 3 + 커피챗 45분.
> 두 회사에 같은 자료를 사용하고, 현장에서 받은 질문과 커피챗으로 강조점만 조정한다.

## v2.0에서 바꾼 것

v0.2에서 좋았던 세 단계의 구조를 강연의 중심으로 되돌린다.

```text
세션 1. 마음가짐        →  무엇을 기준으로 판단할 것인가   (판단의 기준)
세션 2. 좋은 소프트웨어  →  그 기준을 코드와 조직에 적용    (기준의 적용)
세션 3. AI 시대         →  도구가 바뀌어도 기준은 남는가    (기준의 재검증)
```

v1.1은 카지노의 세 가지 우위가 강연 전체를 설명했다. 비유가 강해서 기억에는 남지만, 뒤의 모든 내용을 비유에 맞춰 설명해야 했고 강연의 실제 주제인 **엔지니어의 판단**이 한 단계 뒤로 밀렸다.

v2.0에서는 다음처럼 위계를 바꾼다.

```text
판단의 기준                       ← 강연의 중심축
├─ 카지노                         ← 불확실성을 다루는 짧은 사례
├─ 투자·부채                       ← 시간 배분을 설명하는 국소 비유
├─ 그리디·A*                       ← 결정 속도를 설명하는 선택적 비유
└─ Context·Execution·Verification  ← AI 개발을 점검하는 실행 구조
```

즉, 카지노 이야기는 버리지 않는다. 세션 1에서 **작은 우위, 손실 한도, 반복 가능성**을 설명하는 4분짜리 사례로 사용한다. 이후 세션을 카지노 용어로 회수하지 않는다.

### v1.1에서 유지하는 것

- 같은 자료로 두 회사를 진행한다.
- 소규모 청중이므로 발표 중 질문을 받는다.
- 회사 사례는 개인 경험과 회사 공식 입장을 구분한다.
- `가역성`과 `기술 부채의 금리`는 핵심 도구로 유지한다.
- “AI가 먹기 좋은 코드베이스는 사람이 일하기 좋은 코드베이스와 같다”는 연결 문장을 유지한다.
- AI 세션은 `Context → Execution → Verification → Feedback`으로 설명한다.

### v1.1에서 덜어내는 것

- 카지노형 조직과 도박꾼형 조직의 이분법을 반복하지 않는다.
- 투자 개념을 모든 주장에 일대일로 대응시키지 않는다.
- 그리디와 A*의 수식 설명은 본문에서 빼고 개발자 질문이 나왔을 때만 부록으로 사용한다.
- 사례를 많이 보여주기보다 각 세션의 질문에 정확히 답하는 사례만 남긴다.

## 0. 전체 설계

### 0.1 강연의 중심 명제

> 좋은 엔지니어는 정답을 많이 아는 사람이 아니라, **불완전한 정보 속에서도 설명 가능한 판단을 반복하는 사람**이다.

코드, 조직, AI는 판단의 대상이 달라진 것뿐이다. 세션마다 새로운 철학을 소개하지 않고, 세션 1에서 만든 같은 기준을 세션 2와 3에서 계속 사용한다.

```text
             [세션 1] 판단의 기준을 만든다
                         │
                         ▼
      목적 ─── 근거 ─── 가역성 ─── 피드백과 책임
                         │
             ┌───────────┴───────────┐
             ▼                       ▼
 [세션 2] 코드와 조직에 적용    [세션 3] AI로 다시 검증
```

### 0.2 네 개의 판단 질문

강연에서 반복할 기준은 네 가지다. 슬라이드 한 장에 계속 같은 순서로 노출한다.

| 기준 | 질문 | 이 질문이 막는 것 |
|---|---|---|
| **목적** | 누구의 어떤 문제를 왜 지금 푸는가? | 유행 추종, 목적 없는 리팩터링과 자동화 |
| **근거** | 무엇을 알고, 무엇을 가정하며, 어떻게 확인할 것인가? | 권위 의존, 결과 편향, 근거 없는 확신 |
| **가역성** | 틀리면 얼마나 잃고, 얼마나 쉽게 되돌릴 수 있는가? | 한 번의 큰 실패, 과도한 회의와 과소한 검토 |
| **피드백과 책임** | 누가 언제 결과를 확인하고 다음 행동을 결정하는가? | 방치된 알람·문서·AI 도구, 책임 공백 |

이 네 질문을 한 문장으로 줄이면 다음과 같다.

> **왜 하는지 말하고, 아는 것과 모르는 것을 구분하고, 틀렸을 때의 피해를 제한하고, 결과를 확인할 사람과 시점을 정한다.**

좋은 판단은 언제나 좋은 결과를 만들지는 않는다. 대신 결과가 나빴을 때 배우게 하고, 한 번의 실패가 조직의 퇴장으로 이어지지 않게 한다.

### 0.3 세 세션의 관계

| 세션 | 중심 질문 | 청중이 가져갈 것 |
|---|---|---|
| **1. 판단의 기준** | 불확실한데도 결정해야 할 때 무엇을 볼 것인가? | 네 질문으로 된 판단 카드 |
| **2. 기준의 적용** | 기능, 리팩터링, 테스트, 문서화 중 어디에 시간을 쓸 것인가? | 금리 × 가역성, 작은 변경, 조직의 피드백 장치 |
| **3. 기준의 재검증** | AI가 구현 비용을 낮춘 뒤에도 같은 기준이 유효한가? | 더 싼 생성보다 더 명확한 맥락·권한·검증·피드백 |

세션 사이의 전환 문장은 미리 정해둔다.

```text
1 → 2  판단 기준이 쓸모 있으려면 오늘의 코드와 일정에 적용할 수 있어야 합니다.
2 → 3  그런데 구현 비용을 AI가 크게 낮추면, 방금 만든 기준도 달라져야 할까요?
```

### 0.4 시간표

| 시각 | 구성 | 길이 |
|---|---|---:|
| 09:00~09:15 | 오프닝 — 소개, 범위, 관심사, 오늘의 지도 | 15분 |
| 09:15~09:55 | 세션 1. 무엇을 기준으로 판단할 것인가 | 40분 |
| 09:55~10:00 | 즉석 Q&A ① | 5분 |
| 10:00~10:10 | 휴식 | 10분 |
| 10:10~10:50 | 세션 2. 그 기준을 코드와 조직에 적용 | 40분 |
| 10:50~10:55 | 즉석 Q&A ② | 5분 |
| 10:55~11:05 | 휴식 | 10분 |
| 11:05~11:45 | 세션 3. 도구가 바뀌어도 기준은 남는가 | 40분 |
| 11:45~11:50 | 즉석 Q&A ③ | 5분 |
| 11:50~12:00 | 휴식 | 10분 |

총 3시간 45분이다. 남은 15분은 현장 대화와 지연을 위한 버퍼로 둔다.

각 40분 세션의 본문은 **36분 분량**으로 설계한다. 남은 4분은 세션 중간 질문과 사례 호흡에 쓴다. 즉석 Q&A 5분은 별도다.

### 0.5 두 회사에 같은 자료를 쓰는 원칙

자료는 같되 질문을 연결하는 방식이 달라진다.

| 세션 | 회사 1에 닿는 질문 | 회사 2에 닿는 질문 |
|---|---|---|
| 1 | 무엇을 먼저 고치고 무엇을 미룰까? | 새로운 도구를 어떤 근거로 도입할까? |
| 2 | 기술 부채, RDS 알람, 문서화, 역할 분담 | AI가 일하기 좋은 코드베이스의 선행 조건 |
| 3 | AI 도입 전 무엇부터 정리할까? | Harness, MCP, Eval, 책임, 비개발 직군 협업 |

회사별 맞춤 진단을 하지 않는다. 현장 질문에는 해결책을 바로 단정하기보다 네 기준으로 되묻는다.

> “제가 지금 시스템을 보지 않고 정답을 말씀드릴 수는 없습니다. 다만 목적, 근거, 가역성, 피드백의 네 칸에 놓아보면 먼저 확인할 것은 이렇습니다.”

### 0.6 사례 사용 원칙

사례는 주장을 끌고 가지 않고, 기준이 실제로 작동하는 모습을 보여준다.

```text
기준 제시 → 짧은 사례 → 기준으로 사례 해석 → 청중의 상황에 질문
```

피할 흐름:

```text
긴 사례 → 또 다른 사례 → 사례에서 교훈 추출 → 원래 질문을 잊음
```

사례 하나는 가능하면 2분 안에 끝낸다. 긴 사례는 커피챗으로 넘긴다.

### 0.7 소속사 경험을 말하는 경계

오프닝과 세션 3 시작에서 한 번씩 밝힌다.

> “오늘 말씀드리는 회사 경험은 제 개인 경험이고 회사의 공식 입장이 아닙니다. 공개된 범위 안에서만 말씀드리겠습니다. 구체적인 보안 정책, 내부 수치나 아직 공개되지 않은 내용은 답변드리기 어렵습니다.”

- “카카오뱅크는”보다 “제가 있던 팀에서는”을 쓴다.
- 내부 지표, 비용, 인력, 보안 상세, 미공개 장애는 말하지 않는다.
- 답하기 어려운 질문은 끊고 공개 사례나 일반 기준으로 전환한다.
- 기존 v1.1의 `[KB]` 장문 원고는 발표 전 공개 범위를 다시 검수한다.

# 오프닝 (15분)

## O-1. 자기소개 — 어떤 답을 줄 수 있는가 (3분)

- 2019년부터 백엔드 개발자로 일했다.
- 클라우드 플랫폼, 은행의 메인 홈·수신·인증, AI 서버 영역에서 서비스를 만들고 바꿔왔다.
- 성공 공식보다 **판단이 빗나갔던 순간과 그 뒤에 바꾼 장치**를 이야기한다.

발표 문장:

> “경력이 쌓이면서 정답을 더 많이 알게 됐다기보다, 결정을 내릴 때 묻는 질문이 늘었습니다. 예전에는 ‘기술적으로 가능한가’를 주로 봤다면, 지금은 ‘왜 지금 해야 하는가, 틀리면 무엇을 잃는가, 누가 결과를 확인하는가’까지 함께 봅니다. 오늘은 그 질문들을 나누려고 합니다.”

## O-2. 범위 선언 (2분)

> “오늘은 여러분 회사의 시스템을 진단하고 최적안을 드리는 자리가 아닙니다. 제 실무 경험과 공개된 사례를 바탕으로 판단 기준을 나누는 자리입니다. 같은 기준으로 보더라도 상황에 따라 답은 달라질 수 있습니다.”

소속사 경험에 대한 면책 문구도 여기서 이어 말한다.

## O-3. 관심사 확인 (5분)

> “오늘 네 시간 중에 어떤 질문에 답을 얻고 가고 싶으신가요? 한 분씩 한 문장으로만 말씀해 주세요.”

- 화이트보드나 종이에 질문을 그대로 적는다.
- 대표·사업부장의 질문도 따로 듣는다.
- 세션 중 관련 내용이 나오면 “아까 말씀하신 질문이 이 부분입니다”라고 연결한다.
- 다루지 못한 질문은 커피챗에서 하나씩 지운다.

## O-4. 오늘의 지도 (3분)

```text
1. 기준을 세운다    목적 · 근거 · 가역성 · 피드백과 책임
2. 기준을 적용한다  코드 · 기술 부채 · 조직의 일하는 방식
3. 기준을 검증한다  AI가 바꾼 것과 바꾸지 못한 것
```

> “세 세션에 새로운 정답이 하나씩 나오지는 않습니다. 같은 네 질문이 대상만 바꿔서 반복됩니다. 마지막에는 AI 시대에도 이 질문들이 살아남는지 확인해보겠습니다.”

## O-5. 진행 방식 (2분)

- 세션 중간에도 질문을 받는다.
- 각 세션 끝 5분은 답변보다 질문 수집에 가깝다.
- 길어진 질문은 적어두고 커피챗에서 이어간다.
- 비개발 직군을 위해 코드나 수식은 결론을 먼저 말하고 짧게 지나간다.

# 세션 1. 무엇을 기준으로 판단할 것인가 (40분)

> **한 문장:** 좋은 판단은 미래를 맞히는 능력이 아니라, 목적과 근거를 드러내고 실패 비용을 제한하며 결과에서 배우는 과정이다.

## 1-1. 경력이 쌓일수록 답보다 질문이 늘어난다 (4분)

주니어 시절에는 다음 질문으로 충분해 보였다.

```text
이 구현이 가능한가?
이 코드가 더 깔끔한가?
이 기술이 더 빠른가?
```

하지만 실무의 결정은 기술만으로 닫히지 않는다.

```text
가능하지만 지금 할 가치가 있는가?
깔끔하지만 다음 변경에 실제로 도움이 되는가?
빠르지만 운영과 복구까지 감당할 수 있는가?
```

> 기술 선택은 정답 찾기가 아니라 여러 종류의 비용을 비교하는 일이다.

여기서 `[KB 3] 8년 차가 되며 바뀐 습관`을 60초로 압축해 사용한다. 회사의 방식이 아니라 개인의 변화이므로 오프닝 사례로 안전하고, 강연 주제와 바로 연결된다.

## 1-2. 좋은 결과와 좋은 판단은 다르다 (6분)

결과만 보면 네 종류의 상황을 구분할 수 없다.

| 판단 과정 | 결과 | 평가 |
|---|---|---|
| 좋음 | 좋음 | 반복할 가치가 있다 |
| 좋음 | 나쁨 | 운이 나빴을 수 있다. 가정을 복기한다 |
| 나쁨 | 좋음 | **가장 위험하다. 잘못된 자신감이 생긴다** |
| 나쁨 | 나쁨 | 실패 비용을 제한하고 학습한다 |

- 장애가 없었다고 설계가 안전했던 것은 아니다.
- 장애가 났다고 당시 판단이 반드시 나빴던 것도 아니다.
- 성공담도 당시의 가정과 대안을 기록하지 않으면 학습 자료가 되지 않는다.

> “좋은 판단 뒤의 실패”와 “나쁜 판단 뒤의 행운”을 구분할 수 있어야 한다.

비난 없는 포스트모템은 이 구분을 조직의 습관으로 만든다.

```text
누가 실수했는가?              → 왜 이 실수가 장애까지 갈 수 있었는가?
왜 조심하지 않았는가?          → 시스템은 왜 미리 발견하거나 제한하지 못했는가?
누구 책임인가?                 → 다음에는 어떤 장치가 피해를 줄이는가?
```

사용 사례: `[KB 2] 홈 색상 fallback과 로그 폭증`을 90초 버전으로 말한다.

사례의 결론은 “로그를 켠 사람이 실수했다”가 아니다.

- 이상한 코드에는 과거의 맥락이 있을 수 있다.
- 사용자 오류가 없었다는 사실은 안전의 증거가 아니다.
- 작은 코드 변경도 트래픽과 관측 시스템을 만나면 큰 운영 변경이 된다.
- 다음 판단을 바꿀 장치가 남아야 회고가 끝난다.

## 1-3. 판단 카드 — 네 질문 (8분)

### ① 목적 — 누구의 어떤 문제를 왜 지금 푸는가

“좋은 기술인가?”는 결정으로 이어지지 않는다. 목적과 시점을 함께 물어야 한다.

```text
나쁜 설명: 코드가 더러워서 리팩터링한다.
좋은 설명: 다음 스프린트의 환불 정책 변경 때 같은 분기를 세 곳에서
          수정해야 하므로, 이번 변경 전에 경계를 하나로 모은다.
```

### ② 근거 — 무엇을 알고 무엇을 가정하는가

사실, 해석, 가정을 분리한다.

```text
사실: 최근 3개월간 이 모듈이 12번 바뀌었다.
해석: 변경 때마다 회귀 오류 위험이 커진다.
가정: 경계를 분리하면 변경 시간이 줄어들 것이다.
검증: 다음 두 번의 변경 리드타임과 롤백 여부를 본다.
```

“구글도 쓴다”, “요즘 다 쓴다”, “제가 해봐서 안다”는 참고 자료이지 우리 상황의 근거는 아니다.

### ③ 가역성 — 틀리면 얼마나 잃고 되돌릴 수 있는가

| 가역적인 결정 | 비가역적인 결정 |
|---|---|
| 이름 변경, 함수 추출, 작은 내부 구조 | DB 스키마, 외부 API, 데이터 의미 |
| 담당자가 빠르게 시도 | 충분한 검토와 단계적 전환 |
| 실패하면 되돌림 | 실패하면 장기간 함께 살아야 함 |

핵심은 모든 결정을 신중하게 하는 것이 아니다.

> **가역적인 결정은 빠르게, 비가역적인 결정은 천천히 한다.**

### ④ 피드백과 책임 — 누가 언제 확인하는가

“배포 후 보자”는 피드백 계획이 아니다.

```text
무엇을 본다: 오류율, 지연시간, 이탈률, 재작업률
언제 본다: 1시간 후, 하루 후, 다음 스프린트 회고
누가 본다: 배포 담당자와 기능 오너
문제면 무엇을 한다: 롤백, 플래그 해제, 범위 축소
```

담당자와 시점이 없으면 알람도, 문서도, 실험도 방치된다.

## 1-4. 카지노는 왜 매번 이길 필요가 없는가 (4분)

이 블록은 네 질문 가운데 **근거·가역성·피드백**을 기억시키는 짧은 사례다.

유럽식 룰렛의 빨강은 37칸 중 18칸이다. 카지노는 한 판에서 약 48.6%의 확률로 진다. 그래도 장기적으로 살아남는 이유는 세 가지다.

| 카지노의 장치 | 엔지니어링에서의 의미 |
|---|---|
| 작지만 반복되는 확률 우위 | 완벽한 예측보다 근거 있는 작은 개선 |
| 베팅 한도 | 한 번에 잃을 수 있는 범위 제한 |
| 충분한 반복 | 작은 변경과 빠른 피드백 |

> 카지노의 교훈은 도박처럼 개발하자는 것이 아니다. **매번 맞히려 하지 말고, 틀려도 다음 판단을 할 수 있게 설계하자**는 것이다.

여기서 멈춘다. 복리 수익률 표, 카지노형 조직 대 도박꾼형 조직, 세 우위의 반복 회수는 본문에서 사용하지 않는다.

## 1-5. 개인의 판단을 조직의 장치로 옮긴다 (8분)

사람이 늘 옳게 판단하도록 요구할 수는 없다. 좋은 조직은 네 질문을 업무 흐름 안에 넣는다.

| 기준 | 개인의 질문 | 조직의 장치 |
|---|---|---|
| 목적 | 왜 하는가? | 요구사항의 완료 조건, 작업 제안서 |
| 근거 | 무엇을 가정했나? | ADR, 실험 계획, 포스트모템 |
| 가역성 | 틀리면 어떻게 돌아오나? | 기능 플래그, 카나리, 작은 PR, 백업 |
| 피드백과 책임 | 누가 언제 보나? | CI, 알람 오너, 코드 리뷰, 회고 |

### “조심하자”는 대책이 아니다

```text
좋은 의도와 기억에 의존
        ↓
반복 가능한 절차로 만든다
        ↓
가능한 것은 도구로 자동화한다
```

사용 사례: `[KB 4] 규칙을 도구로 옮긴 사례` 가운데 하나만 고른다.

- 정산 결과 확인을 배포 전 주의사항이 아니라 CI의 통합 테스트 관문으로 만든 사례
- 수기로 하던 복구를 재처리 기능으로 옮긴 사례

둘 다 설명하지 않는다. 청중의 질문과 가까운 하나를 고른다.

### 작은 조직은 문서가 적어도 되지만 기억에 의존해서는 안 된다

| 남길 것 | 목적 | 최소 형태 |
|---|---|---|
| 코드와 가까운 규칙 | 실행 방법, 제약 | README와 테스트 |
| 되돌리기 어려운 결정 | 왜 이 길을 택했나 | 1쪽 ADR |
| 장애와 학습 | 다음에 무엇을 바꾸나 | 5줄 포스트모템 |
| 진행 중 약속 | 누가 언제 무엇을 하나 | 이슈·티켓 |

문서를 많이 쓰는 것이 목표가 아니다. **다음 판단에 쓰이지 않을 문서는 만들지 않고, 만들었다면 오너와 갱신 시점을 둔다.**

## 1-6. 추정과 약속을 구분한다 (5분)

| 구분 | 의미 | 표현 |
|---|---|---|
| 추정 | 현재 정보로 본 범위와 가능성 | “3~5일이 유력하고 외부 API 이슈가 있으면 8일입니다.” |
| 약속 | 특정 범위를 특정 시점까지 책임지겠다는 합의 | “수요일까지 A 범위를 인수 가능한 상태로 만들겠습니다.” |

날짜 하나만 말하면 듣는 사람은 약속으로 받아들인다. 네 판단 질문으로 일정 대화를 바꾼다.

```text
목적: 금요일에 꼭 검증해야 하는 고객 가치는 무엇인가?
근거: 현재 확실한 일과 아직 모르는 일은 무엇인가?
가역성: 줄이거나 나중에 붙일 수 있는 범위는 무엇인가?
책임: 위험이 현실화되면 언제 누구에게 알릴 것인가?
```

좋은 거절은 반대가 아니라 선택지를 만드는 일이다.

> “전체 범위는 어렵습니다. 필수 A와 B는 금요일까지 가능하고, C까지 유지하면 다음 주 수요일입니다. 금요일이 고정이라면 C의 범위를 다시 정해야 합니다.”

사용 사례: `[KB 7] 일정·범위 협상의 실제 화법`.

## 1-7. 마무리 (1분)

청중에게 네 질문을 다시 읽게 한다.

- 누구의 어떤 문제를 왜 지금 푸는가?
- 무엇을 알고, 무엇을 가정하며, 어떻게 확인할 것인가?
- 틀리면 얼마나 잃고 얼마나 쉽게 되돌릴 수 있는가?
- 누가 언제 결과를 확인하고 다음 행동을 정하는가?

전환:

> “이 기준이 좋은 말에 그치지 않으려면 오늘의 코드와 일정에 적용할 수 있어야 합니다. 이제 ‘좋은 소프트웨어’라는 추상적인 말을 실제 시간 배분 문제로 바꿔보겠습니다.”

# 세션 2. 그 기준을 코드와 조직에 적용 (40분)

> **한 문장:** 좋은 소프트웨어는 깨끗한 소프트웨어가 아니라, 필요한 변화를 안전하고 지속 가능하게 받아들이는 소프트웨어다.

## 2-1. 좋은 소프트웨어는 계속 바꿀 수 있는 소프트웨어다 (4분)

프로그래밍이 현재 문제를 푸는 코드를 쓰는 일이라면, 소프트웨어 엔지니어링은 그 코드가 시간과 규모를 지나며 계속 바뀔 것까지 다루는 일이다.

```text
좋은 소프트웨어
├─ 빠르게 배운다       작은 변경 · 실험 · 관측 · 피드백
└─ 복잡성을 통제한다   경계 · 응집도 · 정보 은닉 · 낮은 결합도
```

두 축은 연결된다.

```text
경계가 명확하다 → 변경이 작아진다 → 피드백이 빨라진다
피드백이 빠르다 → 틀린 설계를 일찍 안다 → 복잡성이 덜 쌓인다
```

> 좋은 구조는 아름다운 구조가 아니라 **다음 판단의 비용을 낮추는 구조**다.

## 2-2. 판단 카드를 개발 작업에 대입한다 (3분)

| 기준 | 기능 개발 | 리팩터링 | 운영·조직 |
|---|---|---|---|
| 목적 | 어떤 사용자 가치를 검증하나 | 어떤 변경 마찰을 줄이나 | 어떤 반복 실패를 막나 |
| 근거 | 성공을 무엇으로 확인하나 | 변경 빈도와 추가 비용은 얼마인가 | 알람·리뷰·문서가 실제 쓰이나 |
| 가역성 | 기능을 끄거나 축소할 수 있나 | 동작과 구조 변경을 분리했나 | 새 규칙을 작게 시험할 수 있나 |
| 피드백과 책임 | 지표 오너가 누구인가 | 다음 변경에서 효과를 누가 보나 | 관리·갱신·폐기 담당이 있는가 |

이 표가 세션 2의 목차다.

## 2-3. 목적 — 개발자의 시간은 포트폴리오다 (6분)

“좋은 일인가?”보다 “왜 지금 다른 일 대신 이 일을 하는가?”를 묻는다.

| 시간의 사용처 | 현재 얻는 것 | 미래에 얻는 것 |
|---|---|---|
| 기능 개발 | 고객 가치와 매출 | 시장 학습 |
| 구조 개선 | 현재 변경 마찰 감소 | 다음 변경의 선택권 |
| 관측·자동화 | 상태를 아는 정보 | 사고 제한과 반복 비용 감소 |
| 학습 | 당장 불확실 | 더 나은 판단과 탐색 비용 감소 |

- 100% 기능에 쓰면 다음 변경의 선택권이 사라진다.
- 100% 구조 개선에 쓰면 회수할 고객 가치가 없다.
- 관측에 0을 쓰면 성공과 실패를 구분할 수 없다.
- 정답 비율은 없다. 다만 네 칸의 비용을 의식적으로 비교해야 한다.

### 촉매 — 왜 하필 지금인가

좋은 리팩터링에는 실제로 그 구조를 사용할 예정된 변경이 있다.

```text
현재 마찰: 주문 상태를 바꿀 때 다섯 모듈을 함께 수정한다.
촉매: 다음 스프린트에 환불 정책 변경이 예정돼 있다.
비용: 경계를 모으는 데 이틀이 든다.
회수: 앞으로 두 번의 정책 변경 안에 회수할 것으로 본다.
보류 조건: 환불 기능이 취소되면 작업도 보류한다.
```

> “코드가 나쁘다”는 이유는 늘 참이라 우선순위를 정하지 못한다. **예정된 변경이 있는가**가 시점을 정한다.

사용 사례: `[KB 8] 셀카 인증 이미지 처리 개선`을 목적 중심으로 2분 이내에 사용한다.

- 모델 입력 품질과 전달 비용에 직접 영향을 주는 압축·전달 구조는 이번 범위에 포함했다.
- 여러 서버에 흩어진 결합도 문제까지 한꺼번에 풀지는 않았다.
- 효과가 직접적이고 범위가 작은 개선은 지금, 크고 결합된 개선은 촉매가 생길 때 한다.

## 2-4. 근거 — 기술 부채는 크기가 아니라 금리를 본다 (7분)

기술 부채 자체는 도덕적 실패가 아니다. 그 부채 때문에 반복해서 내는 비용이 문제다.

```text
기술 부채의 이자 = 그 부채 때문에 변경 때마다 추가로 드는 비용
이자율 후보       = 변경 빈도 × 변경당 추가 비용 × 앞으로의 변경 가능성
```

| | 저금리 | 고금리 |
|---|---|---|
| 예 | 3년째 안 건드린 배치, 곧 폐기할 코드 | 매주 바뀌는 결제 모듈, 배포마다 수작업 |
| 판단 | 의도적으로 둔다 | 먼저 갚을 후보로 올린다 |

“오래된 코드”, “테스트가 적은 코드”, “보기 싫은 코드”만으로는 금리를 알 수 없다.

확인할 근거:

1. 지난 3~6개월에 얼마나 자주 바뀌었는가?
2. 바꿀 때마다 추가로 얼마나 오래 걸렸는가?
3. 장애·롤백·문의와 연결됐는가?
4. 로드맵상 앞으로 몇 번 더 바뀔 것인가?

개발자 참고용 예시:

```bash
git log --since="6 months ago" --format= --name-only \
  | sort | uniq -c | sort -rn | head -20
```

이 명령의 결과가 정답은 아니다. **자주 바뀌는 곳에 로드맵과 장애 기록을 겹쳐보는 출발점**이다.

### 금리 × 가역성

| | 저금리 | 고금리 |
|---|---|---|
| **가역적** | 안 하거나 보류 | **작게 지금 한다** |
| **비가역적** | 기록하고 관찰 | **계획을 세우고 단계적으로 갚는다** |

가장 위험한 것은 자주 바뀌는데 되돌리기 어려운 영역이다. 외부 API, 데이터 의미, 결제·정산 규칙처럼 한번 공개하면 함께 살아야 하는 것들이다.

## 2-5. 가역성 — 모든 결정에 같은 회의를 열지 않는다 (6분)

| | 빠르게 결정 | 충분히 검토 |
|---|---|---|
| 가역적 | 이름, 내부 함수, 작은 라이브러리 실험 | 대개 불필요 |
| 비가역적 | 위험 | 스키마, 외부 계약, 데이터 이전, 권한 |

조직이 느려지는 흔한 이유는 결정이 많아서가 아니라 **가역적 결정을 비가역적으로 다루기 때문**이다. 반대로 큰 사고는 비가역적 결정을 가역적인 것처럼 밀어붙일 때 난다.

> 변수명에는 30분을 쓰면서 스키마는 한 번에 배포하고 있지 않은가?

### 작은 변경은 속도 기법이면서 위험 관리 기법이다

- 구조 변경과 동작 변경을 커밋으로 분리한다.
- 기능 플래그로 노출을 분리한다.
- 한 번에 한 가정을 검증한다.
- 롤백 경로를 배포 전에 확인한다.
- 공개 API는 관찰 가능한 동작도 계약이 될 수 있다고 본다.

사용 사례: `[KB 5] 코드 리뷰가 실제로 도는 방식`.

핵심은 “리뷰어 수가 몇 명인가”가 아니다.

- 작은 커밋은 리뷰어가 변경 의도를 구분하게 한다.
- 구조와 동작을 분리하면 검증 질문도 달라진다.
- 3명 팀에서는 리뷰가 결함 검출보다 지식 공유와 버스 팩터 감소에 더 중요할 수 있다.

## 2-6. 피드백 — 테스트·관측·문서는 하나의 시스템이다 (7분)

변경 전, 변경 중, 변경 후에 서로 다른 피드백 장치가 필요하다.

```text
변경 전    타입 · 정적 분석 · 단위/통합 테스트
변경 중    코드 리뷰 · 작은 커밋 · 인수 조건
배포 중    카나리 · 기능 플래그 · 버전별 지표
배포 후    알람 · 로그 · 사용자 행동 · 포스트모템
다음 변경  문서 · ADR · 부채 기록
```

### 좋은 알람의 세 조건

1. 사용자가 실제로 겪는 문제와 연결된다.
2. 받는 사람이 할 수 있는 행동이 있다.
3. 오너와 대응 시간이 정해져 있다.

액션 없는 알람은 정보가 아니라 소음이다. 임계치를 올리는 것 자체는 틀리지 않지만, 그 과정에서 실제 현상을 확인하지 않았다면 **모르는 상태를 조용하게 만든 것**뿐이다.

사용 사례: `[KB 9] 자동로그인 부분 배포와 버전별 관측`을 2분 이내로 사용한다.

- 일부 사용자에게 먼저 배포했다.
- 단순 전체 오류율이 아니라 버전별 상태를 볼 수 있어야 했다.
- 부분 배포만 하고 비교 가능한 관측을 만들지 않으면 학습이 일어나지 않는다.

### 문서는 다음 판단의 입력이다

문서화 수준을 페이지 수로 정하지 않는다.

| 문서 | 반드시 답해야 하는 것 |
|---|---|
| README | 어떻게 실행하고 검증하는가 |
| ADR | 어떤 대안 중 왜 이것을 골랐는가 |
| 포스트모템 | 무엇을 배웠고 어떤 장치를 바꾸는가 |
| 운영 문서 | 알람이 오면 누가 무엇을 하는가 |

낡은 문서는 없는 문서보다 위험할 수 있다. 오너와 갱신 조건을 둘 수 없는 문서는 과감히 줄인다.

## 2-7. 적용의 최소 단위 (3분)

거대한 개선 프로그램 대신 다음 한 장으로 시작한다.

```text
[변경 제안]
목적: 어떤 반복 비용 또는 고객 문제를 줄이는가?
근거: 최근 변경·장애·문의에서 무엇을 봤는가?
가역성: 범위, 롤백 방법, 최대 손실은 무엇인가?
피드백: 성공/실패를 무엇으로, 언제, 누가 확인하는가?
결정: 지금 / 다음 변경 때 / 관찰 / 하지 않음
```

전환:

> “지금까지는 사람이 코드를 쓰는 비용을 전제로 했습니다. 그런데 AI가 구현을 훨씬 싸게 만들면, 목적·근거·가역성·피드백도 오래된 기준이 되는 걸까요?”

---

# 세션 3. 도구가 바뀌어도 기준은 남는가 (40분)

> **한 문장:** AI는 생성 비용과 시도 횟수를 바꾸지만, 무엇을 만들지 정하고 피해를 제한하며 결과를 검증할 책임까지 없애지는 않는다.

## 3-0. 앞선 발표를 이어받는다 (2분)

회사 2가 이미 김현규 님의 발표를 들었다면 다음처럼 연결한다.

> “앞선 발표에서 평가 기준이 명료할수록 AI가 더 잘 동작한다는 이야기를 들으셨을 겁니다. 저는 그다음 질문을 해보겠습니다. 그 기준을 조직은 어디에 두고, AI에 어떤 권한을 주며, 결과를 어떻게 검증하고 개선할까요?”

소속사 경험은 개인 경험이라는 점을 짧게 다시 밝힌다.

## 3-1. AI가 바꾼 것과 바꾸지 않은 것 (5분)

| AI가 크게 바꾼 것 | 아직 바꾸지 못한 것 |
|---|---|
| 초안과 구현의 한계 비용 | 어떤 문제가 중요한지 정하는 일 |
| 한 사람이 시도할 수 있는 횟수 | 운영 환경의 맥락과 암묵지 |
| 코드·테스트·문서 생성량 | 결과의 사실성·도메인 정확성 |
| 직군이 직접 해볼 수 있는 범위 | 출시 승인과 사고의 책임 |

가장 중요한 변화는 “코드를 더 잘 쓴다”보다 **변경을 훨씬 많이 만들 수 있다**는 것이다.

```text
생성 비용 ↓  →  변경량 ↑  →  검토할 가정 ↑  →  검증 병목 ↑
```

따라서 공수도 구현 시간만으로 재기 어려워진다.

```text
전체 비용 = 문제 정의 + 맥락 제공 + 생성 + 검증 + 통합 + 운영 관찰
```

AI는 주로 생성 비용을 줄인다. 법무·보안·도메인 합의·운영 검증은 같은 속도로 줄지 않는다.

사용 사례: `[KB 10] 공수 산정이 실제로 바뀌었는가`.

핵심은 “공수가 몇 퍼센트 줄었다”가 아니다.

- 공식 일정 기준이 즉시 사라진 것은 아니다.
- 줄어든 구현 시간을 검증과 구조 개선에 다시 쓸 수 있다.
- 산정 단위가 코드량에서 **검증 가능한 변경 단위**로 이동한다.

## 3-2. 네 기준을 AI 앞에서 다시 묻는다 (3분)

| 기준 | AI가 던지는 착시 | 다시 물어야 할 질문 |
|---|---|---|
| 목적 | 만들기 쉬우니 일단 만든다 | 반복해서 쓰일 실제 문제가 있는가? |
| 근거 | 그럴듯한 답을 증거로 착각한다 | 어떤 입력·도구·평가로 확인했는가? |
| 가역성 | 샌드박스 성공을 운영 안전으로 착각한다 | 권한과 영향 범위를 어디까지 줬는가? |
| 피드백과 책임 | 생성 주체에게 책임도 넘긴다 | 누가 승인하고 품질·폐기를 관리하는가? |

결론:

> 기준은 남는다. 다만 AI는 네 기준을 **더 자주, 더 명시적으로** 요구한다.

이제 조직의 AI 개발 흐름을 네 기준에 맞춰 본다.

```text
목적
  ↓
Context → Execution → Verification → Feedback
  ↑                                      │
  └──────────────────────────────────────┘
```

## 3-3. Context — 기준과 맥락을 실행 가능한 형태로 만든다 (6분)

AI에 맥락을 많이 주는 것이 목표가 아니다. **지금 작업에 필요한 신뢰 가능한 맥락을 찾기 쉽게 만드는 것**이 목표다.

좋은 컨텍스트의 조건:

- 실행·테스트 명령이 한 곳에 있고 실제로 동작한다.
- 모듈 경계와 공개 인터페이스가 명확하다.
- 도메인 용어가 코드·문서·디자인에서 일치한다.
- 대표적인 좋은 예시와 실패 예시가 있다.
- 문서의 오너와 갱신 시점이 보인다.
- 오래된 규칙을 제거할 수 있다.

> AI가 먹기 좋은 코드베이스는 사람이 일하기 좋은 코드베이스와 같다.

차이는 AI가 암묵적인 맥락을 물어보지 않고 그럴듯하게 채워버릴 수 있다는 점이다. 사람에게 불편했던 모호함이 AI에게는 대량 오류의 원인이 된다.

사용 사례: `[KB 11] AI가 먹기 좋게 정비한 것`.

- 거대한 규칙 파일 하나보다 최소 진입 문서와 링크 구조를 둔다.
- 반복 절차는 장문의 설명보다 실행 가능한 Skill이나 명령으로 옮긴다.
- `docs/`와 README 인덱스로 발견 가능성을 높인다.
- 규칙이 늘어나는 속도만큼 삭제와 갱신 비용도 본다.

토스 공개 사례 후보:

- Swagger·소스 조회 MCP가 모든 정보를 한 번에 넣지 않고 필요한 정의를 단계적으로 조회하게 한 사례
- Technical Writing 문서에서 책임자와 검토 주기를 두고 오래된 지식을 관리한 사례

사례의 결론은 “MCP를 쓰자”가 아니다. **신뢰 가능한 맥락을 작게 조회하고 최신성을 관리하자**는 것이다.

## 3-4. Execution — 가역성에 따라 권한을 다르게 준다 (6분)

“격리 컨테이너인가, 사람 검수인가?”는 양자택일이 아니다. 실행 권한과 영향 범위를 기준으로 등급을 나눈다.

| 등급 | 가능한 작업 | 필요한 장치 |
|---|---|---|
| 0. 제안 | 설명, 초안, 계획 | 사람 확인 |
| 1. 읽기 | 코드·문서·지표 조회 | 최소 권한, 감사 로그 |
| 2. 로컬 변경 | 브랜치 코드·테스트 생성 | 샌드박스, 자동 테스트 |
| 3. 공유 자산 변경 | PR·문서 수정 | 리뷰, CI, 승인 |
| 4. 운영 영향 | 배포·데이터·권한 변경 | 별도 승인, 제한된 도구, 롤백 |

```text
가역적이고 영향이 작다   → 더 자율적으로 실행
비가역적이거나 영향이 크다 → 권한을 좁히고 검증 관문을 늘림
```

에이전트마다 새로운 책임 원칙이 필요한 것은 아니다. 기존 운영 권한과 변경 관리 원칙을 같은 방식으로 적용한다.

사용 사례: `[KB 12] Harness·MCP의 소유와 확산`을 여기서 사용한다.

- 팀의 실제 문제에서 작은 도구가 시작된다.
- 공용 저장소를 열어 다른 사람이 보고 기여할 수 있게 한다.
- 반복 사용과 수요가 확인되면 공용 자산으로 승격한다.
- 중앙 팀은 공통 보안·배포·발견 경로를 제공하고, 도메인 팀은 맥락과 품질을 책임진다.

소규모 조직의 현실적인 시작점:

> 전담 조직보다 **오너 1명 + 공용 저장소 + 기여 규칙 + 최소 권한**이 먼저다.

## 3-5. Verification — 생성 속도가 아니라 검증 가능한 속도를 높인다 (7분)

대원칙:

> AI는 저자가 아니라 도구다. 머지하고 배포를 승인한 사람이 결과를 책임진다.

AI 코드가 사고를 내면 첫 질문은 “AI가 왜 틀렸나?”가 아니다.

> “왜 이 변경이 우리의 테스트, 리뷰, 권한 경계를 통과했는가?”

### 자동 검증과 사람 검토의 역할

| 자동화가 먼저 볼 것 | 사람이 집중할 것 |
|---|---|
| 포맷, 린트, 타입, 컴파일 | 문제 정의와 설계 의도 |
| 기존·생성 테스트 | 도메인 규칙과 빠진 요구사항 |
| 정적 분석, 비밀·취약점 규칙 | 보안·권한·개인정보의 맥락 |
| 중복, 관습적 코드 스멜 | 운영 데이터와 외부 계약의 영향 |
| 변경 범위와 금지 파일 | 비가역적 변경의 승인 |

리뷰와 QA가 사라지는 것이 아니라 무게중심이 이동한다.

```text
기계가 결정적으로 확인할 수 있는 것 → 자동화
의미와 책임이 필요한 것             → 사람
```

AI가 테스트를 많이 만든다고 테스트를 신뢰할 수 있는 것은 아니다. 좋은 테스트의 기준을 팀이 먼저 가져야 한다.

- 내부 구현보다 공개된 동작을 검증한다.
- 호출 순서보다 의미 있는 최종 상태를 본다.
- 리팩터링만으로 쉽게 깨지지 않는다.
- 테스트 자체에 복잡한 분기와 반복을 넣지 않는다.
- 실제 구현이 가능하면 목보다 실제 구현이나 페이크를 선호한다.

토스 공개 사례 후보:

1. Skill 품질 Rubric: 결정적으로 판정 가능한 항목은 규칙으로, 의미 판단은 LLM으로 검사하고 BLOCKER는 배포를 막은 사례
2. 취약점 분석: LLM의 의미 판단을 Semgrep 같은 결정적 도구와 결합한 사례
3. 토스인컴 E2E 자동화: AI가 구현량을 맡고 사람이 문제 정의·제약·검토·승인을 맡은 사례

세 개를 모두 말하지 않는다. 질문에 맞는 하나만 본문에서 쓰고 나머지는 커피챗에 남긴다.

## 3-6. Feedback — 살아남는 도구는 업무 흐름 안에서 배운다 (3분)

AI 도구의 성공을 모델 점수 하나로 재지 않는다.

| 관점 | 볼 수 있는 신호 |
|---|---|
| 품질 | 재작업률, 롤백률, 리뷰 지적, 누락 결함 |
| 속도 | PR 리드타임, 첫 피드백까지 시간 |
| 채택 | 주간 실제 사용, 반복 사용자, 중단 이유 |
| 비용 | 토큰·인프라 비용, 유지보수 시간 |
| 경험 | 개발자·비개발자의 만족과 마찰 |

단일 지표를 KPI로 걸면 행동이 왜곡된다. 사용률, 품질, 비용을 정성 피드백과 함께 본다.

계속 쓰이는 도구와 사라지는 도구의 차이:

```text
살아남기 쉬움  PR·CI·메신저처럼 이미 쓰는 흐름 안에서 자동으로 만남
사라지기 쉬움  별도 설치·사이트·명령을 사용자가 기억해서 찾아가야 함
```

토스의 Technical Writing Skill 사례를 사용한다.

- 좋은 원칙을 Skill로 만들었지만 설치·호출·맥락 수집의 마찰 때문에 기대만큼 쓰이지 않았다.
- 메신저와 GitHub Actions처럼 기존 업무 흐름 안으로 전달 방식을 옮겼다.
- 모델보다 **호출 마찰과 피드백 경로**를 먼저 고친 사례다.

사용 사례: `[KB 13] 폐기한 것과 살아남은 것`은 개인 관찰임을 밝히고 90초로 압축한다.

> 관리할 사람이 없고 반복해서 호출되지 않으며 다른 사람이 기여할 수 없는 도구는 조용히 사라진다.

## 3-7. 직군의 경계보다 책임의 경계를 본다 (2분)

AI로 “할 수 있는 것”의 경계는 넓어진다. 그러나 누가 요구사항, 품질, 보안, 접근성, 출시를 승인하는지는 저절로 바뀌지 않는다.

비개발 직군을 위해 개발자가 할 일은 프롬프트를 대신 써주는 것보다 **안전한 접근 경로를 제품화하는 것**이다.

- 읽기 전용 데이터와 승인된 도구
- 반복 요청의 셀프서비스화
- 샌드박스와 예시
- 이미 쓰는 메신저·문서·디자인 흐름 안의 진입점

Figma와 Agent의 정확도도 연동 자체보다 선행 조건에서 나온다.

```text
디자인 토큰 없음 + 컴포넌트 이름 불일치 → AI가 매번 추측
토큰 + 상태 + 코드와 같은 컴포넌트 이름 → AI는 매핑에 집중
```

> 할 수 있는 일의 경계는 흐려져도 **최종 책임의 경계는 명시해야 한다.**

## 3-8. 마무리 — 무엇이 남았는가 (2분)

| 기준 | AI 이전 | AI 이후 |
|---|---|---|
| 목적 | 무엇을 만들까 | **쉬워졌다는 이유로 만들고 있지 않은가** |
| 근거 | 어떤 증거가 있나 | **그럴듯함과 검증을 구분했나** |
| 가역성 | 실패 비용은 얼마인가 | **권한과 생성량이 키운 영향 범위를 제한했나** |
| 피드백과 책임 | 누가 결과를 보나 | **누가 승인·갱신·폐기를 책임지나** |

최종 문장:

> “도구가 바뀌어도 기준은 남습니다. 오히려 만드는 일이 쉬워질수록, 왜 만드는지와 어떻게 검증할지를 더 엄격하게 물어야 합니다.”

커피챗으로 넘기는 질문:

> “오늘 네 질문 가운데 여러분 팀이 가장 자주 생략하는 질문은 무엇인가요?”

# 질의응답과 커피챗 설계

## 즉석 Q&A 5분

세션마다 다음 형식으로 받는다.

1. 방금 내용에서 동의하기 어려운 지점을 먼저 묻는다.
2. 짧게 답할 질문 1~2개만 받는다.
3. 길어질 질문은 화이트보드에 적고 커피챗으로 넘긴다.

질문이 없을 때 발표자가 던질 질문:

| 세션 | 질문 |
|---|---|
| 1 | “최근 결과는 좋았지만 과정은 위험했던 결정이 있었나요?” |
| 2 | “자주 바뀌는데 계속 불편한 곳이 어디인가요?” |
| 3 | “지금 쓰는 AI 도구에서 생성보다 검증이 오래 걸리는 일은 무엇인가요?” |

## 커피챗 45분

```text
0~5분    오프닝에 적은 질문의 우선순위 확인
5~33분   우선 질문 3~4개를 네 기준으로 함께 분해
33~40분  양쪽 회사별 ‘내일 할 일’ 정리
40~45분  마지막 질문과 전체 회수
```

답변은 다음 순서를 지킨다.

```text
1. 질문을 다시 말한다.
2. 사실이 부족하면 진단할 수 없는 범위를 밝힌다.
3. 목적·근거·가역성·피드백 중 빠진 칸을 찾는다.
4. 선택지와 트레이드오프를 말한다.
5. 내일 확인할 수 있는 작은 행동으로 끝낸다.
```

# 슬라이드 구성 초안

슬라이드 수는 약 32장으로 제한한다. 사례가 길어져도 본문을 줄이지 않도록 각 세션의 선택 슬라이드를 정한다.

## 오프닝 4장

1. 제목 — 기준을 세우고, 적용하고, 다시 검증하기
2. 오늘 답하지 않을 것 — 맞춤 진단과 하나의 정답
3. 청중 질문 수집
4. 오늘의 지도 — 기준 / 적용 / 재검증

## 세션 1: 9장

1. 경력이 쌓일수록 답보다 질문이 늘었다
2. 좋은 결과와 좋은 판단은 다르다
3. 판단 카드 — 목적·근거·가역성·피드백
4. 목적과 근거
5. 가역성과 피드백
6. 카지노는 왜 매번 이길 필요가 없는가
7. 개인의 판단을 조직의 장치로
8. 추정과 약속
9. 네 질문 요약

## 세션 2: 9장

1. 좋은 소프트웨어 = 계속 바꿀 수 있는 소프트웨어
2. 판단 카드를 코드와 조직에 대입
3. 시간 포트폴리오
4. 촉매 — 왜 지금인가
5. 기술 부채의 금리
6. 금리 × 가역성
7. 작은 변경과 리뷰
8. 테스트·관측·문서의 피드백 계층
9. 변경 제안 한 장

## 세션 3: 10장

1. AI가 바꾼 것과 바꾸지 않은 것
2. 생성 비용 감소 → 검증 병목
3. 네 기준을 AI 앞에서 다시 묻기
4. Context
5. AI가 먹기 좋은 코드베이스
6. Execution 권한 등급
7. Verification — 자동과 사람의 역할
8. Feedback — 측정과 폐기
9. 직군 경계와 책임 경계
10. 도구가 바뀌어도 기준은 남는다

시간이 부족하면 뺄 수 있는 선택 슬라이드:

- 세션 1의 카지노 세부 수치
- 세션 2의 시간 포트폴리오 세부 사례
- 세션 3의 직군 경계 사례

빼면 안 되는 슬라이드:

- 판단 카드
- 금리 × 가역성
- AI가 바꾼 것과 바꾸지 않은 것
- 실행 권한 등급
- 자동 검증과 사람 검토의 역할
- 최종 회수

# 부록 A. 선택적으로만 사용할 비유

사용 목적: 기대값과 손실 제한을 직관적으로 설명한다.

- 시간 포트폴리오

- 알파와 시장 비효율
- 자연 수익률
- 복리 수익률 표

본문에서는 사용하지 않는다. 개발자 질문이 나왔을 때 다음 결론만 사용한다.

```text
가역적 결정   → 빠른 국소 선택이 합리적일 수 있다.
비가역적 결정 → 더 넓게 탐색하고 총비용을 비교해야 한다.
이미 쓴 비용  → 앞으로 회수할 수 없다면 매몰비용이다.
```

수식과 동전 교환 반례는 질의응답용으로만 둔다.

# 부록 B. 이 버전의 논리 점검

v2.0은 다음 질문에 모두 같은 언어로 답해야 한다.

| 질문 | 답의 출발점 |
|---|---|
| 신기술을 도입할까요? | 목적과 검증할 가정 |
| 리팩터링을 지금 할까요? | 촉매와 금리 |
| 회의를 얼마나 해야 하나요? | 가역성 |
| 문서를 어디까지 쓸까요? | 다음 판단에 쓰이는가, 오너가 있는가 |
| 알람 임계치를 올려도 되나요? | 사용자 영향과 대응 행동 |
| AI Agent에 배포 권한을 줄까요? | 가역성과 영향 범위 |
| Eval은 무엇으로 하나요? | 목적에 연결된 결과 + 결정적 검사 + 의미 평가 |
| AI가 만든 코드의 책임은 누구에게 있나요? | 승인과 배포 권한을 가진 사람과 조직 |
| 도구를 계속 유지할까요? | 실제 사용, 품질, 비용, 오너, 폐기 조건 |

어떤 질문에 답할 때도 카지노 비유가 없어서는 설명할 수 없다면 구조가 다시 비유 중심으로 돌아간 것이다. 네 판단 질문만으로 먼저 답하고, 비유는 이해를 도울 때만 붙인다.
