# 『Tidy First?』 리팩터링 핵심 정리

> Kent Beck, *Tidy First?: A Personal Exercise in Empirical Software Design*

## 한 줄 요약

『Tidy First?』의 핵심은 리팩터링을 위한 별도 대형 프로젝트를 여는 것이 아니라, **기능을 개발하는 흐름 안에서 다음 변경을 쉽게 만드는 작은 구조 개선을 반복하는 것**이다.

책에서는 이를 일반적인 리팩터링보다 작은 개념인 **정리하기(tidying)**라고 부른다. 정리하기는 시스템이 외부에서 보이는 동작을 바꾸지 않으면서 코드의 구조를 개선하는 작업이며, 보통 몇 분에서 길어도 한 시간 이내의 개인 작업 규모를 가정한다.

---

## 1. 동작 변경과 구조 변경을 구분한다

### 동작 변경(behavior change)

시스템을 실행했을 때 관찰되는 결과가 달라지는 변경이다.

- 기능 추가
- 버그 수정
- 출력 결과 변경
- 사용자에게 보이는 성능 특성 변경

### 구조 변경(structure change)

시스템의 외부 동작은 그대로 두고 코드의 배치와 표현을 바꾸는 변경이다.

- 이름 변경
- 함수 추출 또는 인라인
- 코드 이동
- 중복 제거
- 조건문 단순화
- 인터페이스 정리

두 종류의 변경을 한꺼번에 수행하면 문제가 발생했을 때 원인을 찾기 어렵고, 코드 리뷰도 힘들어진다. 따라서 기본적인 개발 리듬은 다음과 같다.

```text
작은 구조 변경 → 테스트
작은 구조 변경 → 테스트
기능 변경       → 테스트
필요하면 다시 작은 구조 변경
```

가능하면 커밋이나 PR에서도 구조 변경과 동작 변경을 분리한다.

## 2. 언제 리팩터링할 것인가

책은 무조건 먼저 리팩터링하라고 주장하지 않는다. 상황에 따라 네 가지 선택지가 있다.

| 선택 | 적합한 상황 | 예시 |
|---|---|---|
| 먼저 정리하기 | 작은 구조 변경이 당장의 기능 개발을 더 쉽고 안전하게 만든다 | 긴 조건문을 가드 절로 바꾼 뒤 분기 추가 |
| 나중에 정리하기 | 기능을 구현해봐야 적절한 구조가 보인다 | 구현 후 발견된 중복을 제거하고 역할을 분리 |
| 훗날 정리하기 | 개선 가치는 있지만 현재 기능에는 직접 도움이 되지 않는다 | 여러 모듈에 걸친 공통 구조 개선 |
| 정리하지 않기 | 다시 변경될 가능성이 거의 없거나 비용 대비 이득이 없다 | 곧 폐기할 마이그레이션 코드 |

### 2.1 먼저 정리하기

다음 조건에 해당하면 기능을 구현하기 전에 정리하는 편이 좋다.

- 현재 구조 때문에 요구사항을 이해하기 어렵다.
- 작은 정리만으로 기능 변경 범위를 줄일 수 있다.
- 정리 후 테스트와 검증이 쉬워진다.
- 실수하기 쉬운 분기나 결합을 먼저 분리할 수 있다.
- 정리 비용을 이번 기능 개발에서 바로 회수할 수 있다.

경제적으로 단순화하면 다음 조건이다.

```text
정리 비용 + 정리 후 기능 개발 비용
<
현재 구조에서 바로 기능을 개발하는 비용
```

예를 들어 복잡한 메서드에 기능 하나를 추가해야 할 때, 관련 부분을 함수 하나로 추출하면 이후 변경이 명확해진다면 먼저 정리할 가치가 있다.

### 2.2 나중에 정리하기

다음과 같은 경우에는 기능을 먼저 구현하고 나중에 정리한다.

- 요구사항이나 적절한 추상화가 아직 불분명하다.
- 실제 구현 전에는 어떤 부분이 중복되는지 알 수 없다.
- 먼저 정리하면 사용하지 않을 구조를 추측해서 만들 가능성이 크다.
- 기능을 구현한 결과 향후 변경 방향이 명확해진다.

즉, **이해하기 위해 구조 변경이 필요하면 먼저**, **경험을 통해 구조를 발견해야 한다면 나중에** 정리한다.

### 2.3 훗날 정리하기

현재 기능과 직접 관계없는 큰 개선은 당장 하지 않아도 된다.

- 한 번의 기능 개발로 비용을 회수할 수 없는 큰 변경
- 여러 기능이나 팀이 함께 이익을 얻는 공통 구조 개선
- 현재 작업 범위를 크게 벗어나는 변경
- 시스템 경계를 바꾸는 마이그레이션

다만 이런 항목을 이유 없이 백로그에 쌓으면 실제로 실행되지 않는다. 단순히 “코드가 더럽다”라고 적지 말고 반복 비용과 예상 효과를 함께 기록해야 한다.

```text
문제: 주문 상태를 변경할 때 5개 모듈을 함께 수정해야 한다.
영향: 최근 3개 기능에서 각각 1~2일의 추가 작업이 발생했다.
다음 발생: 환불 정책 기능에서 다시 수정할 가능성이 높다.
개선 예상 비용: 2일
예상 회수: 향후 변경 2회 이내
```

### 2.4 정리하지 않기

코드가 지저분하다는 사실만으로 리팩터링의 경제적 가치가 생기지는 않는다.

- 곧 삭제될 코드
- 안정적으로 동작하며 변경 가능성이 매우 낮은 코드
- 정리해도 다음 변경 비용이 줄어들지 않는 코드
- 정리 자체가 기능 변경보다 위험한 레거시 영역

앞으로 동작을 변경할 일이 없다면 정리하지 않는 것도 합리적인 선택이다.

## 3. 전담 인력 없이 기술 부채를 줄이는 방법

핵심은 기술 부채를 별도의 대형 프로젝트로만 취급하지 않는 것이다.

### 3.1 작업하려는 영역만 정리한다

전체 코드베이스를 청소하지 않는다.

```text
이번 기능을 위해 반드시 지나가야 하는 코드
              ↓
다음 변경을 어렵게 만드는 최소한의 구조만 개선
              ↓
기능 구현
```

이렇게 하면 리팩터링은 신규 개발과 경쟁하는 별도 업무가 아니라 신규 개발 비용의 일부가 된다.

### 3.2 시간 비율보다 범위를 제한한다

“스프린트의 20%를 리팩터링에 사용한다”와 같은 고정 비율보다 다음 기준이 중요하다.

- 다음 기능에 필요한 정리만 한다.
- 한 번에 몇 분 단위로 진행한다.
- 한 시간 이상 계속된다면 범위가 커진 것은 아닌지 재검토한다.
- 정리 때문에 원래 기능의 완료 시점을 설명하기 어려워지면 중단한다.

개인 단위의 정리가 한 시간을 넘어간다면, 다음 동작 변경에 필요한 최소 구조 개선의 범위를 놓쳤을 가능성이 있다.

### 3.3 PR 또는 커밋에서 구조와 동작을 구분한다

가장 명확한 형태는 구조 변경과 기능 변경을 별도 PR로 만드는 것이다.

```text
PR 1: 구조 변경만 수행
PR 2: 기능 또는 버그 수정
```

PR을 만드는 비용이 큰 팀이라면 하나의 PR 안에서도 커밋을 분리할 수 있다.

```text
refactor: 결제 조건을 guard clause로 정리
refactor: 금액 계산을 helper로 추출
feat: 부분 환불 조건 추가
```

이렇게 하면 리뷰어는 다음처럼 서로 다른 관점으로 검토할 수 있다.

- 구조 변경: 기존 동작이 그대로 유지되는가?
- 기능 변경: 요구사항에 맞는 동작이 추가됐는가?

### 3.4 정리의 연쇄 작용을 경계한다

코드 하나를 정리하면 다른 문제도 계속 보이기 시작한다. 이것이 리팩터링 범위가 끝없이 커지는 주요 원인이다.

다음 중 하나에 도달하면 일단 정리를 멈춘다.

- 다음 기능을 안전하게 구현할 수 있게 됐다.
- 변경해야 할 코드가 충분히 좁아졌다.
- 테스트할 수 있는 경계가 생겼다.
- 추가 정리가 현재 기능과 직접 관계가 없다.
- 구조 변경이 새로운 설계 논의나 마이그레이션으로 번지기 시작했다.

## 4. 리팩터링 판단 근거

코드의 미관보다는 변경의 경제성을 기준으로 판단한다.

### 4.1 변경 빈도

앞으로 자주 바뀔 코드일수록 구조 개선의 가치가 크다. 거의 바뀌지 않는 코드는 아무리 보기 싫어도 우선순위가 낮다.

### 4.2 현재 변경 비용

다음과 같은 반복적 마찰이 있는지 확인한다.

- 작은 기능인데 여러 파일을 동시에 수정해야 한다.
- 같은 조건을 여러 곳에서 함께 바꿔야 한다.
- 코드를 이해하는 시간이 구현 시간보다 길다.
- 변경할 때마다 예상하지 못한 회귀 버그가 발생한다.
- 테스트를 작성할 수 있는 경계가 없다.

### 4.3 정리 비용과 위험

좋은 정리 작업은 작고 되돌리기 쉽다.

- 이름 변경
- 함수 추출 또는 인라인
- 코드 순서 변경
- 명시적 파라미터 도입
- 사용하지 않는 코드 삭제

대부분의 작은 구조 변경은 쉽게 되돌릴 수 있으므로 빠르게 실험할 수 있다. 반면 다음과 같은 변경은 같은 방식으로 가볍게 취급하면 안 된다.

- 데이터베이스 스키마 변경
- 외부 공개 API 변경
- 대규모 데이터 이전
- 여러 팀이 사용하는 공통 인터페이스 변경
- 운영 데이터의 의미를 바꾸는 변경

이런 결정은 되돌리는 비용이 크기 때문에 더 느리고 신중하게 검토해야 한다.

### 4.4 선택 가능성(optionality)

책에서 설계를 바라보는 가장 중요한 경제적 관점이다.

- 기능 변경은 현재 매출이나 비용 절감 같은 직접 가치를 만든다.
- 구조 변경은 앞으로 더 많은 기능을 싸고 빠르게 선택할 수 있는 가능성을 만든다.

따라서 리팩터링의 가치를 “코드가 깨끗해진다”라고 설명하는 것보다 다음처럼 설명하는 편이 낫다.

> 이 구조를 바꾸면 예정된 세 가지 기능을 각각 한 곳만 수정해서 구현할 수 있다.

기술 부채의 우선순위는 대략 다음 요소로 판단할 수 있다.

```text
예상 가치
= 향후 변경 가능성
× 변경할 때 절약되는 비용
× 영향을 받는 변경 횟수
- 현재 정리 비용
- 정리로 인한 위험과 일정 지연
```

정밀한 계산식이라기보다는 판단 과정에서 빠뜨리는 요소가 없도록 하는 체크리스트에 가깝다.

## 5. 책에서 소개하는 작은 정리 기법

| 기법 | 내용 |
|---|---|
| 가드 절(Guard Clauses) | 예외 조건을 먼저 반환해 중첩을 줄인다 |
| 죽은 코드 삭제 | 실행되지 않거나 사용되지 않는 코드를 제거한다 |
| 대칭성 맞추기 | 같은 의미의 코드를 같은 형태로 통일한다 |
| 새 인터페이스, 기존 구현 | 새로운 호출 방식을 만들고 기존 구현에 위임한다 |
| 읽는 순서 | 독자가 이해하기 좋은 순서로 코드를 배치한다 |
| 응집도 순서 | 서로 관련된 코드를 가까이 배치한다 |
| 선언과 초기화 함께 두기 | 변수의 유효 범위와 이해 부담을 줄인다 |
| 설명 변수 | 복잡한 표현식에 의도를 드러내는 이름을 붙인다 |
| 설명 상수 | 의미 없는 리터럴에 이름을 붙인다 |
| 명시적 파라미터 | 숨겨진 의존성을 함수의 입력으로 드러낸다 |
| 문장 묶기 | 함께 수행되는 문장들을 의미 단위로 묶는다 |
| 도우미 함수 추출 | 세부 구현을 이름 있는 함수로 분리한다 |
| 한 더미로 모으기 | 흩어진 관련 코드를 먼저 한곳에 모은다 |
| 설명 주석 | 코드만으로 드러나지 않는 의도를 기록한다 |
| 중복 주석 삭제 | 코드 내용을 그대로 반복하는 주석을 제거한다 |

## 6. 팀에서 사용할 수 있는 판단 체크리스트

기능 개발 중 정리가 필요해 보이면 다음 질문을 순서대로 확인한다.

1. 이 변경은 시스템의 외부 동작을 바꾸는가, 구조만 바꾸는가?
2. 지금 정리하면 바로 다음 기능을 더 쉽거나 안전하게 만들 수 있는가?
3. 정리 범위를 몇 분에서 한 시간 이내로 제한할 수 있는가?
4. 테스트로 기존 동작이 유지되는지 확인할 수 있는가?
5. 구조 변경과 기능 변경을 별도 커밋 또는 PR로 나눌 수 있는가?
6. 이번 기능과 관계없는 코드를 함께 고치고 있지는 않은가?
7. 추가 정리의 이득보다 일정 지연과 리뷰 비용이 커지지 않았는가?

하나라도 불명확하다면 범위를 더 작게 줄이거나 기능을 먼저 구현한 뒤 다시 판단한다.

---

## 7. 팀 운영 규칙으로 줄이면

1. 기능을 수정하기 전에 현재 구조가 변경을 방해하는지 확인한다.
2. 방해한다면 이번 기능을 쉽게 만드는 최소한의 구조만 먼저 바꾼다.
3. 구조 변경과 동작 변경을 커밋 또는 PR에서 구분한다.
4. 정리는 몇 분 단위로 하고, 한 시간을 넘기면 범위를 다시 검토한다.
5. 현재 기능과 관계없는 대형 개선은 반복 비용과 예상 회수 시점을 근거로 별도 투자 판단을 한다.

## 결론

『Tidy First?』의 메시지는 **“기술 부채를 모두 없애자”가 아니라 “변경할 때마다 미래의 변경 비용을 조금씩 낮추자”**에 가깝다.

전담 리팩터링 인력이 없어도 가능한 이유는 정리를 독립된 장기 프로젝트가 아니라 일상적인 기능 개발 속의 짧은 리듬으로 다루기 때문이다. 중요한 것은 깨끗함 그 자체가 아니라 다음 변경을 더 빠르고 안전하게 할 수 있는 구조를 만드는 것이다.
