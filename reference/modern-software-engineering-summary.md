# 『모던 소프트웨어 엔지니어링』 핵심 정리

> David Farley, *Modern Software Engineering: Doing What Works to Build Better Software Faster*

## 한 줄 요약

『모던 소프트웨어 엔지니어링』의 핵심은 좋은 소프트웨어 엔지니어가 단순히 코드를 많이 작성하는 사람이 아니라, **작은 실험을 통해 빠르게 학습하고 시스템의 복잡성을 지속적으로 통제하는 사람**이라는 것이다.

저자는 특정 언어나 프레임워크 대신 기술이 바뀌어도 유효한 판단 원칙을 제시한다. 소프트웨어 엔지니어링은 현실의 문제에 효율적이고 경제적인 해법을 찾기 위해 경험적·과학적 방법을 적용하는 일이다.

---

## 전체 구조

책의 내용은 크게 두 가지 역량으로 정리할 수 있다.

```text
현대적인 소프트웨어 엔지니어링
├─ 학습 능력 최적화
│  ├─ 반복
│  ├─ 피드백
│  ├─ 점진주의
│  ├─ 경험주의
│  └─ 실험주의
└─ 복잡성 관리
   ├─ 모듈성
   ├─ 응집성
   ├─ 관심사 분리
   ├─ 정보 은닉과 추상화
   └─ 결합도 관리
```

| 핵심 역량 | 목적 | 대표 실천 방법 |
|---|---|---|
| 학습 최적화 | 잘못된 가정을 빨리 발견하고 더 나은 결정을 내린다 | 반복, 빠른 피드백, 작은 변경, 실험, 측정 |
| 복잡성 관리 | 시스템이 커져도 이해하고 변경할 수 있게 유지한다 | 모듈화, 높은 응집성, 관심사 분리, 정보 은닉, 느슨한 결합 |

## 1. 소프트웨어 엔지니어링이란 무엇인가

### 소프트웨어 개발은 생산이 아니라 설계다

소프트웨어는 완성된 뒤 복제하는 비용이 거의 없다. 진짜 어려운 부분은 제품을 반복해서 생산하는 것이 아니라 다음과 같은 설계와 발견의 과정이다.

- 무엇을 만들어야 하는지 발견한다.
- 문제가 무엇인지 이해한다.
- 해결 방법을 설계한다.
- 실제로 작동하는지 검증한다.
- 이후에도 안전하게 변경할 수 있도록 유지한다.

따라서 소프트웨어 엔지니어링은 생산 공학보다 **설계 공학**에 가깝다. 처음부터 정답을 알고 계획대로 만드는 활동이 아니라, 불확실성 속에서 해법을 발견하고 검증하는 활동이다.

### 공학은 관료주의가 아니다

공학적 접근은 문서를 늘리거나 엄격한 절차를 따르는 것이 아니다. 현실적이고 경제적인 제약 안에서 과학적 사고를 적용하는 것이다.

- 가정을 명시한다.
- 결과를 측정한다.
- 반복 가능한 방법으로 검증한다.
- 증거가 예상과 다르면 생각을 수정한다.
- 비용과 효과 사이의 트레이드오프를 고려한다.

### 장인정신만으로는 충분하지 않다

개인의 솜씨와 직관은 중요하지만, 그것만으로는 큰 팀과 복잡한 시스템에서 일관된 결과를 만들기 어렵다. 개인의 경험에만 의존하지 않고 측정하고 재현하며 개선할 수 있는 체계가 필요하다.

개발 진행률 역시 작성한 코드의 양이나 완료한 작업 수가 아니라 다음 결과를 중심으로 판단해야 한다.

- 실제 사용자에게 가치가 전달됐는가?
- 소프트웨어가 검증 가능한 형태로 동작하는가?
- 품질을 유지하면서 지속적으로 변경할 수 있는가?

## 2. 첫 번째 축: 학습을 최적화하라

소프트웨어 개발에서는 요구사항과 해결 방법 모두 처음부터 완전히 알 수 없다. 개발은 정해진 계획을 실행하는 과정이 아니라, 모르는 것을 알아가는 과정이다.

### 2.1 반복

큰 계획을 한 번에 실행하지 말고 짧은 주기로 설계하고, 구현하고, 확인한다.

반복 개발은 일정 관리 기법을 넘어 잘못된 판단으로 인한 손실을 제한하는 **방어적 설계 전략**이다. 한 번의 반복 범위가 작을수록 가정이 틀렸을 때 버려야 할 코드와 비용도 작아진다.

```text
작은 목표 설정
      ↓
설계와 구현
      ↓
동작 확인
      ↓
결과를 바탕으로 다음 목표 조정
```

상세한 장기 계획에 과도하게 의존하면 새로 얻은 정보를 반영하기 어렵다. 계획은 현재의 가설로 취급하고, 반복 과정에서 계속 수정해야 한다.

### 2.2 피드백

의사결정의 품질은 피드백의 속도와 질에 좌우된다.

| 영역 | 피드백 수단 |
|---|---|
| 코딩 | 컴파일러, 정적 분석, 단위 테스트 |
| 통합 | 자동 빌드, 통합 테스트, 지속적 통합 |
| 설계 | 테스트 가능성, 코드 리뷰, 구현 결과 |
| 아키텍처 | 배포 결과, 성능 측정, 운영 관찰 |
| 제품 | 사용자 행동, 실제 사용 데이터 |
| 조직 | 팀의 독립적인 변경 및 배포 능력 |

피드백이 늦으면 여러 변경이 뒤섞여 문제의 원인을 찾기 어려워진다. 개발 환경과 배포 파이프라인은 가능한 한 빠르고 명확한 피드백을 제공해야 한다.

### 2.3 점진주의

변경을 작고 독립적인 단계로 나눈다. 작은 변경은 다음과 같은 장점이 있다.

- 이해하고 검토하기 쉽다.
- 테스트하기 쉽다.
- 실패 원인을 찾기 쉽다.
- 문제가 생겼을 때 되돌리기 쉽다.
- 변경의 부작용과 위험을 제한한다.

점진적인 작업이 가능하려면 시스템도 작은 부분을 독립적으로 변경할 수 있어야 한다. 따라서 작업 방식의 점진주의는 코드와 아키텍처의 모듈성으로 이어진다.

### 2.4 경험주의

직급, 유행, 유명한 성공 사례나 개인의 확신보다 관찰 가능한 현실을 우선한다.

“마이크로서비스가 더 좋다” 또는 “새 프레임워크가 더 빠르다”와 같은 주장은 현재의 조직과 시스템에서 실제로 검증되어야 한다. 경험주의는 측정 결과가 예상과 다를 때 자신의 생각을 수정할 준비가 되어 있는 태도다.

```text
추측이나 권위 < 관찰 가능한 증거
```

### 2.5 실험주의

단순히 무언가를 시도하는 것과 제대로 실험하는 것은 다르다. 유효한 실험에는 다음 요소가 필요하다.

1. 검증할 가설을 세운다.
2. 관찰하고 측정할 결과를 정한다.
3. 가능한 범위에서 변수를 통제한다.
4. 실패 비용이 작은 범위에서 실행한다.
5. 결과를 다음 의사결정에 반영한다.

저자는 TDD를 대표적인 실험 과정으로 본다.

```text
실패하는 테스트 → 최소 구현 → 테스트 통과 → 리팩터링
```

이때 테스트는 단순한 결함 탐지 장치가 아니다. 설계에 관한 가설을 검증하고 새로운 지식을 얻는 측정 장치이기도 하다.

## 3. 두 번째 축: 복잡성을 관리하라

복잡성은 두 종류로 나눌 수 있다.

| 종류 | 의미 | 대응 방법 |
|---|---|---|
| 본질적 복잡성 | 해결하려는 업무와 문제 자체에 존재하는 복잡성 | 정확하게 이해하고 적절하게 모델링한다 |
| 우발적 복잡성 | 잘못된 기술, 구조, 프로세스 때문에 추가된 복잡성 | 설계 개선과 자동화를 통해 줄인다 |

본질적 복잡성은 완전히 제거하기 어렵지만, 우발적 복잡성은 좋은 설계로 상당 부분 줄일 수 있다.

### 3.1 모듈성

시스템을 독립적으로 이해하고 변경하고 조합할 수 있는 부분으로 나눈다.

좋은 모듈은 다음 특성을 가진다.

- 내부 구현을 몰라도 사용할 수 있다.
- 변경이 다른 영역에 미치는 영향이 제한적이다.
- 독립적으로 테스트할 수 있다.
- 가능하다면 독립적으로 배포할 수 있다.
- 역할과 경계가 명확하다.

테스트하기 어려운 코드는 모듈 경계가 불명확하거나 의존성이 지나치게 얽혀 있다는 신호일 가능성이 크다. 따라서 테스트 가능성은 설계 품질을 측정하는 중요한 지표다.

### 3.2 응집성

서로 밀접하게 관련된 데이터와 동작을 같은 장소에 둔다.

한 기능을 변경하기 위해 여러 디렉터리와 서비스를 돌아다녀야 한다면 응집성이 낮다. 하나의 모듈이 서로 무관한 여러 책임을 담당하는 경우도 마찬가지다.

좋은 경계를 만들려면 **같은 이유와 주기로 변경되는 요소를 함께 배치**해야 한다. DDD의 경계 컨텍스트는 업무 개념을 응집성 있게 묶는 대표적인 방법이다.

### 3.3 관심사 분리

업무 규칙, 사용자 인터페이스, 데이터베이스, 네트워크, 외부 시스템처럼 서로 다른 관심사가 뒤섞이지 않도록 한다.

예를 들어 핵심 업무 로직이 특정 데이터베이스나 웹 프레임워크를 직접 호출하면 테스트와 변경이 어려워진다. 다음과 같은 구조를 이용해 핵심 로직과 기술 세부 사항을 분리할 수 있다.

- 의존성 주입
- 포트와 어댑터 또는 육각형 아키텍처
- 명확한 API 경계
- DDD의 경계 컨텍스트
- TDD를 통한 상향식 설계

테스트하기 쉬운 코드는 대체로 관심사가 잘 분리되어 있다.

### 3.4 정보 은닉과 추상화

모듈은 자신의 내부 결정과 변경 가능성이 큰 세부 사항을 외부에 노출하지 않아야 한다.

좋은 추상화는 단순히 코드를 짧게 만드는 것이 아니라, 사용자가 알 필요 없는 정보를 숨긴다. 특히 다음과 같이 자주 바뀌거나 직접 통제할 수 없는 요소는 명확한 경계 뒤에 두는 편이 좋다.

- 외부 라이브러리
- 데이터베이스
- 네트워크 프로토콜
- 외부 서비스 API
- 프레임워크의 구체적인 사용 방식

문제 영역과 맞지 않는 억지 추상화는 오히려 복잡성을 키운다. 추상화는 미래를 추측해서 만드는 것이 아니라 실제 사용 사례와 변화 방향에서 발견해야 한다.

### 3.5 결합도 관리

한 요소의 변경이 다른 요소에 미치는 영향을 최소화한다.

느슨한 결합은 단순히 코드량이나 중복을 줄이는 것과 다르다. 서로 다른 이유와 속도로 변화하는 코드를 중복 제거를 위해 공통 모듈로 묶으면 오히려 결합도가 높아질 수 있다.

따라서 DRY 원칙도 기계적으로 적용하면 안 된다.

```text
잘못된 결합으로 만든 공통화보다
의도가 분명한 작은 중복이 나을 수 있다.
```

마이크로서비스 역시 느슨한 결합을 자동으로 보장하지 않는다. 서비스가 데이터베이스, 동기 호출, 배포 절차 또는 조직의 승인 과정으로 강하게 연결되어 있다면 분산된 모놀리스에 불과하다.

## 4. 엔지니어링을 지원하는 실천 도구

책에서 TDD, 지속적 통합, 지속적 배포 등을 강조하는 이유는 이것들이 유행하는 모범 사례이기 때문이 아니다. 빠른 학습과 복잡성 관리라는 원칙을 실제로 구현하기 때문이다.

| 도구 또는 실천 방법 | 제공하는 효과 |
|---|---|
| 자동화 테스트 | 빠르고 반복 가능한 측정과 회귀 검증 |
| TDD | 테스트 가능하고 모듈화된 설계 유도 |
| 지속적 통합 | 변경을 자주 합쳐 통합 문제를 조기에 발견 |
| 배포 자동화 | 변경을 실제 환경에서 신속하고 반복적으로 검증 |
| 배포 가능성 | 구성 요소의 독립성과 경계를 평가하는 척도 |
| 관찰 가능성 | 운영 중인 시스템에서 빠른 피드백 획득 |
| 작은 변경 단위 | 실패 범위와 복구 비용 제한 |

속도는 품질을 희생해서 얻는 것이 아니다. 자동화, 작은 변경, 테스트 가능성, 좋은 모듈화가 품질과 속도를 함께 높인다.

## 5. 실무 적용 체크리스트

### 학습과 피드백

- [ ] 이번 작업을 더 작고 독립적인 단위로 나눌 수 있는가?
- [ ] 현재의 가정과 검증할 가설이 명확한가?
- [ ] 결과가 옳은지 얼마나 빨리 알 수 있는가?
- [ ] 자동화 테스트가 몇 분 안에 의미 있는 피드백을 주는가?
- [ ] 실제 사용자와 운영 환경에서 피드백을 얻고 있는가?
- [ ] 도구와 아키텍처의 효과를 실제 결과로 측정했는가?

### 변경과 배포

- [ ] 변경 하나의 영향 범위가 충분히 작은가?
- [ ] 실패했을 때 원인을 쉽게 찾을 수 있는가?
- [ ] 안전하고 빠르게 되돌릴 수 있는가?
- [ ] 소프트웨어를 언제든 배포 가능한 상태로 유지하는가?
- [ ] 빌드, 테스트, 배포 과정이 반복 가능하게 자동화되어 있는가?

### 설계와 복잡성

- [ ] 각 모듈의 역할과 경계가 분명한가?
- [ ] 관련된 코드와 데이터가 같은 경계 안에 있는가?
- [ ] 하나의 변경 때문에 무관한 여러 영역을 수정하고 있지는 않은가?
- [ ] 핵심 업무 로직이 프레임워크나 데이터베이스에 직접 의존하지 않는가?
- [ ] 외부 시스템의 세부 사항이 업무 로직으로 새고 있지는 않은가?
- [ ] 테스트하기 어려운 원인이 설계상의 결합에 있지는 않은가?
- [ ] 공통화가 서로 독립적으로 변해야 할 코드를 묶고 있지는 않은가?

---

## 6. 핵심 원칙 간의 관계

이 책에서 소개하는 원칙은 서로 독립된 기법이 아니다.

```text
작은 변경
   ↓
빠른 테스트와 배포
   ↓
빠른 피드백
   ↓
더 정확한 학습
   ↓
다음 변경의 위험 감소

테스트 가능성
   ↓
관심사 분리와 명확한 경계
   ↓
모듈성과 높은 응집성
   ↓
느슨한 결합
   ↓
복잡성 통제와 지속 가능한 변경
```

좋은 설계는 피드백을 빠르게 만들고, 빠른 피드백은 더 나은 설계를 발견하게 한다. 학습 최적화와 복잡성 관리는 서로를 강화하는 하나의 순환 구조다.

---

## 7. 도구와 방법론을 평가하는 기준

애자일, TDD, DDD, 마이크로서비스, 지속적 배포 같은 방법을 이름이나 유행만으로 선택해서는 안 된다. 현재 상황에서 다음 두 질문으로 평가해야 한다.

1. 이 방법은 우리가 **더 빠르고 정확하게 학습**하도록 돕는가?
2. 이 방법은 증가하는 **복잡성을 통제**하도록 돕는가?

두 질문에 긍정적으로 답할 수 있다면 유용한 방법이다. 그렇지 않다면 널리 사용되는 기술이라도 도입 목적과 방식을 다시 검토해야 한다.

---

## 결론

현대적인 소프트웨어 엔지니어링은 특정 개발 방법론이나 기술 스택의 이름이 아니다. 불확실한 문제를 작은 단계로 탐색하고, 빠른 피드백으로 사실을 확인하며, 좋은 설계 원칙을 통해 복잡성을 통제하는 사고 체계다.

핵심을 다시 정리하면 다음과 같다.

- 개발은 계획의 단순 실행이 아니라 학습과 발견의 과정이다.
- 변경은 작고 점진적이어야 하며 피드백은 빨라야 한다.
- 주장보다 실험과 측정 가능한 증거를 우선한다.
- 테스트 가능성은 단순한 품질 속성이 아니라 설계 품질의 지표다.
- 모듈성, 응집성, 관심사 분리, 정보 은닉과 느슨한 결합으로 복잡성을 통제한다.
- 도구와 방법론은 학습 속도와 복잡성 관리 능력을 실제로 개선하는지 평가한 뒤 선택한다.

결국 좋은 소프트웨어 엔지니어링의 목적은 **더 좋은 소프트웨어를 더 빠르고, 더 안전하며, 반복 가능한 방식으로 만드는 것**이다.
