# 토스의 AI 개발문화·업무 자동화 사례 조사

- 조사 목적: 부산 스타트업 회사 2의 4시간 강연 준비
- 조사 기준일: 2026-09-03
- 출처 원칙: 토스 공식 기술 블로그, 토스 공식 채용 콘텐츠, 토스페이먼츠 개발자센터

> **해석 시 주의**  
> 토스테크에 공개된 글에는 전사 조직의 공식 운영 방식, 특정 팀의 적용 사례, 작성자 개인의 방향성 제안이 함께 존재한다. 따라서 개별 사례를 곧바로 “토스 전사 정책”으로 일반화하면 안 된다. 이 문서에서는 확인 수준을 구분해 표시한다.

## 1. 핵심 요약

토스의 공개 사례에서 반복적으로 보이는 흐름은 다음과 같다.

1. AI 활용 역량을 개인의 프롬프트 노하우에만 맡기지 않고, **Harness·Skill·MCP·테스트 인프라 같은 조직 자산**으로 만든다.
2. 공용 도구를 중앙에서 제공하되, 구체적인 문제와 도메인 맥락은 **현업 팀·길드·챕터가 직접 정의**한다.
3. 생성 결과만 평가하지 않고, Skill이 실제로 호출되는지, 안전한지, 반복 실행 가능한지까지 **명시적인 평가 기준과 자동화된 게이트**를 둔다.
4. AI가 산출물을 많이 만드는 만큼 테스트·리뷰·지식의 최신성 관리 등 **검증 비용도 함께 자동화**한다.
5. 좋은 도구를 만들어 배포하는 것만으로는 정착되지 않는다. 사내 메신저, GitHub, CLI처럼 **기존 업무 흐름 안에 넣어야 실제 사용률이 높아진다.**
6. AI가 작성과 리뷰를 보조해도 무엇을 믿을지, 누가 책임질지, 언제 갱신·폐기할지는 **사람과 조직의 거버넌스 문제**로 남는다.

## 3. 상세 사례

### 3.1 AI DX Team: 서버 Harness와 사내 공용 Skill

**확인 수준: 조직·팀의 실제 운영 사례**

토스의 AI DX Team은 토스 서버 개발을 위한 Harness를 만들고, 그 기능 중 하나로 사내 공용 Skill을 제작·배포한다. 공개 글에서는 사내에 많은 Skill이 만들어지고 공유됐지만, 잘 호출되지 않거나 효과가 없는 문제가 있었다고 설명한다.

이를 해결하기 위해 다음과 같은 품질 체계를 만들었다.

- 6개 섹션, 30개 평가 항목
- 타당성, 구조, 트리거, 콘텐츠, 리소스, 안전성 평가
- 형식처럼 결정적으로 판정할 수 있는 17개 항목은 정규식·AST 등 규칙 기반 검사
- 의미 판단이 필요한 13개 항목은 LLM 기반 검사
- BLOCKER·MAJOR·MINOR 심각도와 S~F 등급
- BLOCKER가 하나라도 있으면 배포 불가로 판단
- 저비용 규칙 검사를 먼저 실행하고, 통과한 경우에만 비용이 드는 모델 검사를 실행

**회사 2의 질문에 대한 시사점**

- “누가 관리하는가?”에는 중앙 전담팀이 공통 Harness와 품질 기준을 제공하는 사례로 답할 수 있다.
- 그러나 모든 Skill을 AI DX Team이 직접 만드는지는 공개 자료에서 확인되지 않는다. 여러 팀이 만들고 중앙에서 공용 자산과 평가 체계를 보완하는 혼합 구조로 해석하는 편이 안전하다.
- Eval은 최종 출력의 정답률뿐 아니라 **호출 가능성, 구조, 콘텐츠, 안전성, 배포 가능성**을 함께 봐야 한다.

### 3.2 사내 Swagger MCP: API 연동 맥락을 조직 자산으로 만들기

**확인 수준: 토스 서버 개발자의 실제 사내 도입 사례**

서버 개발자가 Swagger 링크를 찾아 전달하고, 연동 개발자가 변경된 명세를 다시 확인하는 반복 작업을 줄이기 위해 사내 Swagger MCP 서버를 만들었다.

구조적 특징은 다음과 같다.

- 중앙 Swagger 관리 서버에서 서비스 목록과 명세를 조회
- 전체 문서를 한 번에 주입하지 않고 서비스 목록 → API 목록 → 상세 명세 → 컴포넌트 순으로 단계적 조회
- MSA 환경과 원격 제공을 고려해 Stateless Streamable HTTP 사용
- 대량 명세의 토큰 초과 문제를 미사용 API 제거, 정보 가공, 페이징으로 해결
- LLM이 Tool을 적절히 호출하지 않는 문제를 MCP Prompt로 보완
- 정확한 Swagger 문서를 유지하기 위한 GitHub Actions 기반 작성 자동화도 실험

**회사 2의 질문에 대한 시사점**

- 좋은 MCP는 단순히 사내 데이터를 연결하는 것이 아니라, **어떤 맥락을 어떤 순서와 크기로 제공할지 설계하는 제품**에 가깝다.
- MCP 자체보다 원본 명세의 정확성, 최신성, 검색 단위가 더 중요할 수 있다.
- 공개 글은 연구·개발 환경의 사례이며 망분리된 실제 업무망과 통신하지 않는다고 명시한다. 이를 토스의 전체 보안 아키텍처로 확대 해석하면 안 된다.

### 3.3 토스페이먼츠 결제 MCP: 현업 길드에서 시작해 실제 시나리오로 비교 평가

**확인 수준: 특정 조직의 실제 제품·실험 사례**

토스페이먼츠 MCP는 전담조직의 하향식 과제라기보다 서로 다른 팀의 구성원이 모이는 길드의 작은 논의에서 시작됐다. 기존 개발자센터의 MDX 문서를 `llms.txt`로 제공하고, 로컬 MCP가 최신 문서를 탐색하도록 구성했다.

주요 설계 선택은 다음과 같다.

- 개발자센터 문서를 SSOT로 활용해 문서 버전업을 따라감
- 로컬 실행과 STDIO를 선택해 중앙 서버 비용과 별도 운영 부담을 줄임
- NPM 배포를 이용해 기존 개발자의 설치 경험을 활용
- 초기 키워드 검색의 환각과 정보 유실 문제를 겪은 뒤 검색·청킹 방식을 개선

효과 확인은 같은 결제 연동 프롬프트를 아래 세 조건에서 비교하는 방식으로 이루어졌다.

1. Cursor 단독
2. Cursor + 일반 문서 Context
3. Cursor + MCP

공개 결과에서는 MCP 조합이 SDK 주소, 세부 연동 명세와 결제 흐름을 더 정확히 반영했고, Secret Key를 프론트엔드에 노출하지 말아야 한다는 보안 가이드도 제공했다. 다만 글에서도 AI 생성 코드가 완벽하지 않다고 분명히 제한한다.

**회사 2의 질문에 대한 시사점**

- Eval은 추상적인 만족도 조사보다 **실제 업무 시나리오와 동일한 프롬프트를 두고 대조군을 비교**하는 방식이 설득력이 있다.
- “도입 효과”는 MCP 사용 여부가 아니라 결과의 명세 준수, 보안 원칙 준수, 수정 필요량으로 측정할 수 있다.
- 좋은 도구는 처음부터 완성되는 것이 아니라 실제 사용에서 발생한 검색 실패와 환각을 통해 개선된다.

### 3.4 Harness를 ‘팀의 시스템’으로 보는 관점

**확인 수준: 작성자의 방향성·가설이 중심인 글**

토스페이먼츠 개발자의 글에서는 같은 LLM을 사용해도 개인의 Context Engineering 역량에 따라 결과 편차가 커지므로, 조직이 Harness를 통해 생산성의 저점을 높여야 한다고 제안한다.

제시된 아이디어는 다음과 같다.

- 팀의 가이드와 워크플로를 플러그인·마켓플레이스로 배포
- 전사 공통 규정, 도메인 지식, 레포지토리 규칙을 Global·Domain·Local 계층으로 분리
- 일반 규칙을 에이전트가 실행할 수 있는 SSOT로 전환
- 자동 실행하되 도메인별 고위험 지점에는 Human-in-the-Loop 배치
- 공통 모듈을 코드리뷰하듯 AI 워크플로도 동료 피드백으로 개선

**회사 2의 질문에 대한 시사점**

- Harness 전파는 “프롬프트 모음 공유”보다 **팀의 표준 업무 흐름을 설치 가능한 형태로 배포하는 것**으로 설명할 수 있다.
- 다만 글 자체가 아직 성공 사례보다 방향성과 가설에 가깝다고 밝힌다. 강연에서는 토스의 확정된 전사 체계가 아니라 실무자가 제시한 발전 방향으로 소개해야 한다.

### 3.5 토스인컴: AI-driven UI 테스트 자동화

**확인 수준: 특정 서비스의 5개월 실험·운영 사례**

토스인컴 QA Manager는 복잡한 세금환급 서비스의 E2E 테스트 자동화를 2025년 7월부터 11월까지 진행했다. 기존에는 E2E 테스트 하나에 4~8시간, 40개 작성에 160~300시간이 필요할 것으로 추정됐다.

공개된 운영 방식은 다음과 같다.

- Claude Code를 SDET, 문서화, Git 역할의 페르소나로 구분
- Cursor와 Codex를 보조 도구로 병행
- AI가 테스트 코드·유틸리티·리팩터링·문서화를 주로 수행
- 사람은 문제 정의, 요구사항 정리, 맥락과 제약 설명, 결과 검토·승인에 집중
- 5개월 동안 35개 테스트를 만들어 운영 단계에 진입
- 작성자는 “AI 3명 + 사람 1명”이 4~5명 규모 자동화 팀에 해당하는 결과를 냈다고 평가

**회사 2의 질문에 대한 시사점**

- “사람이 수동 검수하던 일을 AI Agent가 수행한 사례가 있는가?”에 가장 직접적으로 대응하는 공개 사례다.
- AI가 사람을 완전히 제거한 사례라기보다, **AI가 구현량을 맡고 사람이 방향·제약·승인을 책임진 사례**로 설명하는 것이 정확하다.
- 코드 작성 속도가 빨라져도 변화가 잦은 UI와 불안정한 외부 연동을 안정적으로 반복 실행하는 것은 별도의 엔지니어링 문제다.

### 3.6 네뷸라 디바이스 팜: AI 검증을 받치는 공용 실행 인프라

**확인 수준: 전사 공용 인프라의 실제 운영 사례**

토스의 디바이스 팜 ‘네뷸라’는 기기 15대와 개발자 1명으로 시작해 실기기 100대를 넘겼고, 여러 팀의 작은 팜을 하나의 중앙 플랫폼으로 통합했다.

같은 API 위에 다음과 같은 사용 방식을 제공한다.

- 비개발자도 사용할 수 있는 웹페이지
- 개발자를 위한 SDK
- 터미널과 CI/CD에서 사용할 수 있는 CLI
- 제품 로그 자동 검수
- 스스로 판단하며 테스트하는 AI Agent
- 필요에 따른 직접 API 호출

공개된 사례에서는 사람이 OS별로 30~40분 수행하던 검수를 10분 안에 자동화했다고 설명한다. 또한 코드 생성량이 늘수록 리뷰·검증 비용이 커지므로 검증도 자동화해야 한다는 문제의식을 밝힌다.

**회사 2의 질문에 대한 시사점**

- Agent의 성능만 올리는 것으로는 충분하지 않고, **재현 가능하고 안전한 실행환경**이 함께 필요하다.
- 공용 플랫폼은 하나의 안정된 API를 제공하고, 웹·SDK·CLI·Agent 등 여러 인터페이스가 그 위에서 생겨나는 구조가 확산에 유리하다.
- 격리와 폐기에 관한 전사 정책이 공개된 것은 아니지만, 테스트 계정·데이터의 상태 준비와 원상 복구가 중요한 다음 과제로 언급된다.

### 3.7 Technical Writing 자동화: 좋은 Skill도 업무 흐름 밖에 있으면 쓰이지 않는다

**확인 수준: 토스 Technical Writing Chapter의 실제 운영 사례**

토스는 Technical Writer의 문서 작성·리뷰 원칙을 AI가 활용할 수 있는 Skill과 워크플로로 만들었다. 기존 가이드와 리뷰 코멘트를 분석하고, 잘못된 예시와 올바른 예시를 함께 제공해 AI가 원칙의 의도를 이해하게 했다.

하지만 초기 Skill은 기대만큼 사용되지 않았다. 사용자가 직접 설치·업데이트하고, 문서 작성 시점을 떠올리고, 필요한 자료를 찾아 제공해야 했기 때문이다.

이후 다음처럼 기존 업무 흐름에 통합했다.

- 사내 메신저에서 대화 맥락을 찾아 문서 초안을 만드는 챗봇
- 문서 PR이 열리면 GitHub Actions에서 자동으로 시작되는 AI 리뷰
- 사용자가 별도 설치·호출을 의식하지 않아도 되는 방식

**회사 2의 질문에 대한 시사점**

- “도입 후 사용하지 않은 시스템”에 가까운 실패 학습 사례다. 완전히 폐기한 것이 아니라 사용되지 않은 원인을 찾아 전달 방식을 바꿨다.
- 비개발자 생산성 향상을 위해 개발자가 할 수 있는 핵심은 새 CLI 사용법을 교육하는 것이 아니라, **이미 쓰는 메신저와 문서 흐름 속에 전문성을 제품화하는 것**이다.
- 사용률이 낮다고 모델이나 프롬프트부터 고치기보다 설치, 호출, 맥락 수집의 마찰부터 확인해야 한다.

### 3.8 지식 거버넌스: AI 문서의 책임·갱신·폐기

**확인 수준: 조직의 실제 지식 관리 기준과 운영 체계**

문서 생성이 쉬워진 뒤에는 비슷한 문서가 쌓이고, AI가 낡은 정책을 근거로 틀린 답을 내는 문제가 발생했다. 토스의 공개 사례는 도구가 “어떤 문서를 믿을지”, “누가 책임질지”, “언제 폐기할지”를 대신 결정하지 못한다고 설명한다.

이에 따라 다음과 같은 기준을 정리했다.

- 반복 질문, 중요 의사결정, 신규 구성원이 알아야 할 내용은 조직 지식으로 남김
- 사람과 AI가 찾을 수 있도록 분류·구조화
- 질문봇, GitHub 등 필요한 업무 순간에 연결
- 책임자와 검토 주기를 지정해 최신성 유지
- Knowledge Committee가 전사 공통 기준을 정의·유지·조율
- 각 도메인과 챕터가 자기 영역의 책임자, 갱신, 폐기를 결정

**회사 2의 질문에 대한 시사점**

- AI 생성 문서의 품질 책임은 “AI가 썼는가”보다 **신뢰할 수 있는 기준 문서가 무엇인지, 담당자와 검토 주기가 정해졌는지**의 문제로 볼 수 있다.
- 중앙 조직은 공통 기준을 관리하고, 현업 조직은 내용의 진실성과 수명주기를 관리하는 이중 구조가 가능하다.
- 자동화가 늘어날수록 문서의 생성보다 검증·갱신·폐기가 더 중요한 병목이 될 수 있다.

### 3.9 LLM 기반 취약점 분석: AI와 결정적 도구의 결합

**확인 수준: Security Researcher가 진행한 연구·자동화 사례**

토스의 보안 연구 사례에서는 LLM이 대규모 소스코드를 한 번에 이해하지 못하고, 같은 입력에서도 탐지 결과가 달라지는 문제를 겪었다.

이를 다음과 같이 보완했다.

- `tree-sitter`, `ctags`, `ripgrep`으로 소스코드를 인덱싱
- SourceCode Browse MCP를 통해 필요한 정의와 참조를 선택적으로 조회
- LLM의 비결정적 판단만 믿지 않고 Semgrep 같은 SAST 도구를 결합
- 소스 접근 도구를 제한된 Tool 인터페이스로 제공

**회사 2의 질문에 대한 시사점**

- 중요한 로직이나 보안 검증에서 AI를 단독 판정자로 두기보다 **AI의 의미 판단과 결정적인 정적 분석 도구를 조합**하는 편이 안전하다.
- 이 사례 역시 토스 전체 코드 검수 정책이 아니라 보안 연구 프로젝트 사례다.
- 공개 글만으로 실행 컨테이너 폐기 방식이나 사고 책임 프로세스까지 확인할 수는 없다.

## 4. 토스 사례에서 도출할 수 있는 운영 모델

아래 모델은 토스의 공식 조직도를 그대로 재현한 것이 아니라, 공개 사례에서 반복되는 패턴을 강연용으로 재구성한 것이다.

### 중앙에서 제공할 것

- 공통 Harness와 배포 방식
- 보안·권한·품질의 최소 기준
- Skill·MCP 평가 도구
- 공용 실행·테스트 인프라
- 조직 전체가 공유할 지식 관리 원칙

### 팀과 도메인이 책임질 것

- 실제 자동화할 문제의 선정
- 도메인 맥락과 업무 규칙
- 결과가 맞는지 판단할 시나리오와 Eval 데이터
- 고위험 작업의 사람 승인 지점
- 문서와 지식의 담당자·검토 주기·폐기 시점

### 확산을 위해 필요한 것

- 새로운 도구를 따로 배우게 하지 않고 기존 IDE·CLI·메신저·GitHub에 통합
- 설치와 업데이트 자동화
- 초기 사용자의 피드백을 빠르게 반영
- 결과 품질뿐 아니라 호출률, 사용률, 재작업량, 실행 시간과 비용 측정

## 5. 공개 자료만으로 답하기 어려운 질문

다음 항목은 토스 공식 공개 자료만으로 전사 차원의 답을 단정하기 어렵다.

- AI가 작성한 코드로 사고가 났을 때의 구체적인 책임 소재와 사후 프로세스
- 중요 로직을 항상 격리 컨테이너에서 실행하고 폐기하는지 여부
- 모든 AI 작성 코드를 사람이 어느 단계에서 승인해야 하는지에 대한 전사 공통 규정
- AI 도입 후 전사 공수 산정 기준이 어떻게 변경됐는지
- 코드리뷰와 QA 중 어느 쪽에 조직적으로 더 많은 비중을 두는지
- 도입 후 완전히 폐기된 AI 시스템의 구체적인 목록
- Figma와 AI Agent를 직접 연결해 웹·Flutter·네이티브 화면을 구현하는 토스의 검증된 사례

강연에서는 위 질문에 대해 “토스는 이렇게 한다”고 답하기보다, 관련 공개 사례를 소개한 뒤 일반적인 선택지와 장단점을 설명하는 편이 안전하다.

## 6. 강연에서 사용할 수 있는 핵심 메시지

1. **좋은 모델보다 좋은 Harness가 조직의 생산성 차이를 만든다.**
2. **중앙팀은 공통 기반과 기준을 만들고, 현업팀은 도메인 맥락과 Eval을 소유한다.**
3. **Eval은 답의 품질뿐 아니라 호출 여부, 안전성, 비용과 반복 가능성을 포함한다.**
4. **AI 도구는 배포하는 것으로 끝나지 않고 기존 업무 흐름 안에 들어가야 한다.**
5. **코드 생성 비용이 내려갈수록 검증 인프라의 중요성은 커진다.**
6. **AI가 만든 산출물의 최종 책임은 모델이 아니라 승인 구조와 소유권을 설계한 조직에 남는다.**
